# 기능 구현

한국어 존댓말로 설명하며 코드·API 식별자는 원문을 유지합니다.

## 적용 범위와 비용

사용자의 명시적 요청과 기존 프로젝트 규칙을 먼저 따릅니다. 사용 범위(개인·팀·외부), 목표 단계(PoC·MVP·운영), 실제 위험, 이번 작업 예산과 완료 조건을 기존 계약에서 읽습니다. 없으면 작업에 영향을 주는 부분만 확인하거나 가정을 표시합니다. 저위험 개인 작업에 기업용 문서·로그인·CI/CD·독립 리뷰를 일괄 추가하지 않습니다. 필요한 조건을 통과하면 종료하고 선택 개선은 후속으로 남깁니다. 예산 소진 시 필수 미달은 미완료로 인계합니다. 없는 도구·권한·실행 증거를 가정하지 않습니다.

## 수행

1. 이슈·현재 코드·관련 ADR·통과한 Spec/계획과 실제 시작 버전을 확인합니다. 명확한 소규모 요청은 짧은 목표·검증으로 충분하며 장문 문서를 새로 요구하지 않습니다.
2. 기존 변경을 보존합니다. 병렬 작업 또는 분리 필요가 있으면 워크트리·브랜치·담당 범위를 확인하고 겹치는 변경을 조율합니다. 모든 개인 작업에 워크트리를 강제하지 않습니다.
3. 핵심 흐름이 끝까지 연결되도록 작은 변경을 구현합니다. 요청하지 않은 로그인·관리자·미래 확장·인프라를 추가하지 않습니다.
4. 목업의 모의 동작을 실제 저장·API·권한·오류 처리로 전환할 때 그 차이를 명시합니다. 스펙이나 중요한 결정이 바뀌면 관련 문서와 영향받는 검토만 갱신합니다.
5. 변경에 비례한 테스트·수동 실행을 수행합니다. 실패하면 원인을 확인하고 같은 입력으로 무한 재생성하지 않습니다. 기존 실패와 새 회귀를 구분합니다.

## 산출물과 종료

변경 파일·동작, 실행한 검증과 결과, 미확인·제약·남은 필수 작업을 남깁니다. 구현 리뷰 후 PR → 해당 버전 CI → 스쿼시 머지 → 스모크가 운영형 순서입니다. 실제 PR·머지·배포는 사용자의 요청·기존 권한 범위에 따릅니다. 구현 완료와 배포·사용 확인을 구분합니다.

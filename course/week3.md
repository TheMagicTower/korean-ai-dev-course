# 3주차 · 실패를 재현하고 선택을 검증합니다

오늘의 산출물은 **고친 오류의 증거, 작은 모델 비교 기록, 전달 환경의 첫 실행**입니다. 더 좋은 모델을 고르기 전에 무엇이 실패했는지 알아야 합니다.

## 120분 진행표

| 시간 | 활동 | 결과 |
|---|---|---|
| 0–10 | 핵심 흐름 점검 | 결함 목록 |
| 10–25 | 재현·원인·리뷰 시연 | 수정 근거 |
| 25–45 | 개인 과제로 두 조합 비교 | 선택 기록 |
| 45–55 | 휴식 | |
| 55–105 | 대표 실패·차단 문제 수정 | 필수 기능 확정 |
| 105–120 | 전달 환경에서 첫 실행 | 버전·전달 문제 |

## 개념 — 증상과 원인은 다릅니다

‘화면이 비었습니다’는 증상입니다. 입력 누락, 잘못된 API 응답 처리, 권한 거부, 배포 버전 차이는 서로 다른 원인입니다. 정상 입력 하나와 실패 입력 하나를 고정하고 로그·코드·계약의 근거를 비교합니다.

<div class="flow"><span>재현</span><b>→</b><span>증거</span><b>→</b><span>가설</span><b>→</b><span>최소 수정</span><b>→</b><span>원래 실패 재검증</span></div>

같은 실패를 두 번 반복했다면 세 번째 생성 전에 새 증거가 있는지 확인합니다. 입력·환경·범위가 그대로인데 모델만 바꿔 반복하는 것은 비용을 늘릴 수 있습니다.

## 강사 시연 — 새로고침 후 데이터가 사라집니다

임시 메모리와 지속 저장의 차이를 먼저 보여 줍니다. 원인을 찾기 전 저장 기능 전체를 다시 쓰게 하지 않습니다. 수정 후 원래 재현 절차와 정상 흐름을 함께 확인합니다.

```text
오류 진단 스킬을 사용해 [환경·버전]에서 [입력·절차]를 수행하면 [실제 결과]가 되는 원인을 조사해 주세요. 기대는 [기대 결과]입니다. 먼저 재현과 증거를 확인하고, 아직 재현하지 못했다면 그렇게 표시해 주세요. 이번 요청은 진단까지만 하며 코드는 수정하지 마세요.
```

## 20분 비교 실험

같은 시작 버전과 요구를 복사해 두 조합을 비교합니다. 한쪽에만 더 많은 설명이나 답을 주지 않습니다. 모델만 바꾸거나 사고 수준만 바꾸면 해석이 쉽습니다. 에이전트도 다르면 ‘제품 조합 비교’로 표시합니다.

| 기록 | 적을 내용 |
|---|---|
| 통제 | 시작 버전·입력·도구 권한·시간 한도 |
| 조합 | 에이전트·프로바이더·모델 ID·사고 설정 |
| 결과 | 수용 조건 통과·오류·사람 수정 횟수 |
| 비용 | 표시된 사용량·시간, 모르면 미확인 |
| 판단 | 내 과제에서 선택한 조합과 비교 한계 |

Jev를 선택한다면 코딩 전체 대신 문의 분류처럼 작은 판단을 비교합니다. 정답이 있는 샘플에서 규칙 기반 처리와 분류 결과·보류·오류를 확인합니다. confidence가 높다는 사실을 정답 보장으로 바꾸지 않습니다. 가입·유료 API 호출은 이 과정의 필수가 아닙니다.

## 이어지는 서비스 사례 — 검토 근거를 재사용합니다

버튼 색상 변경은 화면 확인이 중심입니다. 저장 형식 변경은 기존 공고 호환·새 저장·필터를 다시 확인해야 합니다. 친구 계정의 공고가 보이는 문제는 코드가 짧아도 높은 위험입니다. 난이도와 실패 영향을 나눠 배정합니다.

**직접 해보기:** 과거 증거·이번 변경 영향·다시 확인할 조건을 구분해 적어 보세요.

[ApplyFlow 사례와 실행 예제](case-study.md) · [수준별 프로세스 적용](../docs/adaptive-process.md)

## 내 프로젝트 검토

```text
변경 검토 스킬로 현재 변경을 검토만 해 주세요. 프로젝트 수준은 [수준], 필수 조건은 [조건]입니다. 원본 변경·ADR·실행 증거를 확인하고 핵심 목적이나 실제 위험을 깨는 블로커만 완료를 막아 주세요. 비차단 개선은 후속으로 남기고, 근거가 부족한 사항은 미확인으로 구분해 주세요.
```

필수 조건 통과 후에는 리뷰를 계속 생성하지 않습니다. 수정했다면 영향받는 지적과 흐름을 다시 확인합니다. 스펙이 바뀌지 않았는데 전체 분석부터 시작하지 않습니다.

## 오늘의 완료 확인

- [ ] 대표 실패의 입력·환경·기대·실제를 남겼습니다.
- [ ] 원인과 수정 또는 해결하지 못한 이유를 기록했습니다.
- [ ] 비교 결과를 브랜드 순위가 아닌 내 과제의 근거로 설명했습니다.
- [ ] 남은 블로커와 비차단 후속을 구분했습니다.
- [ ] 전달할 환경에서 처음 실행하고 버전을 기록했습니다.

## 다른 프로젝트에 적용하기

게임은 동일 시드의 기준선·모델 비교와 실패 로그를, 매거진은 근거 누락·중복·발행 실패를 검증합니다. 측정값이 없으면 그래프에 추정 성능을 채우지 않습니다. [사례별 검증 기준](cases/index.md)을 참고하세요. 기존120분의 사례·실습 시간을 대체하며 추가 과제로 세 프로젝트를 모두 요구하지 않습니다.

실제 사용성 개선을 검토하려면 [FlyBlock 키보드·실시간 업데이트](updates/flyblock-keyboard.md)를 사용하세요. 기능 요청을 관찰 가능한 계약으로 바꾸고, 회귀 검증과 실제 발견된 버그를 구분하는 사례입니다. 기존 사례 설명 시간을 대체합니다.

# 4주차 · 실제로 쓰는 결과물을 전달합니다

오늘의 산출물은 **실행 가능한 결과, 사용법, 검증 증거, 제한과 다음 계획**입니다. 발표 화면보다 실제 사용이 우선입니다.

## 120분 진행표

| 시간 | 활동 | 결과 |
|---|---|---|
| 0–10 | 완료 조건 확인 | 남은 필수 |
| 10–20 | 전달·배포·버전 시연 | 전달 방법 |
| 20–55 | 수정·패키징·배포·사용법 | 제출 후보 |
| 55–65 | 휴식 | |
| 65–85 | 계약 환경 재실행·동료 확인 | 사용 증거 |
| 85–105 | 차단 수정·재검증, 통과자는 시연 | 최종 후보 |
| 105–110 | 공유·피드백 | 개선 입력 |
| 110–120 | 제출·회고 | 완성품 묶음 |

## 개념 — 네 가지 성공을 구분합니다

코드 검토 통과, CI 성공, 배포 성공, 사용자 흐름 성공은 다른 상태입니다. 로컬에서 통과한 버전과 배포된 버전이 같은지도 확인합니다. 단순 로컬 도구에 서버 배포를 강요하지 않습니다.

운영형에서는 PR → CI → 스쿼시 머지 → 스모크로 통합을 확인하고, 일별 프리릴리즈·스테이징 확인과 주별 릴리즈·운영 확인을 연결할 수 있습니다. 이는 운영 확장 사례입니다. 정해진 배포 시각이 실패한 후보의 통과를 의미하지 않습니다.

## 강사 시연 — 새 환경에서 사용해 봅니다

개발 중 열린 화면을 그대로 보여 주는 대신 안내문만 보고 새 세션에서 실행합니다. 필요한 설정·실행 명령·입력 예시가 빠졌는지 확인합니다. 실제 키를 설명서에 넣지 않고 설정 이름과 위치만 안내합니다.

```text
완성품 확인 스킬로 현재 제출 후보를 검증해 주세요. 목표 수준은 [수준]이고 전달 방식은 [주소/패키지/명령]입니다. 핵심 흐름·필요한 저장·대표 실패·재실행을 계약한 환경에서 확인하고 버전·일시·증거를 남겨 주세요. 실행하지 못한 것은 미확인으로 표시하고, 필수 미달이면 완료라고 하지 마세요.
```

## 이어지는 서비스 사례 — 서비스와 데모의 완료를 구분합니다

로컬 예제의 저장 성공은 서비스 MVP의 계정별 접근 분리나 배포 성공을 입증하지 않습니다. 실제 MVP라면 새 계정·새 세션에서 공고 저장과 재방문을 확인하고 피드백을 받습니다. 첫 화면 생성부터 검증된 전달까지 시간·비용·사람 수정시간을 나눠 기록합니다.

**직접 해보기:** 합의한 수준에서 확인한 것·미확인·남은 필수를 제출물에 적으세요.

[ApplyFlow 사례와 실행 예제](case-study.md) · [수준별 프로세스 적용](../docs/adaptive-process.md)

## 제출할 다섯 가지

| 제출물 | 내용 |
|---|---|
| 실행 결과 | 주소·패키지 또는 재현 가능한 명령 |
| 프로젝트 계약 | 사용자·수준·범위·제외·위험 |
| 사용 안내 | 준비·실행·대표 입력·종료·문제 해결 |
| 검증 기록 | 버전·환경·핵심 흐름·실패·재실행 결과 |
| 다음 계획 | 제한·피드백·남은 개선·유지할 결정 |

개인용은 본인의 새 세션 재실행을 기본으로 하고 동료는 안내가 이해되는지 확인합니다. 타인용 MVP는 대상 사용자의 실행·피드백이 필요합니다. PoC의 실험 종료와 실제 제품의 완성을 혼동하지 않습니다.

## 완료 판정과 회고

- [ ] 합의한 핵심 흐름과 필요한 결과 유지가 동작합니다.
- [ ] 대표 실패를 처리하고 실제 위험에 필요한 확인을 했습니다.
- [ ] 검증한 버전과 제출 버전이 같습니다.
- [ ] 사용법·제한·필요한 설정을 다른 세션에서 따라갈 수 있습니다.
- [ ] 필수 미확인·실패가 없거나 미완료임을 정확히 기록했습니다.
- [ ] 피드백과 다음 업데이트를 구분해 남겼습니다.

```text
작업 인계 스킬로 최종 상태를 정리해 주세요. 사용 범위·완료 단계, 제출 버전, 실제 검증 증거, 유지할 ADR·시안, 이미 통과한 검토, 남은 필수·선택 개선, 다음 행동과 예산을 남겨 주세요. 계획을 완료 사실로 바꾸지 마세요.
```

‘어떤 모델이 최고였는가’보다 ‘어떤 입력·도구·완료 기준이 결과를 바꿨는가’를 회고합니다. 비용과 속도는 같은 범위·품질 조건에서 비교합니다. 빠르게 초안을 만든 시간과 실제 전달까지 걸린 시간을 나누어 보세요.

<details><summary>강사 메모 · 미완료와 다음 운영</summary>
필수 조건이 남으면 미완료로 기록하고 복구 가능한 다음 작업을 정합니다. 전원 완성을 시간표만으로 보장하지 않습니다. 자동 디버그 운영을 확장할 때는 이슈별 상태·기준 버전·소유권·예산·반려·사용자 ADR 판단 경로를 먼저 정의합니다. 수업 중 스케줄러 구축을 졸업 필수로 추가하지 않습니다.
</details>

## 다른 프로젝트에 적용하기

게임은 실제 모델을 사용한 한 경기와 리플레이를, 매거진은 출처 있는 한 호와 정정 경로를 전달합니다. 핵심이 미구현이면 범위를 줄였다고 숨기지 않고 현재 완료 수준을 기록합니다. [사례별 완료 증거](cases/index.md)를 확인하세요. 기존120분의 사례·실습 시간을 대체하며 추가 과제로 세 프로젝트를 모두 요구하지 않습니다.


다음 업데이트를 정할 때 [고도화·부분 교체·새 구현 판단 실습](evolve-or-rebuild.md)을 사용합니다. 기존 회고·다음 계획 시간 중 10분을 대체하여 유지할 자산, 바꿀 경계, 미래 비용과 재판단 조건을 한 문단 ADR로 남깁니다.

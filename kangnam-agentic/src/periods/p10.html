요청 한 번의 구조: system · tools · messages

{{svg:p10-msg-request}}
요청 하나(POST /v1/messages) = system + tools + messages
{ "model": "…", "system": "너는 이 저장소의 코딩 도우미다. …", "tools": [{"name": "run_tests", "description": "테스트를 실행하고 결과를 돌려준다", "input_schema": {"type": "object", …}}], "messages": [{"role": "user", "content": "tests가 왜 실패하는지 봐 줘"}] }

JSON(JavaScript Object Notation, 자바스크립트 객체 표기법) 블록 하나가 요청 하나. 강조한 system·tools는 하네스가 몰래 채우는 부분입니다.

요청 한 번이 어떻게 생겼는지 봅니다. 바깥 상자가 요청 하나이고, 안에는 시스템 프롬프트인 system, 도구 정의를 담은 tools, 대화 기록인 messages가 들어갑니다. system에는 하네스가 쓰는 규칙과 지침 파일 내용이 들어가고, tools에는 도구 이름과 설명과 입력 형식이 들어가며, MCP로 붙인 도구 정의도 여기 실립니다. messages에는 사용자 프롬프트와 모델의 이전 답이 역할 표시와 함께 쌓입니다. 강조한 system과 tools는 사용자가 직접 쓰지 않고 하네스가 채우는 부분입니다.
개념 · 단순화한 예모델 응답 · 실행은 하네스가

모델은 도구를 실행하지 않는다: tool_use는 ‘부탁’

"role": "assistant", "content": [ {"type": "text", "text": "테스트부터 돌려 보겠습니다."}, {"type": "tool_use", "id": "toolu_01", "name": "run_tests", "input": {"path": "tests/"}}], "stop_reason": "tool_use"

모델은 “이 도구를 이 입력으로 불러 달라”고 적을 뿐. 파일 읽기·명령 실행은 하네스가 내 컴퓨터에서 합니다. → 3교시 권한·승인

모델의 답을 보면 텍스트와 함께 tool_use라는 블록이 있습니다. 이것은 모델이 도구를 실행했다는 뜻이 아니라, 이 도구를 이 입력으로 불러 달라는 부탁을 적어 둔 것입니다. 모델은 글만 쓰고, 실제로 테스트를 돌리는 것은 내 컴퓨터의 하네스입니다. 그래서 무엇을 허락할지 정하는 권한과 승인, 이를 가두는 샌드박스는 하네스의 몫이 됩니다. 참고로 OpenAI의 Chat Completions는 같은 역할을 system 역할 메시지와 tool_calls, tool 역할 메시지로 부릅니다. 이름만 다르고 구조는 같습니다.
개념 · 단순화한 예tool_use → 실행 → tool_result

도구 호출 한 바퀴: tool_use → 실행 → tool_result

{{svg:p10-msg-toolloop}}

③~⑤가 돌고 도는 고리. 도구 호출 없이 답이 끝나면(stop_reason end_turn) 루프가 멈춥니다. → 3교시 에이전트 루프

이제 한 바퀴를 이어서 봅니다. 사용자가 프롬프트를 주면 하네스가 system과 tools와 messages를 갖춰 모델 서버에 요청합니다. 모델이 tool_use를 돌려주면 하네스는 권한을 확인한 뒤 도구를 실행하고, 결과를 같은 번호의 tool_result로 messages 끝에 붙여 다시 요청합니다. 이 ③에서 ⑤까지가 돌고 도는 고리이고, 모델이 도구 없이 답을 마치면 루프가 멈춥니다. 3교시에서 본 에이전트 루프, 즉 맥락 수집에서 행동, 결과 확인의 반복이 바로 이 JSON(JavaScript Object Notation, 자바스크립트 객체 표기법) 왕복입니다.
개념한 턴에 k토큰씩, 요청은 선형 증가

대화가 길어질수록 요청 하나가 커진다

예시 값으로 그린 막대 · S = 고정 앞부분, k = 한 턴에 느는 기록

n번째 요청 = 고정 앞부분 S + n·k. 요청 하나는 선형으로 커진다.

앞에서 본 대로 매 요청마다 대화 전체를 보냅니다. 한 턴에 사용자 말과 모델 답, 도구 결과가 평균 k토큰씩 기록에 쌓인다고 해 봅니다. 그러면 n번째 요청은 고정 앞부분 S에 n배의 k를 더한 크기가 됩니다. 요청 하나만 보면 턴 수에 비례하는 직선이라 아직 감이 안 옵니다. 문제는 요청 하나가 아니라 지금까지 보낸 합계인데, 다음 장에서 그래프로 봅니다.
개념S=10,000 · k=3,000 · 0~100턴 계산

누적 토큰은 제곱으로 불어난다

예시 값(S=10,000·k=3,000)으로 계산한 그래프 · ③은 요청이 150K를 넘으면 20K 요약으로 압축

누적 ≈ n·S + k·n(n+1)/2. 턴 2배 → 누적 약 4배, 10배 → 약 100배.

합계를 계산하면 모양이 달라집니다. n번째까지 보낸 입력 토큰의 합은 고정 앞부분 곱하기 n에, k 곱하기 n 곱하기 n 더하기 1 나누기 2를 더한 값입니다. 턴 수가 두 배가 되면 누적은 약 네 배, 열 배가 되면 약 백 배로 불어납니다. 지수 함수는 아니지만 제곱만으로도 체감은 폭증입니다. 도구 결과가 큰 에이전트 작업은 k가 커서 곡선이 더 가파릅니다. 그래프의 직선은 압축했을 때, 아래 곡선은 다음에 볼 캐싱의 비용 환산입니다.

5분 수명이면 두 번째 요청부터 이득(1.25+0.1=1.35 < 2). 앞부분 재계산이 없어 첫 토큰도 빨라진다.

요금을 봅니다. 캐시에 쓰는 토큰은 기본 입력 단가의 1.25배이고, 읽는 토큰은 약 10분의 1입니다. 두 번만 써도 이득인데, 1.25에 0.1을 더하면 1.35로 두 번 다 새로 보내는 2보다 작기 때문입니다. 수명은 기본 5분이고 1시간짜리도 있으며, 읽을 때마다 타이머가 다시 시작합니다. 앞부분을 다시 계산하지 않으니 첫 토큰이 나오는 시간도 줄어든다고 문서는 설명합니다. 너무 짧은 앞부분은 조용히 캐시되지 않으니, 응답의 사용량 표시로 썼는지 읽었는지를 확인합니다.

왜 CLI인가: 다섯 가지 이유

{{svg:p10-why-cli}}

MCP는 연결만 해도 도구 정의 전체가 tools에 실린다(앞의 ‘요청 구조’ 장). CLI는 쓸 때만 읽는다. MCP는 도구 정의가 바뀔 때마다 캐시가 깨진다.

다섯 가지를 봅니다. 첫째 토큰입니다. MCP는 연결만 해도 도구 정의 전체가 매 요청의 tools 상자에 실리지만, CLI는 필요할 때 도움말만 읽습니다. 둘째 조합입니다. 파이프와 grep, jq로 출력을 줄여 필요한 줄만 결과로 돌려줍니다. 셋째 모델이 이미 압니다. gh나 git 같은 널리 쓰이는 CLI는 학습 데이터에 많아 별도 설명 없이 씁니다. 넷째 사람과 같은 도구라 같은 명령으로 재현하고 디버깅합니다. 다섯째 인증과 권한을 기존 CLI 로그인과 셸 권한 규칙으로 관리합니다.

.gitignore를 따르고 숨김·바이너리를 건너뛰어, node_modules 같은 외부 라이브러리 파일이 검색 결과에 섞이지 않는다.
Claude Code는 내장 ripgrep을 쓰지만, 시스템에서 안 돌면 별도 ripgrep이 필요하다.
검색 결과가 짧을수록 컨텍스트 윈도우에 들어가는 양도 준다. 가장 기본적인 토큰 절약.
$ rg "TODO" src/
ripgrep, rg는 정규식으로 디렉터리를 재귀 검색하는 도구입니다. README에 따르면 기본으로 gitignore 규칙을 따르고 숨김 파일과 바이너리 파일은 건너뜁니다. 에이전트에게 중요한 이유는 의미 없는 결과, 즉 node_modules나 빌드 산출물이 섞여 들어와 컨텍스트 윈도우를 낭비하는 것을 자연스럽게 막기 때문입니다. Claude Code 공식 문서는 검색과 파일 탐색에 내장 ripgrep을 쓰고, 이 바이너리가 시스템에서 안 돌면 시스템용 ripgrep을 따로 쓰라고 안내합니다. 설치는 각자 하시면 됩니다. 다른 도구가 grep을 rg로 바꿨는지는 1차 출처를 찾지 못해 말하지 않겠습니다. 묶어 보면 장점은 볼 필요 없는 파일을 걸러 컨텍스트 윈도우를 아낀다는 것이고, 단점은 내장 바이너리가 안 돌면 별도 ripgrep이 필요하다는 것입니다. 의미는 검색 단계에서 이미 토큰 절약이 시작된다는 점입니다.

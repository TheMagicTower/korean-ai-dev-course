서브에이전트는 메인 에이전트가 일을 맡기는 별도의 에이전트입니다. 공식 문서 첫머리가 이것을 정확히 말합니다. 검색 결과, 로그, 파일 내용처럼 다시 볼 일 없는 것들이 메인 대화를 채울 때 쓰라는 것입니다. 서브에이전트는 자기 컨텍스트 창과 시스템 프롬프트, 도구 접근, 독립된 권한을 가집니다. Claude Code는 2025년 7월 24일 배포된 1.0.60에서 사용자가 직접 서브에이전트를 만드는 기능을 넣었습니다. 변경 기록에는 한 줄만 있습니다. 장점은 탐색 결과가 메인 창을 채우지 않는다는 것입니다. 단점은 대화 이력을 보지 못하고, 서브에이전트도 자기 요청을 보내기 때문에 사용량이 메인 대화와 같은 한도에서 차감된다는 것입니다. 의미는 압축과 달리 애초에 맥락이 쌓이지 않게 하는 장치라는 점입니다.

서브에이전트는 대화 이력을 보지 못합니다. 메인이 작업 내용을 요약해 건네고, 서브에이전트는 거기서 시작합니다.

그림에서 위의 메인 창에는 목표와 계획, 판단만 쌓입니다. 파일 수십 개를 읽고, 긴 로그를 보고, 검색 결과 수백 줄을 훑는 일은 아래의 서브에이전트 창에서 합니다. 일이 끝나면 요약만 메인으로 돌아옵니다. 압축은 이미 쌓인 맥락을 줄이는 방식이고, 서브에이전트는 애초에 쌓이지 않게 하는 방식입니다. 대가도 있습니다. 공식 문서에 따르면 서브에이전트는 새 창으로 시작해서 지금까지의 대화 이력, 이미 읽은 파일을 보지 못합니다. 메인이 작성한 위임 메시지가 전부이므로, 맡길 때 무엇을 알려 줄지가 중요합니다.

결제 장애를 조사하는 장면을 지어낸 예로 보겠습니다. 왼쪽처럼 메인 에이전트 혼자 조사하면 긴 로그와 파일 수십 개, 테스트 출력이 모두 한 창에 쌓입니다. 창이 차서 압축이 일어나면 정작 처음에 찾은 단서인 오류 코드가 요약에서 빠질 수 있고, 그러면 같은 파일을 다시 읽는 일이 생깁니다. 오른쪽은 같은 조사를 셋으로 나눈 경우입니다. 각 서브에이전트는 자기 창에서 읽고, 돌려주는 것은 한두 줄의 결론입니다. 메인은 세 결론을 나란히 놓고 배포 시각과 오류 급증 시각이 맞는다는 것을 바로 알아챕니다. 숫자와 파일 이름은 설명을 위해 만든 것입니다.

서브에이전트 정의: 마크다운 파일 하나

  1. name · description(이름·설명)만 필수. description이 위임 기준
  2. tools로 쓸 수 있는 도구를 제한
  3. model로 가벼운 모델을 지정
  4. 본문 전체가 시스템 프롬프트(기본 지시문)

When invoked, analyze the code and provide specific, actionable feedback on quality, security, and best practices. ✓ 읽기 도구만 → 코드를 고치지 못한다 ✓ sonnet → 리뷰는 가벼운 모델로
서브에이전트 정의는 .claude/agents 폴더의 마크다운 파일입니다. 위쪽 프런트매터에 이름과 설명, 도구, 모델을 적고, 아래 본문이 곧 그 에이전트의 시스템 프롬프트가 됩니다. 이 예시는 공식 문서의 빠른 시작에 나오는 코드 리뷰어를 그대로 가져온 것입니다. 필수는 name과 description 두 가지뿐입니다. 도구를 Read, Glob, Grep으로 제한했기 때문에 이 에이전트는 코드를 읽고 의견만 낼 수 있고 고칠 수는 없습니다. 6교시에서 말한 테스트 파일 보호와 같은 방향의 장치입니다. 서브에이전트는 Claude Code의 전체 시스템 프롬프트가 아니라 이 본문과 기본 환경 정보만 받습니다.

공식 문서서브에이전트를 부르는 네 가지 방법

서브에이전트 호출: 자동 위임·말로 지정·@-멘션·--agent

$ claude > use the test-runner subagent to fix failing tests # 말로 지정 > @"code-reviewer (agent)" look at the auth changes # @로 에이전트 지정 > # 아무 말 없어도 description이 맞으면 Claude가 알아서 위임 $ claude --agent code-reviewer # 세션 전체를 그 에이전트로 실행 ✓ description에 “use proactively”를 넣으면 더 적극적으로 위임 ! 좋은 description = 언제 맡길지에 대한 한 줄 기준

서브에이전트가 일하는 동안 메인은 다른 일을 할 수 있습니다(백그라운드). → 8교시

정의한 에이전트를 부르는 방법은 네 가지입니다. 가장 흔한 것은 자동 위임입니다. 요청 내용과 각 에이전트의 description이 맞으면 Claude가 스스로 맡깁니다. 그래서 description을 정성껏 써야 합니다. 말로 지정할 수도 있고, @-멘션으로 특정 에이전트를 고를 수도 있습니다. --agent 옵션은 세션 전체를 그 에이전트로 돌립니다. 위 명령은 모두 공식 문서의 예시입니다. 어떤 에이전트가 있는지는 .claude/agents 폴더를 열어 보면 되고, 예전에 있던 /agents 마법사는 최근 버전에서 안내 문구로 바뀌었다고 문서에 적혀 있습니다.
공식 문서서브에이전트 병렬 호출

독립된 조사는 병렬로

{{svg:p07-parallel-sub}}

공식 예시: “Research the authentication, database, and API modules in parallel using separate subagents”(인증·DB(Database, 데이터베이스)·API(Application Programming Interface, 응용 프로그램 인터페이스) 모듈을 서브에이전트 따로 병렬로 조사해 줘). 조사 경로가 서로 독립일 때 잘 맞습니다.

서브에이전트는 병렬로도 돌릴 수 있습니다. 인증, 데이터베이스, API(Application Programming Interface, 응용 프로그램 인터페이스) 모듈을 각각 다른 서브에이전트에게 조사시키고, 세 개의 요약만 받는 식입니다. 메인 창에는 세 요약만 남으니 맥락이 깨끗합니다. 공식 문서는 이 방식이 조사 경로가 서로 의존하지 않을 때 가장 잘 맞는다고 덧붙입니다. 반대로 상세한 결과를 돌려주는 서브에이전트가 너무 많으면 그 결과가 메인 창을 다시 채울 수 있다고 경고합니다. 동시 실행 수에도 기본 상한이 있습니다.

해법은 작업마다 폴더와 브랜치(코드 갈래)를 따로 주는 것입니다. 로그인·검색 같은 작업을 동시에 시킬 때 필요합니다.

서브에이전트로 맥락은 나눴지만 아직 한 폴더를 같이 씁니다. 큰 프로젝트에서는 로그인 기능과 검색 기능처럼 서로 다른 작업을 동시에 시키고 싶어집니다. 같은 폴더에서 에이전트 두 개가 파일을 고치면 한쪽의 수정이 다른 쪽에 의해 덮어써지거나, 테스트가 반쯤 고친 상태의 코드 위에서 돌아갑니다. 사람 개발자도 한 폴더에서 브랜치를 바꿔 가며 일하면 같은 일을 겪습니다. git이 오래전부터 제공하던 해법이 워크트리입니다. 에이전트가 늘어나자 이 오래된 기능이 다시 주목받았습니다.

git worktree: 한 저장소에 브랜치별 작업 폴더

git-scm.com/docs/git-worktree
git 공식 문서 화면 캡처
git 공식 문서의 git-worktree 설명. 한 저장소에 작업 폴더를 여럿 붙여 브랜치 여러 개를 한 번에 체크아웃(펼치기)할 수 있다.
$ git worktree add ../app-login -b feat/login $ git worktree add ../app-search -b feat/search $ git worktree list /home/me/app a1b2c3d [main] /home/me/app-login a1b2c3d [feat/login] /home/me/app-search a1b2c3d [feat/search] $ git worktree remove ../app-login ✓ “check out more than one branch at a time” = 브랜치 여럿을 한 번에 펼친다 ! 같은 브랜치는 두 곳에 못 연다(기본값)
git이 오래전부터 제공한 기능. 브랜치마다 폴더가 생기고 기록은 공유해, 합치기도 일반 머지다.
같은 브랜치는 두 곳에 못 연다. 새 체크아웃이라 의존성 설치 등 환경 준비가 따로 필요하다. 서브모듈은 실험적.
에이전트 병렬화의 해법은 새 발명이 아니라 오래된 git 기능. Claude Code·Codex가 이를 제품에 넣었다.
워크트리는 새 기능이 아닙니다. git 공식 문서의 설명처럼 한 저장소에 작업 트리를 여럿 붙여서 한 번에 브랜치 여러 개를 체크아웃해 둘 수 있습니다. git worktree add가 새 폴더와 브랜치를 만들고, list로 목록을 보고, 끝나면 remove로 지웁니다. 터미널 예시는 문서의 문법을 따라 쓴 것이고 경로와 해시는 설명용입니다. 같은 브랜치를 이미 다른 워크트리가 쓰고 있으면 add가 거절됩니다. 두 곳에서 같은 브랜치를 건드리지 못하게 하는 안전장치입니다. 문서는 서브모듈이 있는 저장소의 다중 체크아웃은 아직 실험적이라고 경고합니다. 정리하면 장점은 오래 검증된 git 기능이라는 것, 단점은 환경 준비가 따로 필요하다는 것, 의미는 에이전트 병렬화의 해법이 새 발명이 아니라는 것입니다.

커밋과 브랜치는 모든 워크트리에 즉시 보입니다. 파일, HEAD(현재 커밋 표시), 인덱스(커밋 대기 목록)는 워크트리마다 따로입니다.

워크트리는 새로 clone하는 것과 다릅니다. clone은 저장소 전체를 복사하지만 워크트리는 .git 안의 기록을 공유합니다. 한 워크트리에서 만든 커밋이 다른 워크트리에서도 바로 보이는 이유입니다. 반대로 작업 파일, 현재 가리키는 HEAD, 인덱스는 워크트리마다 따로 있습니다. 그래서 에이전트 A가 파일을 고쳐도 에이전트 B의 폴더에는 영향이 없습니다. 이 공유 덕에 나중에 합치는 일도 같은 저장소 안에서 일반적인 머지로 처리됩니다. 새로 만든 워크트리는 새 체크아웃이라 의존성 설치 같은 환경 준비가 따로 필요합니다.

둘의 결합: 서브에이전트마다 자기 워크트리

프런트매터(파일 맨 위 설정) 한 줄 isolation: worktree
서브에이전트마다 임시 워크트리라 파일을 고쳐도 내 폴더는 그대로. 변경이 없으면 끝날 때 자동 삭제.
기본은 default 브랜치에서 분기. 작업 중인 브랜치 상태가 필요하면 worktree.baseRef 설정이 필요하다.
맥락 분리와 파일 분리를 한 줄로 결합. 13교시 코디네이터-배치의 기반.
# .claude/agents/refactorer.md --- name: refactorer description: Applies mechanical refactors across many files isolation: worktree --- Apply the requested refactor across every affected file, then run the tests and report the results. # refactorer = 여러 파일을 기계적으로 고치는 에이전트 ✓ 파일을 고쳐도 내 작업 폴더는 그대로 ! 기본은 default 브랜치에서 분기(worktree.baseRef)
서브에이전트와 워크트리를 겹쳐 쓰는 방법이 isolation 필드입니다. 변경 기록에 따르면 같은 2.1.49 버전에서 서브에이전트가 임시 워크트리에서 일하는 기능도 함께 들어왔습니다. 위의 정의 파일은 공식 문서의 예시입니다. 이 서브에이전트는 호출될 때마다 자기만의 워크트리에서 작업합니다. 변경이 없으면 끝날 때 자동으로 지워지고, 변경이 있으면 남습니다. 기본적으로 저장소의 기본 브랜치에서 분기하므로, 내가 작업 중인 브랜치 상태가 필요하면 설정으로 바꿔야 합니다. 장점은 호출마다 파일이 격리된다는 것, 단점은 기본 분기 기준이 default 브랜치라는 것, 의미는 맥락 분리와 파일 분리가 한 줄로 결합된다는 것입니다. 같은 구조가 13교시 코디네이터-배치 패턴의 기반이 됩니다.
강사 운영 방식병렬 작업의 비용은 합칠 때

격리의 한계: 충돌은 합칠 때로 미뤄짐

{{svg:p07-merge-conflict}}

워크트리는 작업 중의 덮어쓰기를 막을 뿐, 합칠 때의 충돌은 막지 못합니다. 변경 범위를 미리 나누는 것이 가장 싼 해법입니다.

워크트리가 충돌을 없애 주는 것은 아닙니다. 두 워크트리가 같은 파일의 같은 줄을 고쳤다면 먼저 합친 쪽은 문제없이 들어가고, 나중에 합치는 쪽에서 충돌이 납니다. 이때는 사람이 두 의도를 보고 판단해야 합니다. 제가 운영하는 기준은 워크트리마다 변경 범위와 담당 이슈를 미리 정하고, 겹치는 파일이나 공유 데이터를 바꾸는 작업은 순서를 조율하는 것입니다. 각 작업의 성공과 합친 뒤의 성공은 다르다는 점도 짚어 둡니다. 합친 뒤에도 테스트를 다시 돌려야 합니다. 이 비용을 줄이는 머지 큐는 15교시에서 다룹니다.
사례합칠 때 충돌 · 실제 실행(git 2.54 · Node 22)

비밀번호 검사 한 줄을 각자 고친 두 워크트리

① 나눠서 작업하고 차례로 합치기
$ git worktree add ../app-len -b feat/min-length Preparing worktree (new branch 'feat/min-length') $ git worktree add ../app-special -b feat/special-char Preparing worktree (new branch 'feat/special-char') # A: 8자 → 12자 · B: 특수문자 필수 (같은 줄) $ git merge feat/min-length Fast-forward $ git merge feat/special-char CONFLICT (content): Merge conflict in auth.js
② 두 의도를 보고 풀고, 테스트로 확인
<<<<<<< HEAD if (pw.length < 12) return '12자 이상'; ======= if (!/[^A-Za-z0-9]/.test(pw)) return '특수문자 포함'; >>>>>>> feat/special-char # 둘 다 요구사항 → 두 줄 모두 남긴다 $ node --test --test-reporter=spec ✔ 12자 미만 거절 ✔ 특수문자 없으면 거절 ✔ 둘 다 지키면 통과 ℹ pass 3 ℹ fail 0

git은 어느 쪽이 맞는지 모릅니다. 고르는 일(하나만? 둘 다?)은 사람 몫이고, 합친 뒤 테스트를 다시 돌립니다.

임시 저장소에서 실제로 실행한 출력입니다. 로그인 기능의 비밀번호 검사 함수를 두고, 한 워크트리에서는 최소 길이를 12자로 늘리고 다른 워크트리에서는 특수문자를 필수로 바꿨습니다. 둘 다 원래 있던 같은 한 줄을 고쳤습니다. 먼저 합친 쪽은 아무 문제 없이 들어가고, 나중에 합친 쪽에서 충돌이 났습니다. 충돌 표시를 보면 git은 두 버전을 나란히 보여 줄 뿐 어느 쪽이 맞는지는 정하지 않습니다. 여기서는 두 요구가 모두 필요하다고 판단해 두 줄을 다 남겼고, 그 판단이 맞는지는 세 가지 경우를 검사하는 테스트로 확인했습니다. 에이전트에게 충돌을 풀게 할 때도 두 브랜치의 의도를 알려 주고, 푼 뒤 테스트 결과를 보여 달라고 하면 됩니다. 출력에서 소요 시간과 일부 줄은 지면 때문에 뺐습니다.

OpenAI 쪽 공식 액션은 openai/codex-action의 v1입니다. 이 액션은 러너에 Codex CLI를 설치하고, 비밀값으로 API 키를 받으면 프록시를 띄운 뒤 codex exec를 실행합니다. 할 일은 prompt에 직접 적거나 저장소에 둔 프롬프트 파일을 prompt-file로 가리키며, 둘을 함께 쓰면 오류가 납니다. 권한을 줄이는 장치는 두 겹입니다. sandbox는 Codex 안에서 파일과 네트워크 접근을 제한하고, safety-strategy는 Codex를 실행하기 전에 러너의 sudo 권한을 없애 메모리에 있는 비밀값을 지킵니다. 문서는 read-only 샌드박스만으로 비밀값을 지킬 수 있다고 믿지 말라고 따로 경고합니다. 결과는 final-message 출력으로 나오므로, 다음 단계가 이 값을 받아 PR 댓글로 올리는 식으로 이어 붙입니다.
공식 문서 예시 · 2026-11-09 확인.github/workflows/*.yml · 지면에 맞게 줄임

워크플로우 예: 댓글 멘션과 PR 리뷰

① Claude · @claude 댓글에 응답(대화형)
on: issue_comment: types: [created] jobs: claude: if: contains(github.event.comment.body, '@claude') runs-on: ubuntu-latest permissions: contents: write pull-requests: write issues: write id-token: write steps: - uses: actions/checkout@v6 - uses: anthropics/claude-code-action@v1 with: anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
② Codex · PR이 열리면 리뷰(자동화)
on: pull_request: types: [opened, synchronize, reopened] jobs: codex: runs-on: ubuntu-latest permissions: contents: read steps: - uses: actions/checkout@v5 with: persist-credentials: false - id: run_codex uses: openai/codex-action@v1 with: openai-api-key: ${{ secrets.OPENAI_API_KEY }} prompt-file: .github/codex/prompts/review.md # 다음 job이 final-message를 받아 PR 댓글로 게시

비밀값은 ${{ secrets.… }} 참조만. Claude 쪽은 쓰기 권한, Codex 쪽 실행 job은 읽기 권한만.

두 공식 문서의 예시를 화면에 맞게 줄였습니다. 왼쪽은 댓글에 @claude가 들어 있을 때만 job을 띄우는 대화형 예시이고, Claude가 코드를 고치고 PR을 만들 수 있도록 contents, pull-requests, issues에 쓰기 권한을 줍니다. id-token 쓰기 권한은 액션이 기본으로 쓰는 GitHub 앱 인증에 필요합니다. 오른쪽은 PR이 열리거나 갱신될 때마다 저장소의 프롬프트 파일로 리뷰를 돌리는 예시입니다. 원문은 job을 둘로 나눠서, Codex를 돌리는 job에는 읽기 권한만 주고 댓글을 다는 job에만 쓰기 권한을 줍니다. 권한을 이렇게 나누는 방식은 여러분 워크플로우에도 그대로 가져다 쓸 수 있습니다. 두 예시 모두 키는 저장소 Secrets에 넣고 이름으로만 참조합니다.

하네스 v0:
에이전트에게 설계부터 시킨다

4교시는 실습입니다. 도구 설치는 각자 알아서 해 두신 것으로 하고, 오늘은 설치 없이 진행합니다. 이미 각자 쓰는 에이전트가 있으니 그것을 그대로 씁니다. 오늘은 5회차까지 키워 갈 ‘나만의 하네스’의 첫 버전을 만듭니다. 소개하고 싶은 것은 만드는 방법입니다. 하네스도 에이전트에게 시켜서 만듭니다. 다만 바로 코드를 짜게 하지 않고, 무엇을 만들지 에이전트가 먼저 묻게 합니다. 이 과정에서 소개하는 일하는 방식을 하네스를 만드는 데에도 그대로 씁니다.
약 55분18단계 운영 기준의 1–7단계를 개인 PoC 크기로 · 각자 쓰던 에이전트 그대로

하네스도 에이전틱 엔지니어링 프로세스로 만든다: 분석 → 개요·ADR → 승인 → 구현

{{svg:p04-design-flow}}

여러분이 할 일은 코드를 치는 것이 아니라 질문에 답하고, 설계를 승인하고, 결과를 시험하는 것입니다.

오늘 실습은 이 과정에서 소개하는 프로세스를 그대로 따라 해 봅니다. 제 운영 기준 18단계 가운데 앞의 1~7단계, 즉 프로젝트 분석, 시나리오, 입출력, 개요, 가이드라인, ADR을 개인 PoC 크기로 줄여서 하네스에 적용합니다. 먼저 에이전트가 분석에 필요한 질문을 하고 여러분이 답합니다. 에이전트는 답을 개요 문서와 첫 ADR로 정리합니다. 여러분이 그 문서를 읽고 승인한 뒤에야 에이전트가 구현합니다. 만들어진 v0을 작은 과제로 한 번 돌려 보고, 금지한 일을 일부러 시켜서 정말 막히는지 확인합니다. 마지막으로 막힌 것까지 기록합니다. 설계 대화 15분, 설계 검토와 승인 10분, 구현 15분, 실행과 기록 15분 정도로 잡습니다.
과정 전체의 실습 지도강사 운영 기준 18단계 · 저위험 개인 도구는 1–8단계를 짧은 개요로 합친다

네 번의 실습은 하나의 에이전틱 엔지니어링 프로세스를 따라간다

{{svg:p04-process-map}}

하네스를 만드는 일 자체가 이 과정의 프로세스를 연습하는 과제입니다. 회차마다 다음 단계로 넘어갑니다.

네 번의 실습이 따로 노는 것이 아닙니다. 제가 실제 프로젝트에 쓰는 18단계 운영 기준을 하네스라는 작은 개인 프로젝트에 맞게 줄인 것입니다. 오늘은 1~7단계로 분석하고 개요와 ADR을 씁니다. 다음 주에는 스펙을 Task와 이슈로 나누고, 이슈 하나를 스펙, 계획, 구현, 리뷰 순서로 처리합니다. 3회차에는 워크트리와 워크플로를 정하고 스킬과 MCP, /goal로 이슈를 끝까지 맡깁니다. 4회차에는 PR, CI, 스모크, 피드백, 다음 루프까지 갑니다. 저위험 개인 도구에서는 1~8단계를 짧은 개요 하나로 합쳐도 된다는 것이 제 기준입니다.
왜 질문부터인가1교시 DDD·PoC 명시, 11교시 grill-me로 이어짐

“하네스 만들어 줘”라고만 하면, 에이전트가 빈칸을 가정으로 채운다

바로 시키면

가정이 설계가 된다

  • 모델·언어·도구를 에이전트가 마음대로 고른다
  • 멈춤 조건·권한이 빠지거나 대충 들어간다
  • PoC로 충분한데 계층과 설정이 잔뜩 붙는다
  • 왜 그렇게 만들었는지 내가 설명하지 못한다
질문부터 시키면

결정이 내 것이 된다

  • 목적·범위·수준을 먼저 정한다
  • 멈춤 조건과 금지 목록이 설계에 들어간다
  • 결정과 이유가 개요·ADR에 남는다
  • 5회차 발표에서 구조를 내 말로 설명할 수 있다
에이전트에게 하네스를 만들어 달라고만 하면 대개 바로 코드를 씁니다. 그 순간 비어 있던 결정들, 어떤 모델을 쓸지, 어떤 도구를 줄지, 언제 멈출지, 무엇을 금지할지가 전부 에이전트의 가정으로 채워집니다. 결과물은 그럴듯하지만 왜 그렇게 생겼는지 여러분이 설명하지 못합니다. 반대로 질문부터 시키면 같은 결정을 여러분이 내리게 됩니다. 1교시에서 PoC라고 명시한다고 말씀드린 것, 11교시에서 볼 grill-me 스킬이 바로 이 생각입니다.
분석 대화 체크리스트4단계(마켓 인사이트)는 개인 도구라 생략 · 에이전트가 묻지 않으면 내가 먼저

분석 대화는 1–7단계의 질문을 하나씩 묻고 끝난다

단계에이전트가 물을 것예시 답빠지면
1 분석누가 어떤 일에 쓰나나, 메모 앱의 작은 수정범위가 끝없이 넓어진다
2 시나리오정상·실패 예 하나씩정렬 옵션 추가 / 테스트 실패 시 중단무엇이 성공인지 모른다
3 입출력입력과 기대 출력, 성공 판정과제 문장 → 변경 + pytest 통과“된 것 같다”로 끝난다
5 개요수준과 범위, 제외할 것PoC, 파일 3개, UI 없음과잉 설계
6 가이드라인트랙·모델·도구·비용코드형, 읽기·수정·실행, 하루 예산비용 폭주, 할 수 없는 일 시도
7 ADR권한·멈춤 같은 되돌리기 비싼 결정금지 3개, 완료+20바퀴+예산3교시의 사고 사례
분석 대화가 잘 됐는지 보는 기준입니다. 18단계 중 1~7단계의 질문을 하네스 크기로 줄였고, 4단계 시장 분석은 개인 도구라 뺐습니다. 이 여섯 줄이 다 정해졌으면 충분합니다. 에이전트가 이 중 일부를 묻지 않으면 제가 먼저 꺼냅니다. 특히 7단계의 권한과 멈춤 조건은 3교시에서 본 사고 사례와 승인 피로로 바로 이어집니다. 트랙은 둘 중 하나를 고릅니다. 코드형은 모델 API를 직접 부르는 작은 루프를 에이전트가 짜 주는 것이고, 설정형은 지금 쓰는 Claude Code나 Codex 위에 규칙과 지침 파일을 얹는 것입니다. 모르는 항목은 에이전트에게 선택지 두 개와 장단점을 달라고 하면 됩니다.
그대로 붙여 넣어도 됩니다각자 쓰는 에이전트(Claude Code · Codex · Gemini CLI · Cursor …)

첫 프롬프트: 코드 전에 질문을 하나씩 하라고 못 박는다

> 내 프로젝트(메모 앱, PoC)에 쓸 작은 코딩 에이전트 하네스를 만들고 싶다. 아직 코드는 쓰지 마. 분석·시나리오·입출력·개요·가이드라인·ADR 순서로 필요한 질문을 한 번에 하나씩 해 줘. 질문마다 네 추천 답과 이유를 같이 주고, 10개 안에서 끝내. 끝나면 docs/overview.md와 docs/adr/0001-harness-shape.md로 정리하고 내가 “승인”이라고 할 때까지 기다려.

grill-me 스킬. 계획을 세우기 전에 에이전트가 사용자에게 질문을 하나씩 집요하게 던지게 하는 스킬.
첫 프롬프트에서 세 가지를 못 박습니다. 아직 코드를 쓰지 말 것, 질문을 한 번에 하나씩 할 것, 그리고 정리한 설계를 내가 승인할 때까지 기다릴 것입니다. 질문마다 에이전트의 추천 답과 이유를 같이 달라고 하면, 모르는 부분도 선택하기 쉬워집니다. 질문 수에 상한을 두는 이유는 끝없는 질문도 시간을 잡아먹기 때문입니다. 오른쪽은 같은 생각을 스킬로 만든 예입니다. 매번 이 프롬프트를 쓰기 귀찮다면 11교시에서 자기 스킬로 만들어 보면 됩니다.
5단계 개요 · 7단계 ADR결정과 이유를 짧게 · 강사 ADR 서식(14교시)

분석 대화의 결과물은 짧은 개요 하나와 첫 ADR 하나다

# docs/overview.md (1–6단계 요약) 사용자·시나리오 나 · 메모 앱 작은 수정, 실패 시 중단 입출력·판정 과제 문장 → 변경 + pytest 통과 수준·범위 PoC · 파일 3개 · UI 없음 가이드라인 코드형 · 도구 read/edit/run · 하루 예산 아직 안 정한 것 스킬·MCP는 3회차에 # docs/adr/0001-harness-shape.md (7단계) 결정 금지 3개 + 멈춤 3중(완료·20바퀴·예산) 대안 전부 허용 / 매번 승인 이유 3교시 사고 사례, 승인 피로 다시 판단할 조건 금지 시험이 하나라도 뚫리면
  • 개요는 무엇을, ADR은 왜 그렇게 정했나
  • “아직 안 정한 것” 칸을 둔다. 다음 회차에 하네스가 자란다
  • 승인 전에 내가 읽고 고친다. 승인은 사람만 한다
→ 14교시: 이 방식이 ADR이 된다
분석 대화가 끝나면 에이전트가 이런 두 문서를 만들어 줍니다. 개요는 1~6단계에서 정한 것을 한 장에 모은 것이고, ADR은 7단계로 되돌리기 비싼 결정, 여기서는 권한과 멈춤 조건을 왜 그렇게 정했는지 남긴 것입니다. 길 필요가 없습니다. 아직 안 정한 것 칸을 일부러 둡니다. 이 과정에서 하네스는 회차마다 자라기 때문에, 이번에 정하지 않은 것을 적어 두면 다음 회차의 출발점이 됩니다. 그리고 승인은 사람만 합니다. 저는 에이전트가 쓴 설계를 그대로 승인하지 않고 한 번은 고쳐 봅니다. 이 짧은 결정 기록은 14교시의 ADR로 이어집니다.
승인 체크리스트다섯 가지가 다 ‘예’일 때만 “승인”

승인 전에 다섯 가지만 확인한다

  1. 수준이 PoC/MVP로 적혀 있고, 파일 수가 작다
  2. 멈춤 조건이 둘 이상이다(완료 + 최대 횟수)
  3. 금지 목록에 비밀값·대량 삭제·강제 푸시가 있다
  4. 비용 상한이 있다
  5. 구조를 내 말로 30초 안에 설명할 수 있다
사람이 보는 곳이 다섯 군데로 줄어, 설계를 빨리 검토할 수 있다.
체크리스트에 없는 위험(예: 외부 API 호출)은 놓칠 수 있다. 낯선 항목은 에이전트에게 위험을 따로 물어본다.
에이전트가 쓰고 사람이 판정하는 분업의 첫 연습. 2회차의 스펙·테스트 승인으로 이어진다.
설계 문서를 다 읽을 시간이 없어도 이 다섯 가지는 봅니다. 수준이 적혀 있는지, 멈춤 조건이 두 개 이상인지, 금지 목록에 비밀값 읽기와 대량 삭제와 강제 푸시가 있는지, 비용 상한이 있는지, 그리고 마지막으로 내가 이 구조를 30초 안에 설명할 수 있는지입니다. 저는 다섯 번째를 가장 중요하게 봅니다. 설명이 안 되면 승인하지 않고 에이전트에게 더 단순하게 바꿔 달라고 합니다. 이렇게 에이전트가 쓰고 사람이 판정하는 분업이 2회차의 스펙과 테스트 승인으로 이어집니다.
코드형 트랙에이전트가 만든 v0은 대략 이런 모양 · 직접 칠 필요 없음

코드형 v0을 검토할 때는 루프의 두 멈춤 조건부터 본다

# harness.py · 루프 부분 (에이전트가 쓴 코드의 예) MAX_STEPS = 20 # ① 최대 횟수 def main(task): messages = [{"role": "user", "content": task}] for step in range(MAX_STEPS): resp = client.messages.create( model=MODEL, max_tokens=2048, tools=TOOLS, system=open("AGENTS.md").read(), messages=messages) messages.append({"role": "assistant", "content": resp.content}) if resp.stop_reason != "tool_use": # ② 도구 호출 없음 = 완료 return report(resp) results = [] for b in resp.content: if b.type == "tool_use": out = IMPL[b.name](**b.input) # ③ 여기서 금지 목록 검사 log(step, b.name, b.input) # 기록 results.append({"type": "tool_result", "tool_use_id": b.id, "content": str(out)}) messages.append({"role": "user", "content": results}) print("최대 횟수 도달: 중단")
루프 전체가 한 화면에 보여, 3교시의 에이전트 루프가 실제로 어떻게 도는지 직접 확인할 수 있다.
API 키와 사용 비용이 필요하다. 권한 검사를 직접 넣지 않으면 아무것도 막지 않는다.
이후 회차의 장치(테스트 보호·MCP·스킬)를 코드로 하나씩 붙여 보며 원리를 본다.
코드형을 고른 분은 에이전트가 이런 코드를 만들어 줍니다. 직접 칠 필요는 없습니다. 대신 검토할 곳 세 군데를 봅니다. 첫째, 최대 횟수가 있는가. 둘째, 도구를 더 부르지 않으면 끝내는가. 셋째, 도구를 실행하기 전에 금지 목록을 검사하는가. 세 번째가 없으면 이 하네스는 아무것도 막지 않습니다. 코드형은 원리를 가장 깊게 볼 수 있지만 API 키와 비용이 필요하다는 점이 있습니다.
설정형 트랙쓰던 도구 위에 지침 파일 + 권한 규칙 · 2026-10-28 문서 확인

설정형 v0은 지침 파일 하나와 권한 규칙 몇 줄이다

# CLAUDE.md (Codex 등은 AGENTS.md) - 메모 앱 PoC. 테스트: pytest -q - 요청 범위 밖 파일은 고치지 않는다 - 테스트를 지우거나 skip 하지 않는다 - 끝내기 전에 pytest 결과를 보고한다 # .claude/settings.json (권한 부분) "deny": ["Read(./.env)", "Bash(rm -rf *)", "Bash(git push --force *)"], "ask": ["Bash(npm install *)", "Bash(git push *)"]
구독만으로 바로 시작하고, 이미 익숙한 도구의 루프·도구를 그대로 쓴다.

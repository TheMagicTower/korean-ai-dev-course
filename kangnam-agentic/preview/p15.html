하루 머지 약 2,500건 → 30,401건(5월→9월 9일)에 맞춰 git 대신 자체 소스 관리 Scion을 새로 만들었다.
인프라를 직접 새로 만든 사례다. 대부분의 프로젝트는 이 규모가 아니어서 그대로 따라 할 수는 없다.
에이전트가 늘면 PR·머지·CI가 사람 속도가 아닌 기계 속도로 는다. 방향은 우리 프로젝트도 같다.
가장 극단적인 사례가 Anthropic입니다. 2026년 10월 13일 글에 따르면 자사 모노레포의 하루 머지는 5월에 평균 약 2,500건이었는데 9월에는 3만 건을 넘었고, 차트의 정점이 9월 9일의 30,401건입니다. CI를 위한 코드 체크아웃도 하루 약 2,500만 회라고 합니다. Anthropic은 코딩이 아니라 사람 규모로 만든 개발 인프라가 병목이 되었다고 보고, git을 대체하는 Scion을 만들었습니다. 여러분의 프로젝트가 이 정도가 되지는 않겠지만, 방향은 같습니다. 에이전트가 늘면 PR과 머지와 CI 실행이 사람 속도가 아니라 기계 속도로 늘어납니다. 묶으면 장점은 에이전트 규모에 맞춘 설계, 단점은 직접 인프라를 만들어야 한다는 점이며, 시사점은 머지 자체가 병목이 된다는 것입니다.
CI 분량 줄이기실행 횟수 × 실행당 시간 × 단가 중 앞의 두 항

단가는 못 건드리니, 횟수와 시간을 줄인다

오른쪽으로 갈수록 효과가 크지만 설정과 위험도 큽니다. 왼쪽부터 하나씩 켭니다.

청구서는 실행 횟수, 실행당 시간, 단가의 곱입니다. 단가는 우리가 정할 수 없으니 앞의 두 항을 줄입니다. 방법은 네 단계로 나눠 볼 수 있습니다. 먼저 같은 PR에서 낡은 실행을 취소합니다. 다음으로 바뀐 것과 관계없는 검사를 거릅니다. 그다음 의존성과 빌드 결과를 재사용합니다. 마지막으로 머지 큐로 여러 PR을 묶어 검증합니다. 저는 여기에 PR 개수 자체를 이슈 단위 병합으로 줄이는 방법을 더합니다. 앞 단계일수록 쉽고 안전해서 먼저 켭니다.
1단계 · 취소GitHub Docs · concurrency

1. 낡은 실행은 취소한다: concurrency

docs.github.com/…/control-workflow-concurrency
GitHub Docs 화면 캡처
GitHub Docs 동시 실행 제어 문서. 같은 그룹의 실행이 겹칠 때 이전 실행을 취소하는 concurrency 설정을 다룬다.
# .github/workflows/ci.yml concurrency: group: ci-${{ github.workflow }}- ${{ github.event.pull_request.number || github.sha }} cancel-in-progress: ${{ github.event_name == 'pull_request' }} ✓ 같은 PR에 새 푸시 → 이전 실행 취소 ! 큐 후보(merge_group)는 취소 안 함 후보마다 sha가 달라 서로 끊지 않는다
같은 PR에 푸시가 잇따를 때 낡은 실행을 끊어 러너 분을 아낀다. 설정 몇 줄이면 된다.
큐 후보(merge_group)까지 같은 그룹에 넣고 취소하면 서로의 필수 검사를 끊는다.
에이전트는 푸시가 잦아서 가장 싸고 안전한 1단계. 효과는 작아도 위험이 거의 없다.
에이전트는 한 PR에 짧은 간격으로 푸시를 여러 번 합니다. 그때마다 전체 CI가 돌면 앞의 실행은 결과가 쓸모없는데도 러너를 씁니다. concurrency 그룹을 PR 번호로 잡고 cancel-in-progress를 켜면 새 푸시가 올 때 앞 실행을 취소합니다. 문서에 따르면 이 값은 표현식도 받습니다. 그래서 이벤트가 pull_request일 때만 취소하게 했습니다. 머지 큐 후보를 같은 그룹에 넣고 취소해 버리면 서로 다른 후보가 서로의 필수 검사를 끊기 때문입니다. 장점은 설정 몇 줄로 낭비를 끊는 것, 단점은 큐 후보를 취소하면 안 된다는 것, 의미는 가장 먼저 켜는 1단계라는 점입니다.
2단계 · 거르기GitHub Docs · 워크플로 구문 · paths

2. 관계없는 변경은 거른다: 경로 필터

docs.github.com/…/workflow-syntax
GitHub Docs 화면 캡처 · paths / paths-ignore
GitHub Docs 워크플로 구문 문서. 목차에 paths(특정 경로가 바뀔 때만 실행) 항목이 보인다.
# 문서만 바뀐 PR은 테스트를 건너뛴다 on: pull_request: paths-ignore: - 'docs/**' - '**.md' ! 필수 검사 워크플로 전체를 paths로 생략하면 상태가 안 올라와 PR·머지 큐가 기다릴 수 있다 → 워크플로는 항상 실행하고, 안에서 작업만 고른다
문서만 바뀐 PR은 테스트를 건너뛰어 실행 횟수가 준다. 가장 쉬운 거르기다.
필수 검사 워크플로를 통째로 생략하면 상태가 안 올라와 PR·머지 큐가 기다릴 수 있다.
워크플로는 항상 실행하고 안에서 작업만 고른다. 이 구조가 13장의 게이트로 이어진다.
가장 쉬운 거르기는 경로 필터입니다. 문서만 바뀐 PR에 테스트 전체를 돌릴 이유는 없습니다. 다만 함정이 하나 있습니다. 브랜치 보호에서 필수로 지정한 검사 워크플로를 paths 필터로 통째로 건너뛰면 그 검사의 상태가 보고되지 않아 PR이나 머지 큐가 기다릴 수 있습니다. 그래서 진입과 분석, 최종 게이트는 항상 실행하고, 그 안에서 실제 작업만 선택하는 구조를 권합니다. 이 구조는 뒤의 게이트 장에서 다시 봅니다. 장점은 쉬운 설정으로 실행 횟수를 줄이는 것, 단점은 필수 검사를 통째로 건너뛰면 대기가 걸린다는 것, 의미는 항상 실행하는 게이트가 필요하다는 점입니다.
3단계 · 재사용GitHub Docs · 의존성 캐시 · 강사 자료 ci-cd-optimization

3. 받은 것은 다시 받지 않는다: 캐시

docs.github.com/…/dependency-caching
GitHub Docs 화면 캡처
GitHub Docs 캐시 문서. 호스티드 러너는 매번 깨끗한 이미지에서 시작해 의존성을 다시 받으므로, 캐시로 재사용한다.
# PHP · Laravel 예: composer 캐시 - uses: actions/cache@v4 with: path: ~/.composer/cache key: composer-${{ hashFiles('composer.lock') }} - run: composer install ✓ lock 파일이 같으면 다운로드 생략 ! 캐시는 재사용일 뿐, 검사 생략이 아님 ! 비밀정보는 캐시하지 않는다
lock 파일이 같으면 다운로드를 생략해 실행 시간·네트워크·비용이 준다.
캐시는 재사용일 뿐 검사 생략이 아니다. 비밀정보는 캐시하지 않고, 설치가 짧으면 효과가 작다.
PHP·Laravel은 composer 캐시가 첫 후보. 먼저 설치 시간을 재 보고 도입한다.
호스티드 러너는 매번 깨끗한 이미지에서 시작하므로 의존성을 매번 내려받습니다. 문서가 설명하듯 이 반복이 네트워크와 실행 시간, 비용을 늘립니다. 의존성 캐시는 lock 파일 해시를 키로 삼아 같은 의존성을 재사용합니다. PHP와 Laravel이라면 composer 캐시가 첫 후보입니다. 두 가지는 지킵니다. 하나는 캐시와 결과 아티팩트를 구분하는 것이고, 캐시를 지워도 빌드가 재현돼야 합니다. 다른 하나는 테스트 결과를 캐시해서 코드가 바뀌었는데 검사를 건너뛰는 일을 만들지 않는 것입니다. 작은 프로젝트는 먼저 측정하고, 설치가 실제로 오래 걸릴 때 도입합니다. 장점은 반복 다운로드를 없애는 것, 단점은 검사 결과를 캐시하면 안 되고 작은 프로젝트에서는 효과가 작다는 것, 의미는 먼저 측정하고 넣으라는 점입니다.
2단계 · 거르기 심화강사 자료 parallel-ai-merge-train · Nx affected

폴더 필터를 넘어: 영향받는 검사만 고른다

기본 규칙은 변경 영역 + 전이적 소비자(그 영역을 가져다 쓰는 곳) + 경계 계약 검사. 확실하지 않으면 전체 검사로 돌아갑니다.

폴더 필터는 출발점일 뿐입니다. 공고 조회 응답에서 필드 하나가 사라지면 그것을 받아 쓰는 지원 기록과, 그 뒤의 알림까지 영향을 받을 수 있습니다. 그래서 변경 영역에 전이적 소비자를 더하고 경계 계약 검사를 붙여 고릅니다. Nx의 affected 기능도 Git 변경 파일과 프로젝트 의존성 그래프를 함께 씁니다. 이것이 가능하려면 DDD(Domain-Driven Design, 도메인 주도 설계)로 경계를 나눠 둬야 합니다. 6교시에서 본 도메인 경계가 여기서 실제로 비용을 줄입니다. 공통 라이브러리나 설정이 바뀌었거나 영향 범위를 모르겠으면 전체 검사로 돌아가는 것이 안전합니다.

4. 묶어서 검증한다: 머지 큐

docs.github.com/…/managing-a-merge-queue
GitHub Docs 화면 캡처
GitHub Docs 머지 큐 문서. 머지 큐는 PR 머지를 줄 세우고, 합친 상태로 먼저 검사하는 기능.
합친 상태로 먼저 검사해 main이 깨지는 일을 머지 전에 막고, 브랜치를 매번 최신으로 맞추지 않아도 된다.
실패가 잦거나 러너가 부족하면 대기가 오히려 늘고, 충돌 해결·검토는 대신하지 않는다. 제공 범위도 제한된다.
PR이 몰려도 기본 브랜치를 항상 초록으로 지키는 4단계 최종 수단. 앞 단계를 켠 뒤에 쓴다.

Claude Code 문서에 따르면 CLI(Command-Line Interface, 명령줄 도구)나 VS Code 확장에서 연결해 웹 앱을 테스트하고 콘솔 로그로 디버깅할 수 있습니다. 새 탭을 열어 일하며 브라우저의 로그인 상태를 공유하므로, 로그인이 필요한 관리자 화면 같은 곳도 확인할 수 있습니다. 로그인 페이지나 CAPTCHA(Completely Automated Public Turing test to tell Computers and Humans Apart, 사람 확인 퀴즈)를 만나면 멈추고 사람에게 처리를 맡깁니다. 로그인 상태를 공유한다는 것은 편리한 만큼 위험하기도 하므로, 스모크 테스트에는 테스트 계정과 개발 환경을 씁니다. 장점은 로그인된 화면까지 확인하는 것, 단점은 계정 공유의 위험, 의미는 테스트 계정과 개발 환경에서만 쓴다는 점입니다.
고르는 기준어떤 도구로 눌러 볼까

무엇을 확인하느냐로 도구를 고른다

정답은 하나가 아닙니다. 웹 앱이면 Playwright MCP로 흐름, DevTools MCP로 증거가 무난한 조합입니다.

도구는 확인 대상으로 고르면 됩니다. 웹 앱의 화면과 흐름이면 Playwright MCP가 기본입니다. 콘솔 오류나 네트워크 요청까지 증거로 남기려면 DevTools MCP를 더합니다. 로그인된 내 Chrome에서 확인해야 하면 Claude in Chrome이 편합니다. 브라우저 밖의 데스크톱 앱이라면 computer use입니다. 특정 도구만 정답은 아닙니다. Codex나 Gemini, Cursor 같은 다른 도구에서도 같은 MCP 서버를 연결해 같은 일을 할 수 있습니다.
스모크 시나리오 쓰는 법강사 운영 방식

시나리오 한 개는 다섯 칸이면 된다

핵심 흐름 3~5개만. 로그인, 핵심 기능 한 번, 저장 후 다시 열기 정도가 적당합니다.

스모크 시나리오는 길게 쓰지 않습니다. 목적, 전제, 단계, 판정, 증거 다섯 칸이면 됩니다. 목적은 이 시나리오가 어떤 약속을 확인하는지 한 줄로 적습니다. 전제에는 주소와 테스트 계정, 필요한 데이터를 적습니다. 단계는 사용자가 하는 행동을 순서대로 쓰고, 판정은 화면에 무엇이 보여야 하는지를 눈으로 확인 가능한 문장으로 씁니다. 마지막으로 어떤 증거를 남길지 정합니다. 시나리오 수는 핵심 흐름 서너 개로 제한합니다. 많아지면 느려져서 아무도 돌리지 않습니다.
예시 파일smoke/login.md · Playwright MCP로 실행

시나리오는 저장소 안의 마크다운 파일이다

playwright.dev/mcp/introduction
Playwright 공식 문서 화면 캡처 · 실행 방법
Playwright MCP 문서의 시작 방법 화면. 오른쪽 시나리오 파일을 이 도구로 실행한다.
# smoke/login.md 목적: 로그인하면 대시보드에 닿는다 전제: http://localhost:8000 계정 demo@example.test (시드) 단계 1. /login 을 연다 2. 이메일·비밀번호 입력, [로그인] 3. 대시보드 제목을 확인 판정 - 주소가 /dashboard - "내 현황" 제목이 보인다 - 콘솔 error 0건 - 실패한 요청(4xx·5xx) 0건 증거: 단계마다 스크린샷
실제 시나리오 파일은 이 정도입니다. 저장소 안에 마크다운으로 두면 에이전트가 읽고 그대로 실행하고, 사람도 읽을 수 있고, 변경 이력도 남습니다. 판정에 콘솔 오류와 실패한 요청을 넣는 것이 중요합니다. 화면이 보여도 뒤에서 오류가 나는 경우를 걸러 내기 때문입니다. 단계에는 클릭할 좌표가 아니라 사용자가 보는 이름을 씁니다. 그래야 접근성 스냅샷으로 요소를 찾는 Playwright MCP가 안정적으로 따라갑니다. 데이터는 시드 계정처럼 항상 같은 상태로 만들 수 있는 것을 씁니다.
스크린샷 · 콘솔 로그통과했다는 말이 아니라 통과한 증거

“통과했습니다”가 아니라 증거 파일을 남긴다

규칙: 증거 없는 PASS는 FAIL. 에이전트에게 파일 이름 규칙까지 시키고, PR에 보고서를 붙입니다.

에이전트가 스모크를 돌린 뒤 통과했다고만 말하면 그 말은 검증할 수 없습니다. 그래서 실행마다 증거 폴더를 만들게 합니다. 단계별 스크린샷, 콘솔 로그, 실패한 네트워크 요청, 그리고 PASS 또는 FAIL을 적은 보고서입니다. 프롬프트에는 증거가 없는 항목은 실패로 처리하고, 콘솔 오류가 있으면 화면이 정상이어도 실패로 보고하라고 적습니다. 보고서와 핵심 스크린샷은 PR이나 이슈 댓글로 남기고, 머지 큐에 넣기 전에 사람이 증거를 보고 판정합니다. 비밀번호나 토큰이 스크린샷과 로그에 남지 않는지도 확인합니다.

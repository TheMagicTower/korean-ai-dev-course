권한 규칙: deny가 먼저, 그다음 ask, 마지막 allow

{{svg:p04-rule-order}}

처음 맞은 규칙이 결과를 정합니다. 구체적인 allow도 넓은 deny를 뚫지 못합니다. → 3교시 복습

3교시에서 본 순서를 파일로 옮기는 시간입니다. 규칙은 deny, ask, allow 순서로 평가되고, 처음 맞은 규칙이 결과를 결정합니다. 규칙이 구체적이라고 우선하지 않습니다. 예를 들어 Bash(aws *)를 deny로 막았다면 Bash(aws s3 ls)를 allow로 적어도 막힌 상태입니다. 어디에도 맞지 않는 호출은 현재 권한 모드의 기본 동작을 따릅니다. 그래서 금지할 것은 deny에, 반드시 확인받을 것은 ask에, 안전하고 자주 쓰는 것만 allow에 적습니다.

# 프로젝트 루트/.claude/settings.json { "permissions": { "deny": [ "Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)", "Bash(rm -rf *)", "Bash(git push --force *)" ], "ask": [ "Bash(git push *)", "Bash(git commit *)" ], "allow": [ "Bash(npm run test *)", "Bash(git diff *)" ] } }

공식 문서 화면 캡처 · 2026-10-28
권한 문서. 규칙을 allow(허용)·ask(확인)·deny(금지)로 나누고 deny → ask → allow 순으로 평가한다.
이 파일이 오늘의 첫 결과물입니다. 프로젝트 루트에 .claude 폴더를 만들고 settings.json에 이렇게 적습니다. deny에는 환경 변수 파일과 비밀 폴더 읽기, 재귀 삭제, 강제 푸시를 넣었습니다. ask에는 일반 푸시와 커밋처럼 사람이 한 번 봐야 하는 것을, allow에는 테스트 실행과 diff처럼 안전하고 자주 쓰는 것을 넣었습니다. 한 가지 주의할 점이 있습니다. Read 규칙은 내장 파일 도구와 cat 같은 알려진 명령에는 적용되지만, 파이썬 스크립트가 파일을 직접 여는 경우까지 막지는 못한다고 문서에 적혀 있습니다. 그래서 규칙은 안전장치의 한 겹이고, 진짜 격리는 샌드박스가 맡습니다. 샌드박스는 3교시에서 본 그 이야기입니다.

다른 도구를 고른 분은 같은 개념을 자기 도구의 방식으로 옮기면 됩니다. Codex는 홈 폴더의 .codex/config.toml에 승인 정책과 샌드박스 모드를 적습니다. 공식 문서의 예시는 approval_policy를 on-request로, sandbox_mode를 workspace-write로 둔 것입니다. 작업 폴더 안에서만 쓰고, 필요하면 사용자에게 묻는다는 뜻입니다. Claude Code처럼 도구별 deny, ask, allow 목록을 쓰는 방식과는 모양이 다릅니다. Gemini CLI나 Cursor는 설정 형식이 또 다르니 각자 공식 문서에서 승인과 격리 설정을 찾아 적용해 주세요. 어느 도구든 Codex의 장점은 두 줄로 승인과 격리 범위를 정할 수 있다는 점이고, 단점은 Claude Code처럼 명령별로 세밀하게 규칙을 쓰는 방식과 모양이 다르다는 점입니다. 의미는 개념은 같고 형식만 다르다는 것입니다. 무엇을 막았고 무엇을 허락했는지를 제출물에 적는 것이 기준입니다.

# 방식 A: 수동(기본) $ git switch -c try-manual $ claude > utils.py에 slugify(title)와 테스트를 추가하고 테스트를 돌려줘 ! 승인 창마다 Yes, 횟수를 센다 # 방식 B: 편집 자동 승인 $ git switch -c try-accept main $ claude --permission-mode acceptEdits > (같은 프롬프트) → 모드 전환: Shift+Tab

공식 문서 화면 캡처 · 2026-10-28
권한 모드 문서. 매번 확인하는 수동(Manual), 편집을 자동 승인하는 acceptEdits 등 모드별로 묻는 범위가 다르다.
이제 승인 피로를 직접 느껴 볼 차례입니다. 같은 저장소 상태에서 브랜치를 둘로 나눠, 같은 프롬프트를 한 번은 기본 모드로, 한 번은 acceptEdits 모드로 실행합니다. acceptEdits는 작업 폴더 안의 파일 편집과 mkdir, mv, cp 같은 파일 명령을 묻지 않고 처리하는 모드입니다. 그래도 테스트 실행 같은 일반 명령은 여전히 묻습니다. 그래서 두 번째 실행에서 승인 횟수가 줄어드는 정도와, 남은 승인이 무엇인지를 함께 봅니다. 프롬프트는 두 번 모두 한 글자도 다르지 않게 복사해서 쓰세요. 비교가 공정해야 합니다. 시작 전에 5분 타이머를 켜 둡니다.

Claude API 도구 사용 문서. 모델이 우리가 정의한 함수를 호출하게 하는 방법(tool use).
코드형 트랙의 첫 반쪽입니다. 도구는 평범한 파이썬 함수 세 개입니다. 파일 읽기, 문자열 하나를 정확히 한 번 바꾸는 수정, 명령 실행입니다. 중요한 것은 safe 함수와 DENY 목록입니다. 에이전트가 작업 폴더 밖을 건드리거나 금지된 명령을 실행하지 못하게 하는, 오늘 만든 권한 규칙의 코드 버전입니다. 모델 이름은 환경 변수로 받습니다. 모델은 자주 바뀌므로 코드에 박아 두지 않는 편이 낫습니다. 이 스켈레톤은 구조를 보여 주는 것이고, 오류 처리와 로그는 각자 채워서 약 100줄로 완성합니다. 도구 사용 규약은 오른쪽의 공식 문서에 있습니다.
코드형 트랙모델 호출 → 도구 실행 → 결과 확인 → 멈춤

코드형 (2): 도구 호출이 없거나 20번째 바퀴에서 멈춘다

# harness.py (2/2) · 루프 TOOLS = [{"name": "read_file", "description": "파일을 읽는다", "input_schema": {"type": "object", "properties": {"path": {"type": "string"}}, "required": ["path"]}}, # edit_file(path, old, new), run(cmd)도 같은 형식] IMPL = {"read_file": read_file, "edit_file": edit_file, "run": run} MAX_STEPS = 20 def main(task): messages = [{"role": "user", "content": task}] for step in range(MAX_STEPS): # 멈춤 1: 횟수 resp = client.messages.create( model=MODEL, max_tokens=2048, tools=TOOLS, system=open("AGENTS.md").read(), messages=messages) messages.append({"role": "assistant", "content": resp.content}) if resp.stop_reason != "tool_use": # 멈춤 2: 도구 호출 없음 print("".join(b.text for b in resp.content if b.type == "text")) return results = [] for b in resp.content: if b.type == "tool_use": out = IMPL[b.name](**b.input) print(f"[{step}] {b.name} {b.input}") results.append({"type": "tool_result", "tool_use_id": b.id, "content": str(out)}) messages.append({"role": "user", "content": results}) print("최대 횟수 도달: 중단") if __name__ == "__main__": main(input("task> "))

나머지 반쪽이 루프입니다. 모델을 호출하고, 응답의 stop_reason이 tool_use이면 요청된 도구를 실행해 결과를 tool_result로 대화에 붙이고, 다시 모델을 부릅니다. 도구를 더 부르지 않으면 모델이 끝났다는 뜻이므로 멈춥니다. 여기에 반드시 최대 횟수라는 두 번째 멈춤 조건을 둡니다. 모델이 끝없이 도구를 부르는 경우를 대비한 안전장치입니다. system에 AGENTS.md를 읽어 넣은 것은 설정형 트랙의 프로젝트 지침 파일과 이어지는 부분입니다. 한 줄씩 출력하게 해 두면 에이전트가 무엇을 했는지 대화 기록으로 그대로 남습니다.

공식 문서 화면 캡처 · 2026-10-28
CLAUDE.md 문서. 세션마다 읽히는 프로젝트 지침 파일(CLAUDE.md·AGENTS.md)로 Claude가 프로젝트를 기억한다.
설정형은 이미 만든 권한 파일에 지침 파일 하나를 더하면 됩니다. Claude Code는 시작할 때마다 프로젝트의 CLAUDE.md를 읽고, CLAUDE.md가 없고 AGENTS.md만 있으면 AGENTS.md를 프로젝트 지침으로 읽습니다. 다른 도구를 쓰는 분은 그 도구가 읽는 지침 파일 이름을 확인해 주세요. 내용은 짧게 씁니다. 프로젝트 수준, 실행 명령, 지켜야 할 규칙 정도면 충분합니다. 특히 테스트를 지우거나 건너뛰지 말라는 규칙, 끝내기 전에 테스트 결과를 보고하라는 규칙은 뒤의 회차에서 계속 쓰게 되는 뼈대입니다. 그 뒤에 같은 작업을 한 번 더 돌려서 지침을 쓰기 전과 어떻게 달라졌는지 대화 기록으로 남깁니다.

Quickstart 문서. 시작 전 준비물과 단계별 순서(설치 → 첫 세션 → 첫 질문)가 나온다.
막히는 지점은 대개 정해져 있습니다. 설치 직후에 명령을 못 찾는 경우는 거의 PATH 때문이고, 새 터미널을 열면 풀리는 일이 많습니다. 로그인이 안 되면 claude 안에서 /login으로 다시 인증합니다. 규칙이 먹지 않을 때는 JSON 문법 오류가 가장 흔합니다. 쉼표와 따옴표를 확인하고 /permissions로 규칙이 읽혔는지 봅니다. 마지막 줄이 중요합니다. 오류 문구를 그대로 복사해서 에이전트에게 물어보는 것도 정당한 방법입니다. 다만 그 질문과 답도 대화 기록에 남겨 제출해 주세요. 도움을 받은 과정도 하네스 연습의 일부입니다.

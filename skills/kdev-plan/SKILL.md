# 목업과 설계·작업 계획

한국어 존댓말로 설명하며 코드·API 식별자는 원문을 유지합니다.

## 적용 범위와 비용

사용자의 명시적 요청과 기존 프로젝트 규칙을 먼저 따릅니다. 사용 범위(개인·팀·외부), 목표 단계(PoC·MVP·운영), 실제 위험, 이번 작업 예산과 완료 조건을 기존 계약에서 읽습니다. 없으면 작업에 영향을 주는 부분만 확인하거나 가정을 표시합니다. 저위험 개인 작업에 기업용 문서·로그인·CI/CD·독립 리뷰를 일괄 추가하지 않습니다. 필요한 조건을 통과하면 종료하고 선택 개선은 후속으로 남깁니다. 예산 소진 시 필수 미달은 미완료로 인계합니다. 없는 도구·권한·실행 증거를 가정하지 않습니다.

## 수행

1. 기존 계약·개요·기술 가이드라인·ADR·Spec을 읽습니다. 이미 확정한 문제를 처음부터 재조사하지 않습니다. 신규 UI 작업은 디자인에서 상세 설계를 도출하는 흐름을 기본으로 하며, 단순 수정에 새 목업을 강제하지 않습니다.
2. 문제·시나리오·제약으로 목업 또는 조작 가능한 프로토타입을 만듭니다. 사용 가능한 도구를 쓰며 Claude 디자인은 기본 사례일 뿐입니다. UI 없는 작업은 예시 입력·결과 파일로 대체합니다. 비교할 안과 시간 예산을 제한합니다.
3. 목업을 조작하며 사용자 행동·정상/빈/오류 상태·피드백을 확인합니다. 가짜 데이터·항상 성공하는 응답·미구현 권한을 표시합니다.
4. 행동에서 업무 규칙·상태 전이·권한·기능/수용 조건을 도출하고, API 요청·응답·오류·부작용, 데이터 의미·관계·제약·저장 구조로 구체화합니다. 화면마다 테이블을 기계적으로 만들지 않습니다. 기술 모순은 해당 경험을 다시 검토합니다.
5. 상세 Spec과 중요한 결정의 ADR을 갱신합니다. ADR에는 배경·대안·선택·이유·영향·다시 판단할 조건을 남깁니다. 목업 코드의 재사용/재구현은 제품 적합성으로 결정합니다.
6. 운영형은 프로젝트 → 마일스톤(결과) → 작업 스테이지(목표) → 스프린트(산출물) → Task(할 일)로 분해합니다. 작은 프로젝트는 하나의 계획 안에 통합합니다. 작업 스테이지와 배포 스테이징 환경을 구분합니다.
7. Task마다 범위·의존·검증·완료 증거를 정합니다. GitHub 추적 이슈·워크트리는 필요한 규모와 요청에 맞게 구성하며 계획 요청만으로 외부 이슈를 생성하지 않습니다.
8. 운영형 개발 순서는 이슈 분석 → ADR → 이슈 Spec → 스펙 리뷰 수렴 → 구현 계획 → 계획 리뷰 수렴 → 구현입니다. 검토가 필요한 수준이면 블로커가 없는 단계부터 진행합니다. 이전 통과 단계는 영향 있는 변경에만 다시 엽니다.

## 산출물과 종료

선택 시안·미구현 목록, 규칙/기능/API/데이터 계약, Spec·ADR 변경, 작업별 산출물·검증·예산을 남깁니다. 이미 제공된 시안·Spec은 재사용합니다. 계획만 요청받으면 구현 전 종료합니다.

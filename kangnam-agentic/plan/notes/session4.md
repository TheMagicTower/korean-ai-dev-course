**주의 (흔한 오해)**
- 3~7장 근거는 Anthropic ‘Skill authoring best practices’와 agentskills.io 명세(2026-11-18 확인). 500줄·참조 한 단계·대표 요청 3개는 문서의 권고값이다.
- 무엇이든 스킬로 만들지 않는다. 모든 세션에 필요한 짧은 규칙은 CLAUDE.md·AGENTS.md, 매번 같은 결과가 필요한 일은 스크립트(3장).
- 호출이 안 되면 본문보다 description부터 본다. 3인칭, 핵심을 앞에(1,536자에서 잘림). 사람이 불러야 하는 스킬은 모델 호출 끄기(4장).
- 자유도는 스킬 전체가 아니라 작업마다 정한다. 코드 리뷰는 글로, 마이그레이션은 정해진 명령으로(6장).
- task-observer는 관찰→제안→사람 검토. 작은 추가도 검토용 복사본에만, 실제 스킬 반영은 사람이 설치할 때(8–9장).
- 오늘은 실습이 아니라 설명이다. 학생이 설정 파일을 쓰거나 읽는 순서가 아니고, 에이전트가 질문하고 ADR·스킬·MCP를 만들고 학생은 답하고 승인하고 스모크로 확인하는 흐름을 소개한다. 승인은 사람만 한다(15장). 슬라이드의 스모크 결과는 모두 예시.
- 15단계 범위는 격리·충돌·리뷰·머지 규칙이다. PR(Pull Request, 변경 병합 요청) 생성·머지는 정하기만 하고, 실제 순서는 16교시 뒷부분에서 설명으로 본다(13–14장, 스킬 프롬프트의 ‘PR·머지는 넣지 마’).
- /goal 평가자는 명령 실행·파일 읽기를 못 한다. 증명을 출력에 붙이라고 해야 하고 상한 없으면 비용이 끝없이 늘 수 있다. 자동 승인 모드에서는 도구 승인도 없으니 상한을 꼭 적는다(18장).
- 스킬은 설명 문장이 호출을 좌우한다. 안 불리면 원인을 설명시키고 고친 뒤 같은 문장으로 다시 보게 한다(16·23장).
- MCP 서버는 공식 제공처 등 출처를 믿을 수 있는 것 하나만 연결하고, 쓰기 권한이 필요한지 확인해 되도록 읽기 권한으로 둔다. 비밀 값은 환경 변수 이름으로만, 설정을 바꾼 뒤엔 새 세션에서 확인(17·23장). 서버가 가져오는 글은 주입 위험이 있어 지시로 따르지 않는지 묻는다.
- 실패한 기록도 좋은 자료이고, 21장 표의 숫자(14분·11턴 등)는 양식용 예시다. 못 쟀으면 못 쟀다고 적는다.

**예상 질문**
- “자동 호출이 안 돼요.” → description의 사용 상황·사용자가 할 법한 말을 앞에(4장). 먼저 슬래시로 직접 불러 위치·형식 확인.
- “스킬 vs MCP?” → MCP는 도구 연결, 스킬은 절차 지침 폴더. 둘 다 점진적 로딩 원리가 비슷.
- “스킬을 많이 깔면 컨텍스트 윈도우가 차나요?” → 시작 시 이름·설명만 올라가 본문보다 훨씬 작지만, 스킬마다 이름·설명만큼의 비용은 쌓인다. 설명 목록은 1,536자 상한.
- “/goal이 안 끝나요.” → 조건이 모호하거나 측정 불가. 상태를 보고 측정 가능한 문장으로 다시 쓰게 한다(23장).
- “/goal이 없는 도구예요.” → 상한이 있는 반복 실행 루프를 시키고 풀 수 없는 과제로 멈춤을 확인한다(19장).
- “질문이 계속 나와요.” → 8개 안에서 끝내라고 첫 프롬프트에 적었다. 모르는 항목은 선택지 두 개와 장단점 표를 달라고 한다(13장).
- “실패 기록도 나누나요?” → 예. 5회차 공유의 가장 좋은 소재.

**시연·준비**
- 직접 SKILL.md 한 장으로 호출 시연(7장). `.claude/skills` 구조를 열어 보여 줌.
- 프롬프트와 스모크 결과는 슬라이드의 예시로 설명한다(사전 실행 불필요). 지난 회차(8교시) 하네스 저장소와 처리해 둔 이슈 한 건이 있으면 설계 대화 예시로 언급.
- 제출물 없음. 5회차에 나누면 좋은 것만 안내(쓴 프롬프트, 스모크 표 한 장, 막힌 곳 하나). 캡처 대기 장 없음.

**주의 (흔한 오해)**
- 일반론과 강사가 더한 것을 섞지 않는다. 일반론 장(6·13·14·15·20–24장)은 공식 문서·원저자 글로 말하고, ‘강사가 더한 것’ 장(16–19·25–26장)은 무엇을 더했고 어떤 문제를 막으려 했는지 말한다.
- 13장은 Nygard 원형과 MADR만 비교한다. MADR의 확인 칸은 구현이 결정을 따르는지 확인하는 용도라 ‘다시 판단할 조건’과 성격이 다르다. 재평가 조건을 적으라는 권고는 Fowler(2026-03-24)에 있지만 전용 칸은 일반 서식에 없다(16장).
- 17·18장 예시 ADR은 교육용 가상 프로젝트(실제 기록 아님).
- 14장 “ADR이 에이전트에게 좋다”는 현장 경험의 설명이며 모든 프로젝트에서 이득을 측정한 것이 아니다.
- 25장 네 계층(마일스톤·스테이지·스프린트·Task)은 교육용 구체화이며 GitHub 별도 기능이 아니다(22장은 GitHub 기능인 하위 이슈·마일스톤만). 하위 이슈 제한은 GitHub 문서 수치.
- 23장 이슈 병합 도식은 가상 예시. 묶는 기준은 GitHub 문서의 ‘작고 한 목적에 집중한 PR’에서 목적 하나. 중복으로 닫은 이슈(Duplicate of #N)는 수정 완료가 아니다. 24장: 부분 반영·단순 연관은 `Related`, 사이드바 수동 연결 이슈는 머지 때 닫힐 수 있어 연관 표시로 쓰지 말 것. 키워드는 기본 브랜치 대상 PR에서만 해석.
- 초안은 에이전트가 써도 ‘승인됨’은 사람이 바꾼다(15장). 이 강의의 서식에서는 사용자 판단 칸도 사람이 채운다(16·18장).
- 25장 18단계·26장 12단계는 일반론이 아니라 이 강의가 더한 운영 틀이다. 18단계 번호는 1회차부터 쓰므로 그대로 두고, 작은 프로젝트에서는 합치거나 생략한다.
- “Actions 과금이 올랐다”가 아니라 “단가는 내렸고 실행량이 폭증”. 셀프호스티드 러너 신규 과금은 보류(29장).
- 경로 필터로 필수 검사 워크플로를 통째로 건너뛰면 상태가 보고되지 않아 PR·머지 큐가 기다린다. 진입·분석·최종 게이트는 항상 실행(34장).
- 머지 큐에서 취소 concurrency를 후보에 걸면 후보끼리 필수 검사를 끊는다. `merge_group` 이벤트를 안 받으면 필수 검사가 보고되지 않아 머지가 실패한다(GitHub Docs ‘Managing a merge queue’). 게이트의 `always`는 항상 성공이 아니며 실패·취소·예상 밖 skip을 통과로 바꾸면 안 된다(39장).
- 머지 큐는 충돌 해결·검토 대체 도구가 아니고 제공 범위(조직 공개 저장소·Enterprise Cloud 비공개)를 확인. 실패가 잦으면 오히려 대기가 늘 수 있음.
- 41장 표는 제품 실측이 아닌 교육용 가정(러너 3개: 36분 → 12분이나 사용량 36 러너·분 동일). “최대 병합 3 → 비용 1/3”으로 계산 금지(문서: 병합 한도는 merge_group 빌드를 합치지 않음).

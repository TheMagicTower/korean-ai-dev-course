SDD의 두 뜻: 1987년 설계 기술서, 2025년 스펙 주도 개발

같은 약어, 다른 말. Software Design Description(IEEE(Institute of Electrical and Electronics Engineers, 전기전자공학자협회) 1016, 1987)은 사람에게 설계를 전하는 문서, Spec-Driven Development는 스펙으로 개발을 이끄는 방식이다.

SDD라는 약어는 2025년에 새로 생긴 말이 아닙니다. 1987년 IEEE(Institute of Electrical and Electronics Engineers, 전기전자공학자협회) 1016, ‘소프트웨어 설계 기술서에 관한 권고 실무’가 Software Design Description을 SDD로 불렀습니다. 표준은 SDD를 소프트웨어 시스템의 표현이자 설계 정보를 전달하는 매체로 정의했고, 1998년과 2009년에 개정된 뒤 2020년에 비활성 상태가 됐습니다. 이때의 SDD는 사람이 읽고 사람이 코드를 쓰는 문서였습니다. 2004년에는 Ostroff, Makalsky, Paige가 애자일 학회에서 ‘Agile Specification-Driven Development’를 발표합니다. 테스트 주도 개발과 계약에 의한 설계를 묶어, 명세가 개발을 이끌게 하자는 제안이었습니다. 그 사이 모델에서 코드를 생성하는 MDD(Model-Driven Development, 모델 주도 개발), 시나리오를 실행 가능한 명세로 쓰는 BDD(Behavior-Driven Development, 행동 주도 개발)도 같은 생각을 다른 방식으로 시도했습니다. 그리고 2025년 Kiro와 Spec Kit이 에이전트가 읽는 스펙을 내세우면서 Spec-Driven Development라는 말이 퍼졌습니다. 10월에는 Böckeler의 글이 이를 세 수준으로 정리했습니다. 약어는 같지만 앞은 문서의 이름이고, 뒤는 일하는 방식의 이름입니다.

SDD의 세 수준: 스펙의 수명으로 구분

같은 SDD라도 스펙의 수명이 다릅니다. 글쓴이는 Kiro와 Spec Kit이 대체로 spec-first라고 평가했습니다.

세 수준을 구분하면 이야기가 선명해집니다. 첫째 spec-first는 작업 전에 스펙을 쓰고, 작업이 끝나면 그 스펙의 역할이 끝납니다. 모든 SDD 도구가 공유하는 수준입니다. 둘째 spec-anchored는 스펙을 작업 뒤에도 남겨 두고 기능을 고치고 유지할 때 다시 씁니다. 셋째 spec-as-source는 사람이 스펙만 고치고 코드는 손대지 않는 단계입니다. 글쓴이는 Kiro가 대체로 spec-first이고, Spec Kit은 기능마다 브랜치를 새로 만들기 때문에 역시 spec-first에 가깝다고 봤습니다. Tessl만이 anchored와 as-source를 목표로 탐색 중이라고 했습니다.

“만료를 15분으로 줄여 주세요”: 세 수준의 차이

사람이 고치는 것끝난 뒤 남는 것흔한 문제
spec-first코드의 RESET_TTL = 30 * 60을 직접 수정. 옛 스펙은 안 본다스펙엔 여전히 “R1 … 30분”다음 사람·에이전트가 낡은 스펙을 믿고 30분으로 되돌린다
spec-anchored스펙 R1을 먼저 15분으로 → 테스트 → 코드스펙·테스트·코드가 모두 15분스펙을 고치는 수고가 매번 든다
spec-as-source스펙 R1 한 줄만. 코드는 다시 생성스펙이 원본, 코드는 생성물생성 결과가 매번 같은지 보장하기 어렵다
# spec-anchored: 스펙 → 테스트 → 코드 순으로 한 줄씩 - R1 재설정 링크는 발급 30분 뒤 만료된다 spec.md + R1 재설정 링크는 발급 15분 뒤 만료된다 - def test_link_expires_after_30_minutes(): test_reset.py + def test_link_expires_after_15_minutes(): - RESET_TTL = 30 * 60 reset.py + RESET_TTL = 15 * 60
앞 장의 R1을 그대로 가져와 요구가 바뀌는 상황을 만들어 보았습니다. 세 수준의 차이는 처음 만들 때가 아니라 이렇게 바꿀 때 드러납니다. spec-first에서는 스펙이 이미 할 일을 마친 문서라서 보통 코드만 고치게 되고, 그 결과 저장소에 서로 다른 두 숫자가 남습니다. 나중에 에이전트가 그 낡은 스펙을 읽으면 오히려 코드를 스펙에 맞춘다며 30분으로 되돌릴 수 있습니다. spec-anchored는 스펙부터 고치는 습관이고, spec-as-source는 사람이 코드를 아예 안 만지는 극단입니다. 여러분 과제에서는 spec-anchored 정도, 즉 스펙 한 줄과 테스트 한 줄을 같이 고치는 것을 권합니다. 표의 내용은 Böckeler의 세 수준 정의를 이 예에 대입한 가상 예입니다.

TDD: 실패하는 테스트 먼저

martinfowler.com/bliki/TestDrivenDevelopment.html
Martin Fowler bliki 화면 캡처 · 2026-10-28 확인
Fowler의 TDD 설명 글. 테스트 목록에서 하나 골라 쓰고(Red) → 통과시키고(Green) → 정리(Refactor)하는 반복 도식.
  1. 다음 기능의 테스트를 쓴다 (Red: 아직 실패)
  2. 통과할 때까지 구현한다 (Green: 통과)
  3. 동작은 그대로 두고 구조를 정리한다 (Refactor)

Kent Beck이 1990년대 후반 익스트림 프로그래밍의 일부로 발전시킨 기법

TDD는 새로운 방법이 아닙니다. Fowler의 설명대로 Kent Beck이 1990년대 후반 익스트림 프로그래밍의 일부로 만들었고, 세 단계를 반복합니다. 다음 기능의 테스트를 먼저 쓰고, 통과할 최소한의 코드를 쓰고, 구조를 정리합니다. 이 글은 테스트를 먼저 쓰면 인터페이스를 먼저 생각하게 된다는 점도 이점으로 꼽습니다. 그리고 가장 흔한 실패가 세 번째, 정리를 건너뛰는 것이라고 지적합니다. 사람이 오래 못 지킨 습관이라는 점을 짚어 둡니다.

“구현 완료했습니다” 뒤에 숨은 쿠폰 중복 적용

1) 완료 기준 없이 시킴
> 장바구니에 할인 쿠폰 적용 기능 만들어 줘 에이전트: 구현 완료했습니다. # 같은 쿠폰 WELCOME3000을 두 번 적용 {'total': 14000, 'coupons': ['WELCOME3000', 'WELCOME3000']}
  • 20,000원 주문이 6,000원 할인
  • 판정 기준이 없어 “완료”를 믿을 수밖에 없음
2) 테스트를 완료 기준으로 줌
> test_cart.py가 모두 통과해야 완료. 같은 쿠폰 두 번은 ValueError. 실행 출력을 붙여서 보고해. $ python3 test_cart.py # 첫 구현 FAIL: test_same_coupon_twice_is_rejected AssertionError: ValueError not raised $ python3 test_cart.py # 수정 후 Ran 2 tests ... OK
  • 같은 첫 구현이 이번엔 보고 전에 걸림

코드는 같아도 판정 기준이 있으면 빠진 규칙이 보고 전에 드러납니다.

쇼핑몰에서 할인 쿠폰을 붙이는 기능을 맡긴 가상 상황입니다. 왼쪽처럼 기능만 말하면 에이전트는 할인이 한 번 들어가는 것을 확인하고 완료라고 보고합니다. 그런데 같은 쿠폰을 두 번 넣으면 할인이 두 번 들어갑니다. 이 출력은 그 첫 구현을 실제로 실행해 얻은 결과입니다. 오른쪽처럼 중복 규칙을 테스트로 적고 통과를 완료 조건으로 주면, 똑같은 첫 구현이 보고 전에 실패로 걸리고 에이전트가 스스로 고칩니다. 핵심은 에이전트가 더 똑똑해진 것이 아니라, 완료를 판정할 기준이 생겼다는 점입니다.

Red 확인이 먼저, Green은 그다음

1) 스텁(가짜 구현) · 테스트 실행 → Red(실패)
def submit(status): return "submitted" $ python3 transition_test.py FAIL: test_submitted_cannot_be_submitted_again AssertionError: ValueError not raised Ran 2 tests ... FAILED (failures=1)
2) 구현 → Green(통과)
def submit(status): if status != "draft": raise ValueError("작성 중인 지원만 제출할 수 있습니다.") return "submitted" $ python3 transition_test.py Ran 2 tests ... OK

규칙: 이미 제출한 지원은 다시 제출할 수 없다. 실패가 규칙을 가리키는지 확인한 뒤에 구현합니다.

제 강의 자료의 작은 예시를 이 자리에서 실제로 실행한 결과입니다. 규칙은 이미 제출한 지원은 다시 제출할 수 없다는 것입니다. 먼저 항상 제출됨을 돌려주는 스텁으로 테스트를 돌리면 두 번째 테스트가 실패합니다. 이 Red를 눈으로 확인하는 것이 중요합니다. 실패한 이유가 규칙 때문이어야 테스트가 쓸모 있다는 증명이 됩니다. 그다음 구현을 넣으면 두 테스트가 통과합니다. 에이전트에게도 구현 전에 테스트를 실행해 실패를 보여 달라고 시킵니다.

의존 방향이 안쪽 하나라 규칙이 단순하다. 안쪽은 엔티티(업무 규칙), 바깥은 UI(User Interface, 사용자 화면)·DB(Database, 데이터베이스)·프레임워크.

클린 아키텍처의 핵심은 의존성 규칙입니다. 소스 코드 의존은 안쪽으로만 향하고, 안쪽 원은 바깥쪽 이름을 알아서는 안 됩니다. 가장 안쪽은 엔티티, 즉 업무 규칙이고, 바깥은 UI(User Interface, 사용자 화면), DB(Database, 데이터베이스), 프레임워크 같은 세부 사항입니다. 이 글의 원래 도식 이미지는 제가 가져온 화면에서 로딩되지 않아 본문 문단을 보여 드립니다. 프롬프트에 클린 아키텍처라고 적으면 에이전트는 이 계층 구조를 따라 도메인, 응용, 인프라로 나누려 합니다. 장점은 의존 방향이 하나라 단순하다는 것, 단점은 작은 PoC에는 과하다는 것, 의미는 규모를 프롬프트에 적어야 한다는 점입니다.

import 화살표는 바깥에서 안쪽으로만

화살표 = import(소스 코드 의존). 호출과 데이터는 양방향으로 오가도, import 화살표는 안쪽으로만. DB가 필요하면 안쪽에 RoomRepository 인터페이스를 두고 바깥이 구현합니다(의존성 역전).

도식을 바깥 겹부터 따라가 보겠습니다. 가장 바깥은 FastAPI, PostgreSQL 같은 프레임워크와 드라이버이고, 그 안에 컨트롤러와 저장소 구현이 있는 인터페이스 어댑터, 다시 그 안에 예약하기 같은 유스케이스, 가장 안쪽에 Room과 can_reserve 같은 엔티티가 있습니다. 화살표는 누가 누구를 import하는지를 뜻하고, 모두 바깥에서 안쪽으로만 향합니다. 실행 중에는 요청이 안으로 들어가고 결과가 밖으로 나오지만, 소스 코드의 import는 그 방향을 따르지 않는다는 점이 헷갈리는 지점입니다. 안쪽이 DB 조회가 필요하면 안쪽에 RoomRepository라는 인터페이스를 두고, 바깥의 SqlRoomRepository가 그것을 구현하게 해서 화살표 방향을 지킵니다. 분홍색 점선처럼 can_reserve가 PostgreSQL을 직접 부르는 것이 금지된 방향이고, 다음 장이 바로 그 위반을 실제로 만든 사례입니다.

git 공식 문서의 git-worktree 설명. 한 저장소에 작업 폴더를 여럿 붙여 브랜치 여러 개를 한 번에 체크아웃(펼치기)할 수 있다.
$ git worktree add ../app-login -b feat/login $ git worktree add ../app-search -b feat/search $ git worktree list /home/me/app a1b2c3d [main] /home/me/app-login a1b2c3d [feat/login] /home/me/app-search a1b2c3d [feat/search] $ git worktree remove ../app-login ✓ “check out more than one branch at a time” = 브랜치 여럿을 한 번에 펼친다 ! 같은 브랜치는 두 곳에 못 연다(기본값)
git이 오래전부터 제공한 기능. 브랜치마다 폴더가 생기고 기록은 공유해, 합치기도 일반 머지다.
같은 브랜치는 두 곳에 못 연다. 새 체크아웃이라 의존성 설치 등 환경 준비가 따로 필요하다. 서브모듈은 실험적.
에이전트 병렬화의 해법은 새 발명이 아니라 오래된 git 기능. Claude Code·Codex가 이를 제품에 넣었다.
워크트리는 새 기능이 아닙니다. git 공식 문서의 설명처럼 한 저장소에 작업 트리를 여럿 붙여서 한 번에 브랜치 여러 개를 체크아웃해 둘 수 있습니다. git worktree add가 새 폴더와 브랜치를 만들고, list로 목록을 보고, 끝나면 remove로 지웁니다. 터미널 예시는 문서의 문법을 따라 쓴 것이고 경로와 해시는 설명용입니다. 같은 브랜치를 이미 다른 워크트리가 쓰고 있으면 add가 거절됩니다. 두 곳에서 같은 브랜치를 건드리지 못하게 하는 안전장치입니다. 문서는 서브모듈이 있는 저장소의 다중 체크아웃은 아직 실험적이라고 경고합니다. 정리하면 장점은 오래 검증된 git 기능이라는 것, 단점은 환경 준비가 따로 필요하다는 것, 의미는 에이전트 병렬화의 해법이 새 발명이 아니라는 것입니다.

워크트리는 작업 중의 덮어쓰기를 막을 뿐, 합칠 때의 충돌은 막지 못합니다. 변경 범위를 미리 나누는 것이 가장 싼 해법입니다.

7단계: 실패하는 테스트 먼저, 막는 장치는 그다음

> 이슈 #2를 구현해. 순서를 지켜. 1. 먼저 시험을 써. 막는 장치가 아직 없으니 실패해야 해. 실패하는 걸 보여 주고 시험만 따로 커밋해. 2. 그다음 커밋된 시험 파일의 편집을 막아. 새 시험 파일과 구현 파일은 허용. 3. 막을 땐 이유가 너한테 돌아오게 해. 4. 끝나면 세 경우를 직접 돌려서 표로 보여 줘. 시험은 구현에 맞춰 고치지 마.

‘커밋된 테스트만’ 막아 새 테스트는 쓸 수 있다. 이유가 하네스에게 돌아가 스스로 방향을 바꾼다.
하네스가 명령 실행 안에서 스스로 파일을 여는 우회까지는 못 막는다. 샌드박스가 필요하고, 범위 밖에 명시했다.
시험만 먼저 커밋한 기록이 시험을 고쳐 통과시키지 않았다는 증거가 된다.
7단계 구현은 테스트부터입니다. 하네스에게 순서를 못 박아 시킵니다. 시험을 먼저 쓰고, 막는 장치가 없으니 실패하는 것을 보여 달라고 하고, 시험만 따로 커밋하게 합니다. 이 커밋이 나중에 시험을 고쳐 통과시키지 않았다는 증거가 됩니다. 구현이 끝나면 코드를 읽는 대신 세 경우를 직접 돌려 보게 합니다. 커밋된 시험 파일은 막히고, 새 시험 파일과 구현 파일은 허용되어야 합니다. 구현 파일까지 막히면 일이 멈추니 그것도 이 스모크로 잡힙니다. 오른쪽 대화는 예시입니다.

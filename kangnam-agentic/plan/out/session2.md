
### 5교시 · SDD·Plan 모드와 압축의 한계 (26장, 60분)
목표: 딴길로 새는 에이전트를 스펙·계획 파일로 붙잡고, 압축을 건너 살아남는 것은 디스크 파일뿐임을 설명하게 한다.
| 구간 | 장 | 분 | 꼭 짚을 말 |
| --- | --- | --- | --- |
| 열기·딴길 문제 | 1–3 | 4 | 승인을 줄여도 남는 문제: 시키지 않은 가정, 기록 없는 요구사항. Plan 모드(2025-06)·Kiro(07-14)·Spec Kit(09-02)·Cursor(10-07)는 같은 해 거의 동시 |
| 용어의 계보 | 4–5 | 6 | SDD(Spec-Driven Development, 스펙 주도 개발) 약어는 1987 IEEE(Institute of Electrical and Electronics Engineers, 전기전자공학자협회) 1016 Software Design Description(문서, 2020 비활성)에서 먼저 쓰였다. 2004 Ostroff 외 Agile Specification-Driven Development → MDD(Model-Driven Development, 모델 주도 개발)·BDD(Behavior-Driven Development, 행동 주도 개발) → 2025 Kiro·Spec Kit → 2025-10 Böckeler 세 수준. 5장 비교표: 읽는 쪽·스펙의 위상(참고용 도면 → 지켜야 할 계약)·검증·최신화·최종 자산. 가까운 조상은 TDD(Test-Driven Development, 테스트 주도 개발)·BDD |
| SDD 정의·세 수준 | 6–7 | 6 | Böckeler(2025-10-15): spec-first → spec-anchored → spec-as-source. 지금 도구는 대체로 첫째. 정의가 아직 유동적 |
| Kiro·Spec Kit | 8–13 | 10 | Kiro: requirements(EARS, Easy Approach to Requirements Syntax) → design → tasks. Spec Kit: constitution + spec → plan → tasks. 이름만 다르고 세 층 구조는 같다(13장 비교) |
| 질문 시간 | 14 | 5 | 질문 받기 |
| SDD의 한계 | 15 | 3 | 작은 버그가 스토리 4·수용 기준 16으로 부풂, 마크다운 리뷰 부담, 스펙이 있어도 가끔 지시 무시. 그래서 이슈 단위로 작게 |
| Plan 모드 | 16–18 | 8 | 읽기 전용 조사 → 계획 → 승인 선택지. Shift+Tab, Ctrl+G로 계획 편집. Cursor Plan Mode도 계획을 파일로 저장 |
| 강사 운영 방식 | 19–20 | 6 | 이슈 하나 단위로 스펙을 작게. 이슈 하나가 열두 단계(분석 → ADR(Architecture Decision Record, 아키텍처 결정 기록) 점검 → 스펙 → 리뷰 → 계획 → 리뷰 → 구현 → 리뷰 → PR(Pull Request, 병합 요청) → CI(Continuous Integration, 지속적 통합) → 스쿼시 머지 → 스모크). 스펙·계획·구현 세 번 리뷰, 블로커 없으면 종료, 예산 소진 시 중단 |
| 압축의 한계 | 21–25 | 9 | 자동 압축 2025-03-18(0.2.47). CLAUDE.md·Plan 모드 계획은 디스크에서 재주입, 읽은 파일은 최근 최대 5개. Context Rot(Chroma, 18개 모델). 진행 파일+기능 목록 JSON(2025-11-26). 세션 경계를 넘는 것은 파일뿐 |
| 정리 | 26 | 3 | 스펙이 붙잡고 파일이 남는다. 6교시 예고(스펙을 실패하는 테스트로) |

**주의 (흔한 오해)**
- 강의 순서(문제 → 해결)와 실제 날짜는 다르다. Plan 모드(2025-06)는 Kiro·Spec Kit보다 앞서고 자동 압축(2025-03)은 Plan 모드보다 앞선다. 슬라이드마다 날짜를 말하고 ‘같은 시기에 같은 문제를 푼 두 갈래’로 설명(3장).
- SDD는 오래된 개념에서 Plan 모드가 나온 것이 아니다. AI용 SDD 도구는 2025년 중반부터.
- SDD 약어는 두 뜻: 1987 IEEE 1016 Software Design Description(문서) / 2025 Spec-Driven Development(방식). 섞어 말하지 않는다.
- Spec Kit 명령 이름(10장)은 2026-10 README 기준이고 발표 당시 이름은 달랐다.
- “압축하면 결정 이유가 빠지기 쉽다”는 문서 문장이 아니라 요약이라는 방식에서 나온 추론. 문서가 직접 말한 것은 재주입 대상 표(22장).
- 창을 키워도 해결이 아니다(Context Rot, 23장). 1M 이야기는 3회차.
- 24장 진행 파일(claude-progress.txt)은 Anthropic 장기 하네스 글 기준. 8교시에 만들어 볼 진행 파일이 이것을 작게 줄인 것.

**예상 질문**
- “SDD 하면 스펙이 항상 좋은가요?” → 아니다. Böckeler도 작은 일엔 과하고 에이전트가 가끔 지시를 무시한다고 지적(15장). 그래서 이슈 단위로 작게.
- “Plan 모드와 Kiro 차이는?” → 앞은 도구 안 읽기 전용 계획, 뒤는 요구사항·설계·Task를 파일로 남김.
- “압축 대비는 어느 파일에?” → 맞는 동작=스펙, 어디까지 했나=계획, 왜 그렇게 정했나=진행 파일(26장).

**시연·준비**
- Plan 모드 진입(Shift+Tab)과 승인 화면을 실제로 한 번 보여 준다(16–17장). `/compact` 후 무엇이 남는지 시연 가능(22장).
- 학생 도구에 Plan/SDD 기능이 있는지 확인 안내(3장). 14장 질문 시간 5분 확보. 캡처 대기 장 없음.

### 6교시 · TDD와 DDD: 범위를 묶는 삼중 방어 (24장, 60분)
목표: 스펙·테스트·도메인 경계가 서로 다른 실패를 막음을 이해하고, 테스트 조작을 구조로 막는 법을 말하게 한다.
| 구간 | 장 | 분 | 꼭 짚을 말 |
| --- | --- | --- | --- |
| 열기·삼중 방어 | 1–3 | 4 | 스펙=딴길, 테스트=가짜 완료, 경계=범위 폭주를 막는다. 하나만 쓰면 나머지 실패가 남음 |
| TDD(Test-Driven Development, 테스트 주도 개발)와 Red 확인 | 4–7 | 10 | Beck 1990년대 후반, 테스트 → 최소 구현 → 정리. 분량 때문에 못 하던 TDD를 AI에게. 완료=통과 결과, 실행한 명령과 출력을 요구(6장). Red 이유가 규칙이어야 함(7장) |
| 속임수와 대응 | 8–11 | 10 | 고치기·skip·하드코딩. 초록불이어도 skipped=1. 대응 4겹: 테스트 먼저 커밋, deny·훅 차단, 리뷰어 서브에이전트, 사람이 직접 실행. 11장 권한 deny |
| 질문 시간 | 12 | 5 | 질문 받기 |
| 훅과 리뷰어 | 13–14 | 7 | 훅: 종료 코드 2로 차단+이유 전달. 리뷰어 서브에이전트: 스펙 기준, 스타일 지적은 건너뛰라 |
| DDD(Domain-Driven Design, 도메인 주도 설계) 기초 | 15–20 | 11 | 유비쿼터스 언어, 바운디드 컨텍스트(‘상태’가 영역마다 다름), 폴더만 나눈다고 경계가 아님. 에이전트에게 경계=볼 범위 축소 |
| 클린 아키텍처·수준 | 21–23 | 9 | 의존은 안쪽으로만. 프롬프트에 PoC(Proof of Concept, 개념 증명)/MVP(Minimum Viable Product, 최소 기능 제품) vs 클린 아키텍처를 적는다. 안 적으면 과잉 개발 |
| 정리 | 24 | 4 | 초록불인데 틀렸다면 테스트 변경·skip부터 확인. 7교시 예고, 8교시는 테스트 먼저 구현 |

**주의 (흔한 오해)**
- Claude Code 문서에 ‘TDD’ 별도 절은 없다. 근거는 프롬프트 예시(5장)와 ‘검증 수단 주기’(6장).
- Claude 4 발표의 “지름길·허점 65% 감소”는 취약한 에이전트 과제에서 Sonnet 3.7 대비이며, 사라졌다는 보장이 아니다(8장).
- 파일 경로 deny는 `Write(경로)`가 아니라 `Edit(경로)`로 써야 매칭된다. 슬라이드의 `tests/`는 예시 경로. Bash 우회 가능성이 있어 하나에 의존하지 않는다(11장).
- 훅은 종료 코드 2가 차단, stderr 메시지가 에이전트에 전달. 0이면 진행(13장). 스크립트 전체는 8교시에서 함께.
- 19장 공고·지원 기록·알림은 가정 예시. 용어집 방식(17장)은 원문이 아니라 강사 운영 방식.
- 클린 아키텍처 원문 도식은 로딩 실패로 본문 문단을 보여 줌(21장).
- 23장 파일 수·줄 수는 측정해 두지 않았으니 미리 말하지 않는다.

**예상 질문**
- “DDD를 꼭 해야 하나요?” → 복잡한 규칙의 도메인에 맞는 접근(16장). 간단한 앱은 PoC/MVP로 적으면 충분.
- “리뷰어가 자꾸 뭔가 찾아내요.” → “스펙 기준으로만, 스타일 지적은 건너뛰라”를 프롬프트에 넣는다(14장).
- “테스트를 먼저 커밋하는 이유는?” → 이후 변경이 git diff에 드러나 조작 증거가 된다(10장).

**시연·준비**
- 7·9장 unittest 예제를 직접 돌려 Red → Green, skip 한 줄 속임수 시연. 13장 훅 스크립트 동작 준비(8교시와 연결).
- 23장은 강사 Claude Code 화면 캡처 대기(plan/capture-todo.md에는 ‘p06 22장’으로 적혀 있으나 지금은 23장): 같은 요구사항을 PoC·클린 아키텍처 두 프롬프트로 실행한 파일 수·줄 수. 현재는 도식이므로 수업에서 두 번 시켜 그 자리에서 센다.
- 12장 질문 시간 5분 확보.

**주의 (흔한 오해)**

- 워크트리는 clone이 아니다. 같은 브랜치를 두 워크트리가 동시에 쓰면 add가 거절됨. 새 워크트리는 의존성·.env가 없어 환경 준비 필요(17장 .worktreeinclude).

- “같은 파일 동시 수정 금지”는 공식이 아니라 강사 운영 규칙(10장). 에이전트 팀·뷰는 이름만, 13교시에서.

### 8교시 · 실습 2 (14장, 60분)
목표: 하네스에게 질문부터 시켜, 메뉴로 소개한 딴길 방지 장치(끝내기 관문·테스트 보호·진행 파일·리뷰어 등) 중 내 하네스에 필요한 것을 골라 스펙 개요 → Task → 이슈로 정리하고, 이슈 하나를 이슈별 워크플로우 1–8단계로 처리한다. 코드는 읽지 않고, 프롬프트와 스모크(일부러 어겨 보기)로 확인한다. 18단계 중 8·13·14단계.
| 구간 | 장 | 분 | 꼭 짚을 말 |

**주의 (흔한 오해)**
- Stop 훅은 연속 8번 막으면 Claude Code가 막기를 넘긴다. `stop_hook_active` 확인으로 무한 반복 방지(10장).
- 보호 장치가 구현 파일까지 막으면 스모크의 “구현 파일 수정 → 허용”에서 잡힌다(9·14장). 코드는 읽지 않는다.
- 경계 조건(‘커밋된 것만 막는다’ 등)은 하네스 초안에 맡기지 말고 사람이 결정(5장).
- 축소하더라도 적용하지 않은 절차와 이유를 남기게 한다(7장). 개인 하네스는 마일스톤·스테이지·스프린트 이슈를 만들지 않고 Task 이슈만(5–6장).
- 블로커는 정확성에 영향 주는 것만. 나머지는 후속 이슈로, 리뷰 최대 2회(4·14장). 예산이 떨어졌는데 블로커가 남으면 통과시키지 않고 멈춰 인계(11장).
- 장치 구성(G1~G4, 이슈 #1~#4)은 강제가 아닌 메뉴·예시이고 내 하네스에 필요한 것을 고른다. 제 방식(18단계·이슈 워크플로우)도 ‘저는 이렇게 합니다, 바꿔도 됩니다’로 소개(1–3장). 설정만 있고 막힌 증거가 없으면 스모크로 다시 확인(12장). 화면 예시는 Claude Code 문법이고 다른 도구는 에이전트에게 자기 형식으로 써 달라고 한다.
- 9–12장의 스모크 대화·결과 값은 모두 예시로 진행한다.
- 못 끝낸 이슈는 열린 채 인계해도 괜찮음(13장).

**예상 질문**
- “리뷰가 끝나지 않아요.” → 블로커 기준과 최대 횟수를 정해 준다(14장).
- “구현 파일까지 막혀요.” → 스모크 결과를 보여 주며 “테스트 폴더의 커밋된 파일만 막게 고쳐”라고 다시 시킨다(14장).
- “스펙과 계획이 섞여요.” → 각각 무엇만 쓰라고 구분(14장). 스펙=맞는 동작, 계획=어디를 어떤 순서로(8장).
- “다음 시간에는 뭘 하나요?” → 쓴 프롬프트·스모크 표·막힌 곳을 나누는 것뿐(13장).

**시연·준비**
- 프롬프트와 스모크 결과는 슬라이드의 예시로 진행한다(사전 실행 불필요). 끝내기 관문은 실패·통과 두 상태를 스모크로 본다는 점만 짚는다.
- 설치·로그인 안내 없음. 질문 시간 장 없음 — 대화 중 수시로, 막히면 손들기(14장). 캡처 대기 장 없음.

Aider의 git 연동 문서. AI가 고칠 때마다 설명이 붙은 커밋을 만들고 /undo로 되돌린다.
저장소 전체를 지도 하나로 요약해 넘겨, 열지 않은 파일도 고려한다. 편집마다 커밋이 남아 되돌리기 쉽다.
편집 단위로 커밋이 쌓여 기록이 잘게 쪼개진다. 무엇을 실행하고 검증할지는 여전히 사람이 정했다.
터미널 + git을 에이전트의 작업 장부로 쓰는 방식의 원형. Claude Code 같은 도구가 이 방식을 이어받았다.
터미널에서 AI에게 저장소를 맡기는 방식은 Claude Code보다 먼저 있었습니다. Aider의 첫 릴리스는 2023년 6월 8일입니다. 문서에 따르면 Aider는 저장소 전체의 클래스와 함수를 요약한 지도를 모델에 보내고, 파일을 고칠 때마다 설명이 붙은 커밋을 만듭니다. 마음에 안 들면 undo 명령으로 되돌립니다. 변경 이력을 git에 맡긴다는 발상은 지금의 터미널 에이전트에도 그대로 이어집니다.

터미널 에이전트: 나와 같은 셸 권한

{{svg:ide-vs-terminal}}

터미널 에이전트는 내 셸 권한으로 내가 쓰던 git · 빌드 · 테스트 명령을 그대로 씁니다. 같은 권한이 곧 위험이기도 합니다.

IDE 확장은 편집기가 열어 준 API(Application Programming Interface, 응용 프로그램 인터페이스) 안에서만 움직입니다. 터미널 에이전트는 사용자의 셸에서 사용자와 같은 권한으로 git, 패키지 관리자, 테스트 러너를 그대로 씁니다. 그래서 고치고, 돌려 보고, 실패하면 다시 고치는 루프를 혼자 돌릴 수 있습니다. 반대로 말하면 에이전트가 사용자 계정으로 할 수 있는 일은 모두 할 수 있다는 뜻입니다. 이 장의 장점이 뒤쪽 장들의 문제가 됩니다.

터미널의 이점: 파이프와 CI에도 연결

code.claude.com/docs/en/headless
공식 문서 화면 캡처 · 2026-10-29 확인
Claude Code를 사람 없이 한 번 실행(-p)해 스크립트·CI에 넣는 방법. 다른 명령의 출력을 파이프로 받을 수도 있다.
$ git diff main | claude -p \ "오타만 파일:줄로 보고" $ claude -p "테스트 실패 고쳐 줘" \ --allowedTools "Bash,Read,Edit" ✓ 질문 없이 끝까지, 종료 코드 반환 ! 허용 도구를 미리 정해야 멈추지 않음
터미널의 또 다른 장점은 다른 명령과 이어 붙일 수 있다는 점입니다. 문서에는 p 옵션을 붙이면 비대화식으로 실행되고, 표준 입력으로 데이터를 받아 결과를 출력으로 내보낸다고 되어 있습니다. 빌드 스크립트나 CI(Continuous Integration, 지속적 통합)에도 넣을 수 있습니다. 다만 사람이 없으니 승인 창에 답할 수도 없습니다. 그래서 미리 허용할 도구를 정해 주어야 하고, 이것이 곧 권한 설정이라는 주제로 이어집니다. 화면의 명령은 문서 예시를 줄여 쓴 것입니다.
Claude Code 문서“How Claude Code works” · 에이전트 루프

에이전트 루프: 맥락 수집 → 행동 → 결과 확인

code.claude.com/docs/en/how-claude-code-works
공식 문서 화면 캡처 · 2026-10-29 확인
공식 문서의 에이전트 루프 도식. 프롬프트 → 맥락 수집 → 행동 → 결과 확인을 반복하고, 사용자는 끼어들 수 있다.
  1. 맥락 수집: 파일과 코드 검색
  2. 행동: 편집, 명령 실행
  3. 결과 확인: 테스트 출력 읽기

결과가 다음 판단의 입력이 됩니다. 사람은 언제든 끼어들 수 있습니다.

공식 문서는 에이전트의 작업을 세 단계로 설명합니다. 맥락을 모으고, 행동하고, 결과를 확인합니다. 이 단계들은 섞이고 반복됩니다. 버그 수정이라면 세 단계를 여러 번 돕니다. 중요한 것은 확인의 결과가 다시 다음 판단의 재료가 된다는 점입니다. 2교시에서 사람이 하던 오류 복사가 이 루프 안으로 들어온 셈입니다. 사람이 끼어들 수 있다는 점도 도식에 표시되어 있습니다.

에이전트의 행동 수단: 도구 다섯 범주

code.claude.com/docs/en/how-claude-code-works
공식 문서 화면 캡처 · 2026-10-29 확인
내장 도구 표. 파일·검색·실행·웹·코드 인텔리전스 다섯 범주별로 Claude가 할 수 있는 일.
  • 파일: 읽기 · 편집 · 생성
  • 검색: 패턴 · 정규식
  • 실행: 셸 명령, 테스트, git

도구 호출이 없으면 에이전트는 응답하고 멈춥니다.

문서는 내장 도구를 파일 작업, 검색, 실행, 웹, 코드 인텔리전스의 다섯 범주로 나눕니다. 이 도구들이 있어야 모델이 텍스트 응답을 넘어 실제로 행동할 수 있습니다. 모델이 도구를 부르면 그 결과가 돌아오고, 더 부를 도구가 없으면 응답하고 멈춥니다. 이 구조가 4교시에서 여러분이 만들 최소 루프의 뼈대입니다. 이 중 실행 범주가 가장 위험하다는 점만 짚어 둡니다.
직접 도식에이전트 루프와 멈춤 조건

루프 해부: 도구 호출이 끝날 때까지 반복

{{svg:p03-agent-loop}}

멈춤 조건은 “더 부를 도구가 없다”입니다. 계속 여부를 사람이 아닌 모델이 판단합니다.

방금 본 세 단계를 도구 이름과 함께 다시 그렸습니다. 프롬프트가 들어오면 검색 도구로 맥락을 모으고, 편집과 셸 도구로 행동하고, 테스트 결과를 읽어 확인합니다. 더 할 일이 있으면 다시 돌고, 도구 호출이 없으면 응답하고 멈춥니다. 사람이 하던 계속이 모델의 판단으로 옮겨 간 것입니다. 이 계속의 자동화는 9교시에서 더 길게 다룹니다. 사람의 끼어들기와 승인은 이 루프 바깥에서 들어옵니다.
재현 예시장바구니 합계 버그 맡기기 · 실제 출력 아님

버그 하나를 에이전트에게: 찾기 → 고치기 → 재시험

$ claude > 장바구니 합계가 틀려. 고쳐 줘 ● Bash(php artisan test --filter Cart) 1 failed: total expected 30000, got 33000 ● Grep("function total", app/) ● Read(app/Models/Cart.php) ● Edit(app/Models/Cart.php) ● Bash(php artisan test --filter Cart) 1 passed
  1. 테스트로 실패를 먼저 확인
  2. 검색하고 읽고 고친다
  3. 다시 돌려 통과를 확인

사람이 한 일은 문장 하나입니다. 대신 각 ●마다 승인 질문이 따라옵니다.

2교시에서 채팅창에 붙여넣던 것과 같은 종류의 버그를 터미널 에이전트에게 맡긴 모습을 재현했습니다. 실제 출력이 아니라 흐름을 보여 주기 위한 예시입니다. 에이전트는 테스트를 먼저 돌려 실패를 확인하고, 코드를 찾아 읽고, 고친 뒤 다시 돌려 통과를 확인합니다. 사람이 한 일은 문장 하나뿐입니다. 이때 도구 호출마다 허락을 구하면 어떻게 될까요. 바로 이어지는 승인 피로의 출발점입니다.
Claude Code 문서세션 기록은 로컬 JSONL(JSON Lines) 파일

도구 호출 기록으로 에이전트 점검

호출무엇을 알려 주나확인할 것
Bash(테스트)실패 상태와 오류 메시지실제로 실패했는가
Grep · Read어떤 파일을 근거로 삼았나엉뚱한 파일을 보지 않았는가
Edit어디를 얼마나 바꿨나범위를 넘지 않았는가
Bash(재실행)통과 여부테스트를 고쳐서 통과시키지 않았는가

각 메시지·도구 호출·결과는 평문 JSONL(한 줄에 기록 하나)로 ~/.claude/projects/ 아래에 저장됩니다. 4교시 실습에서 확인할 때 쓸 수 있습니다.

공식 문서에 따르면 Claude Code는 각 메시지와 도구 호출, 결과를 평문 JSONL(JSON Lines, 한 줄에 JSON 하나씩) 파일로 로컬에 저장합니다. 그래서 에이전트가 무엇을 했는지 나중에 읽을 수 있습니다. 읽을 때는 표처럼 호출 종류별로 질문을 던져 봅니다. 특히 마지막 줄이 중요합니다. 에이전트가 테스트를 고쳐서 통과시킨 것은 아닌지 보는 일은 6교시에서 다시 다룹니다. 4교시에서는 필요하면 이 기록을 열어 에이전트가 한 일을 확인해 봅니다.

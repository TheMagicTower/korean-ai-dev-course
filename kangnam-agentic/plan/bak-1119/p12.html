하네스 v2:
워크플로는 스킬로, 이슈는 /goal로

12교시는 실습입니다. 도구 설치와 로그인은 하지 않고, 각자 쓰던 에이전트를 그대로 씁니다. 지난 회차에는 이슈 하나를 스펙, 계획, 구현, 리뷰 순서로 에이전트와 처리했습니다. 오늘은 그 순서를 스킬 하나로 포장하고, 이슈마다 작업 공간을 나누는 규칙을 정하고, 외부 도구 하나를 연결한 뒤, 이슈 하나를 완료 조건까지 통째로 맡깁니다. 이번에도 설정 파일은 여러분이 손으로 쓰지 않습니다. 에이전트에게 질문부터 시켜서 만들고, 여러분은 답하고 승인하고 시험합니다.
약 55분18단계 중 15단계(워크플로·워크트리 설정) · 이슈별 워크플로우 1–8단계를 스킬로

오늘도 프로세스는 같다: 질문 → 설계 승인 → 구현 → 시험, 그리고 /goal로 이슈 하나

{{svg:p12-flow}}

여러분이 할 일은 설정 파일을 치는 것이 아니라 질문에 답하고, 설계를 승인하고, 스킬이 정말 불리는지 시험하는 것입니다.

오늘은 제 운영 기준 18단계 가운데 15단계, 작업을 어떻게 격리하고 합칠 것인가를 하네스 크기로 줄여 적용합니다. 먼저 에이전트가 격리, 리뷰, 머지 규칙과 스킬, MCP, 완료 조건에 대해 질문하고 여러분이 답합니다. 에이전트는 답을 ADR 한 건과 스킬 설계로 정리하고, 여러분이 읽고 승인한 뒤에야 구현합니다. 구현 뒤에는 스킬이 불리는지, MCP가 연결되는지 확인하고, 마지막으로 이슈 하나를 /goal로 맡깁니다. 설계 대화 12분, 승인 8분, 구현 10분, 시험 10분, 이슈 완주 15분 정도로 잡습니다.
이슈별 워크플로우 1–8단계11교시 스킬 · 목록에는 이름과 설명만 먼저 올라감

지난 시간에 매번 말로 시킨 순서가 스킬 후보다

  • 이슈 분석 → ADR 점검 → 스펙 → 스펙 리뷰 → 계획 → 계획 리뷰 → 구현 → 구현 리뷰를 이슈마다 다시 설명했다
  • 같은 설명을 세 번 쓰면 후보. 한 스킬 = 한 작업
  • 스킬의 본문은 필요할 때만 읽힌다. 설명 문장이 호출을 좌우한다

8교시에 이슈 하나를 처리하면서 에이전트에게 스펙을 쓰라고 하고, 리뷰하라고 하고, 계획을 세우라고 하고, 구현하라고 했습니다. 이슈가 열 개면 같은 설명을 열 번 하게 됩니다. 이런 반복이 스킬로 만들 후보입니다. 도식처럼 세션이 시작되면 스킬의 이름과 설명만 목록에 올라가고, 요청이 설명과 맞을 때 본문을 읽습니다. 그래서 설명 문장을 잘 쓰는 것이 중요합니다. 이 스킬도 여러분이 쓰지 않고 에이전트에게 설계 대화를 거쳐 쓰게 합니다.
그대로 붙여 넣어도 됩니다각자 쓰는 에이전트(Claude Code · Codex · Gemini CLI · Cursor …)

첫 프롬프트: 코드 전에 질문을 하나씩 하고, 설계는 ADR로 남기라고 한다

> 내 하네스 저장소(메모 앱 PoC)에 ① 이슈마다 격리할 워크트리·브랜치·리뷰·머지 규칙, ② 지난주 이슈별 1–8단계를 하나의 issue-flow 스킬, ③ MCP 서버 하나를 더하고 싶다. 아직 파일은 만들지 마. 필요한 질문을 한 번에 하나씩, 네 추천 답과 이유를 같이 주고 8개 안에서 끝내. 끝나면 docs/adr/0003-workflow.md와 스킬·MCP 설계 요약을 쓰고 내가 “승인”이라고 할 때까지 기다려.

Claude Code 문서의 ‘공통 워크플로’. 목차에 워크트리로 병렬 세션을 돌려 동시 수정이 충돌하지 않게 하는 절이 있다.
4교시와 같은 방식의 프롬프트입니다. 아직 파일을 만들지 말 것, 질문은 한 번에 하나씩 추천 답과 함께, 정리한 설계는 제가 승인할 때까지 기다릴 것, 이 세 가지를 못 박습니다. 이번에는 결정할 것이 세 묶음입니다. 이슈를 어떻게 격리하고 합칠지, 이슈별 순서를 어떤 스킬로 만들지, 어떤 외부 도구를 붙일지입니다. 결과는 새 ADR 한 건으로 남깁니다. 4교시에 만든 문서가 있으면 에이전트가 먼저 읽도록 저장소 안에서 시키면 됩니다. 오른쪽은 워크트리를 설명하는 공식 문서 화면입니다.
설계 대화 체크리스트15단계 + 스킬 · MCP · /goal · 에이전트가 묻지 않으면 내가 먼저

에이전트가 물을 질문은 격리, 리뷰, 스킬, MCP, 완료 조건에 걸쳐 있다

주제에이전트가 물을 것예시 답빠지면
15 격리이슈 하나를 어디서 작업하나이슈마다 워크트리 + issue/번호 브랜치두 이슈가 한 폴더에서 섞인다
15 충돌같은 파일을 건드리는 이슈는한 번에 하나, 공유 파일은 이슈에 미리 적음합칠 때 뒤늦게 충돌
15 리뷰·머지누가 리뷰하고 언제 합치나리뷰어 서브에이전트, 머지는 사람 승인(16교시)쓴 쪽이 스스로 통과시킨다
스킬순서와 멈춤을 어디까지 담나1–8단계, 블로커 없으면 종료, 예산 소진 시 인계이슈마다 말로 다시 설명
MCP어떤 외부 정보가 필요하고 믿을 만한가라이브러리 문서 서버 1개, 읽기만, 비밀 없음쓸모없는 도구, 주입·토큰 낭비
/goal어느 이슈를 어떤 끝 상태까지, 상한은이슈 하나, 테스트 통과 + 블로커 0, 20턴조건이 모호해 헛돈다
기록무엇을 남기나시간·턴·토큰·성공/실패다음 회차의 근거가 없다
설계 대화가 잘 됐는지 보는 기준입니다. 15단계의 핵심은 작업을 어떻게 격리하고 어떻게 합치는가입니다. 격리, 충돌, 리뷰와 머지 세 줄이 여기에 해당합니다. 나머지 네 줄은 오늘 더할 장치인 스킬, MCP, /goal, 기록입니다. 에이전트가 일부를 묻지 않으면 여러분이 먼저 꺼내 봅니다. 모르는 항목은 선택지 두 개와 장단점을 표로 달라고 하면 됩니다. 머지와 PR 규칙은 오늘은 정하기만 하고, 실제로 PR을 만들고 머지하는 일은 4회차에서 합니다.
15단계 결과 예에이전트가 쓴 ADR의 모양 · 직접 칠 필요 없음 · 검토할 곳 ①–④

15단계의 결과물은 ADR 한 건과 워크트리 규칙이다

# docs/adr/0003-workflow.md (15단계) 결정 이슈 하나 = 브랜치 하나 = 워크트리 하나 # ① 대안 한 폴더에서 차례로 / 이슈마다 저장소 복제 이유 두 이슈를 동시에 열어도 파일이 섞이지 않는다 규칙 같은 파일을 건드릴 이슈는 한 번에 하나 # ② 구현 리뷰는 리뷰어 서브에이전트가 한다 # ③ PR·머지는 사람 승인 뒤, 4회차(16교시)에 # ④ 다시 판단할 조건 두 이슈가 같은 파일에서 충돌하면 # 에이전트가 쓴 워크트리 명령의 예 $ git worktree add ../harness-wt/issue-12 -b issue/12-sort $ git worktree list $ git worktree remove ../harness-wt/issue-12 # 끝난 뒤
이슈마다 폴더가 나뉘어, 한 이슈를 하는 동안 다른 이슈의 변경이 섞이지 않는다. 4회차의 병렬 실행의 바탕이 된다.
폴더마다 의존 설치가 필요하고 디스크를 더 쓴다. 겹치는 파일은 여전히 합칠 때 충돌한다.
15단계의 질문 ‘작업을 어떻게 격리하고 합치는가’에 대한 답. 결정과 이유가 ADR에 남아 다음 판단의 기준이 된다.
에이전트가 정리한 ADR의 예입니다. 직접 쓸 필요는 없고 검토할 곳 네 군데를 봅니다. 첫째, 이슈와 브랜치와 워크트리가 하나씩 대응하는가. 둘째, 같은 파일을 건드리는 이슈를 어떻게 다루는가. 셋째, 리뷰를 구현한 쪽이 아닌 다른 서브에이전트가 하는가. 넷째, 머지를 사람 승인 뒤로 미루었는가. 아래 명령은 에이전트가 이슈마다 실행하는 워크트리 명령의 예입니다. 마지막 줄의 다시 판단할 조건은 4교시 ADR과 같은 서식입니다.
승인 체크리스트다섯 가지가 다 ‘예’일 때만 “승인”

승인 전에 다섯 가지만 확인한다

  1. 이슈 하나에 브랜치·워크트리 하나가 대응하고, 겹칠 때의 규칙이 있다
  2. 스킬의 description이 쓰이는 상황을 앞에 적었고, PR·머지는 스킬 밖이다
  3. 멈춤: 블로커가 없으면 종료, 예산이 소진되면 통과가 아니라 중단·인계
  4. MCP는 믿을 서버 하나이고 비밀 값은 환경 변수 이름으로만 적혔다
  5. /goal 조건에 끝 상태·증명 방법·상한이 있고, 구조를 30초 안에 설명할 수 있다
검토할 곳이 다섯 군데로 줄어, 문서 세 개(ADR·스킬·MCP 설정)를 빨리 읽을 수 있다.
체크리스트에 없는 위험(예: 서버가 가져오는 글의 프롬프트 주입)은 놓칠 수 있다. 낯선 항목은 에이전트에게 위험을 따로 묻는다.
에이전트가 쓰고 사람이 판정하는 분업. 4교시 승인과 같고, 이번에는 대상이 스킬·MCP·완료 조건이다.
4교시와 같은 방식으로 승인 전에 다섯 가지를 봅니다. 격리 규칙이 있는지, 스킬 설명이 쓰이는 상황을 앞에 적었는지, 멈춤 조건에서 예산이 떨어졌을 때 통과시키지 않고 중단하고 넘기게 되어 있는지, MCP가 하나뿐이고 비밀이 파일에 없는지, 완료 조건에 상한이 있는지입니다. 마지막 항목처럼 내가 이 구조를 30초 안에 설명하지 못하면 승인하지 않고 더 단순하게 바꿔 달라고 합니다. 승인은 사람만 합니다. 에이전트가 쓴 설계를 한 곳은 직접 고치게 해 봅니다.
이슈별 워크플로우 1–8단계에이전트가 쓴 SKILL.md의 모양 · 검토할 곳 ①–④

스킬을 검토할 때는 설명 문장과 멈춤 규칙부터 본다

# .claude/skills/issue-flow/SKILL.md (Codex는 .agents/skills/issue-flow/) --- description: GitHub 이슈 하나를 스펙→계획→구현→리뷰까지 처리한다. “이슈 12 처리해 줘”, 이슈 번호가 주어질 때 사용. # ① --- ## 이슈 !`gh issue view $ARGUMENTS` ## 순서 (블로커가 없으면 다음 단계, 있으면 그 단계 반복) 1 이슈 분석 2 ADR 점검 3 이슈 스펙 4 스펙 리뷰 5 구현 계획 6 계획 리뷰 7 구현(테스트 먼저) # ② 8 구현 리뷰 = 리뷰어 서브에이전트에게 맡긴다 ## 멈춤 예산이 소진되고 블로커가 남으면 통과시키지 말고 # ③ docs/progress.md에 적고 중단한다 ## 하지 않는 것 PR 생성·머지 (사람 승인 뒤, 4회차) # ④
8교시에 말로 시키던 순서가 파일 하나가 되어, 이슈마다 같은 순서와 같은 멈춤으로 돈다.
description이 나쁘면 아예 안 불린다. 본문이 길어지면 지침이 흐려지니 500줄 이내로 두고 자료는 따로 뺀다.
이슈별 워크플로우를 재사용 가능한 자산으로 만든 것. 같은 SKILL.md 형식을 Claude Code와 Codex가 모두 읽는다.
에이전트가 쓴 스킬의 예입니다. 검토할 곳은 네 군데입니다. 첫째, description이 쓰이는 상황과 여러분이 실제로 할 말을 앞쪽에 담았는가. 맨 위 메타데이터 블록은 파일 첫 줄부터 시작해야 합니다. 둘째, 구현을 테스트 먼저로 하는가. 셋째, 예산이 떨어졌는데 블로커가 남았을 때 통과시키지 않고 멈추는가. 넷째, PR과 머지는 스킬 밖에 두었는가. 느낌표와 백틱 줄은 스킬이 실행될 때 명령 결과를 본문에 채워 넣는 기능으로, 여기서는 이슈 본문을 읽어 옵니다. Codex는 같은 형식을 저장소의 점에이전트 스킬 폴더에서 읽습니다.
MCP 서버 하나Claude Code는 명령 한 줄, Codex는 config.toml · 에이전트가 만든 결과의 예

MCP를 검토할 때는 서버를 믿을 수 있는지, 비밀이 새지 않는지부터 본다

# Claude Code (프로젝트 범위 → .mcp.json, 팀과 공유) $ claude mcp add --scope project context7 \ -- npx -y @upstash/context7-mcp # ① 어떤 서버 $ claude mcp list > /mcp # 세션 안에서 상태 확인 # Codex (~/.codex/config.toml) [mcp_servers.context7] command = "npx" args = ["-y", "@upstash/context7-mcp"] [mcp_servers.figma] # 원격 서버 예 url = "https://mcp.figma.com/mcp" bearer_token_env_var = "FIGMA_OAUTH_TOKEN" # ② 값이 아닌 이름 # 선택: startup_timeout_sec = 20 ③ 시간 초과
문서 조회 도구(예: Context7) 같은 외부 도구를 설정만으로 더해, 에이전트가 최신 라이브러리 문서를 보고 이슈를 분석한다.
서버가 가져오는 글에 프롬프트 주입 위험이 있고, 도구 설명이 토큰을 쓴다. 프로젝트 범위 서버는 처음 쓸 때 승인을 묻는다.
도구를 늘리는 일도 사람이 판정한다. 이슈 분석(1단계)에서 쓰는 정보원 하나만 연결한다.

검토 ① 어느 서버·어느 범위인가 ② 토큰은 환경 변수 이름뿐인가 ③ 연결 확인(목록·/mcp)을 했는가. 이슈 읽기에는 GitHub용 서버도 후보입니다(주소·인증은 자기 도구 문서로 확인).

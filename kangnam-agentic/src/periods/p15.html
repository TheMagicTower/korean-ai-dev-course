해법: 결정은 ADR, 할 일은 이슈, 동작은 코드·테스트에

{{svg:p14-where-things-live}}

결정과 이유는 ADR(저장소에 결정 하나씩), 할 일은 이슈(작업을 계획·추적), 실제 동작의 기준은 코드와 테스트(예시로 쓴 명세).

해법은 스펙을 없애는 것이 아니라 성격에 따라 나눠 두는 것입니다. Nygard와 Fowler는 결정 하나를 짧은 기록으로 코드 저장소에 두고, 결정이 바뀌면 고쳐 쓰지 말고 새 기록으로 대체하라고 합니다. GitHub 문서는 이슈를 작업을 계획하고 논의하고 추적하는 곳으로 설명하고, 큰 일은 하위 이슈로 쪼개게 합니다. 실제로 어떻게 동작해야 하는지는 Fowler가 예시에 의한 명세, Specification By Example이라고 부른 테스트가 맡고, 테스트는 코드와 함께 실행되므로 어긋나면 실패로 드러납니다. 이렇게 나누면 오래 가는 결정, 끝나면 닫히는 작업, 늘 실행되는 기준이 각자 제자리를 갖습니다. 병렬 에이전트도 서로 다른 이슈와 ADR 파일을 만지게 되어 한 파일에서 부딪히는 일이 줄어듭니다.

결정 근거 기록은 1992년, ‘ADR’ 이름은 2011년부터

{{svg:p14-adr-lineage}}

ADR(Architecture Decision Record, 아키텍처 결정 기록) = 결정 하나와 그 근거. 무거운 아키텍처 문서에서 떼어 낸 작은 기록이다.

ADR도 새 말이 아닙니다. 1992년 Perry와 Wolf는 소프트웨어 아키텍처를 요소, 형태, 그리고 근거, rationale로 정의했습니다. 왜 그렇게 했는지가 처음부터 아키텍처의 일부였던 셈입니다. 2005년 IEEE Software에 Tyree와 Akerman이 아키텍처 결정을 문제, 결정, 가정, 제약, 대안 같은 칸으로 적는 서식을 냈고, 같은 해 Jansen과 Bosch는 아키텍처를 설계 결정의 집합으로 봤습니다. 2011년 ISO/IEC/IEEE 42010, 곧 국제표준화기구 ISO(International Organization for Standardization), 국제전기기술위원회 IEC(International Electrotechnical Commission), 전기전자공학자협회 IEEE(Institute of Electrical and Electronics Engineers)가 함께 낸 아키텍처 기술 표준은 결정과 근거를 아키텍처 기술의 표준 항목으로 넣었습니다. 여기까지는 큰 아키텍처 문서 안의 한 부분이었습니다. 같은 2011년 11월 15일 Michael Nygard가 ‘Documenting Architecture Decisions’에서 큰 문서는 아무도 최신으로 유지하지 않는다며, 다섯 칸짜리 짧은 기록을 코드 저장소에 두자고 제안합니다. 이것이 지금 말하는 ADR입니다. Thoughtworks 기술 레이더는 2016년 11월 시도, 2017년 11월 도입 단계로 올렸고, 2018년 MADR이 마크다운 서식을 정리했습니다. 그리고 지금은 에이전트가 이 기록을 지켜야 할 규칙으로 읽습니다.

Nygard의 ADR 원형: 다섯 칸, 한두 쪽 분량

cognitect.com/blog/2011/11/15/documenting-architecture-decisions
원문 화면 캡처 · 2011-11-15
Nygard 글에서 Status(상태)와 Consequences(결과) 칸을 설명하는 부분.
  1. Title(제목): 짧은 명사구
  2. Status(상태): 제안됨 · 승인됨 · 폐기 · 대체됨
  3. Context(맥락): 힘겨루기 중인 사실들
  4. Decision(결정): “We will …”(우리는 ~한다)
  5. Consequences(결과): 좋은 것도 나쁜 것도
다섯 칸, 한두 쪽이면 끝난다. 상태를 바꿔 결정의 역사가 남는다.
대안을 적는 전용 칸이 없다(13장 표). 낡음을 알리는 조건 칸도 없다.
모든 서식의 뼈대. AI 이전인 2011년부터 ‘작은 문서’를 주장했다.
Nygard가 제안한 형식은 다섯 칸뿐입니다. 제목은 짧은 명사구, 상태는 제안됨이나 승인됨, 그리고 나중에 폐기되거나 다른 ADR로 대체됨으로 바뀝니다. 맥락은 긴장 관계에 있는 기술적, 정치적, 사회적 사실을 값을 매기지 않고 적는 칸입니다. 결정은 우리는 이렇게 한다는 능동형 문장으로, 결과는 긍정적인 것뿐 아니라 부정적인 것과 중립적인 것까지 전부 적습니다. 문서 전체는 한두 쪽을 넘기지 말고, 미래의 개발자와 대화하듯 쓰라고 합니다. 파일은 저장소의 doc/arch 아래에 adr-번호.md로 두고 번호는 다시 쓰지 않습니다.

상태는 바꾸되 기록은 보존

{{svg:p14-adr-status}}

낡은 ADR을 고쳐 쓰지 않고 상태만 바꾸고 새 ADR을 추가합니다. 그때 무엇이 결정이었는지가 남습니다.

Nygard는 결정이 뒤집히면 옛 ADR을 지우지 않고 대체됨으로 표시해 두라고 합니다. 그때는 그것이 결정이었다는 사실이 여전히 의미가 있기 때문입니다. 번호도 순서대로 매기고 다시 쓰지 않습니다. 이 방식은 스펙과 정반대입니다. 스펙은 계속 덮어써서 최신 상태만 남기지만, ADR은 결정의 역사를 쌓습니다. 에이전트가 현재 유효한 결정만 읽게 하려면 상태 칸이 승인됨인 것만 읽도록 하면 됩니다.

GitHub Docs 캐시 문서. 호스티드 러너는 매번 깨끗한 이미지에서 시작해 의존성을 다시 받으므로, 캐시로 재사용한다.
# PHP · Laravel 예: composer 캐시 - uses: actions/cache@v4 with: path: ~/.composer/cache key: composer-${{ hashFiles('composer.lock') }} - run: composer install ✓ lock 파일이 같으면 다운로드 생략 ! 캐시는 재사용일 뿐, 검사 생략이 아님 ! 비밀정보는 캐시하지 않는다

캐시는 재사용일 뿐 검사 생략이 아니다. 비밀정보는 캐시하지 않고, 설치가 짧으면 효과가 작다.

호스티드 러너는 매번 깨끗한 이미지에서 시작하므로 의존성을 매번 내려받습니다. 문서가 설명하듯 이 반복이 네트워크와 실행 시간, 비용을 늘립니다. 의존성 캐시는 lock 파일 해시를 키로 삼아 같은 의존성을 재사용합니다. PHP와 Laravel이라면 composer 캐시가 첫 후보입니다. 지킬 것은 캐시와 결과 아티팩트를 구분하는 것입니다. 캐시를 지워도 빌드가 재현돼야 합니다. 다른 하나는 테스트 결과를 캐시해서 코드가 바뀌었는데 검사를 건너뛰는 일을 만들지 않는 것입니다. 작은 프로젝트는 먼저 측정하고, 설치가 실제로 오래 걸릴 때 도입합니다.

4. 묶어서 검증: 머지 큐

docs.github.com/…/managing-a-merge-queue
GitHub Docs 화면 캡처
GitHub Docs 머지 큐 문서. 머지 큐는 PR 머지를 줄 세우고, 합친 상태로 먼저 검사하는 기능.
합친 상태로 먼저 검사해 main이 깨지는 일을 머지 전에 막고, 브랜치를 매번 최신으로 맞추지 않아도 된다.
실패가 잦거나 러너가 부족하면 대기가 오히려 늘고, 충돌 해결·검토는 대신하지 않는다. 제공 범위도 제한된다.
PR이 몰려도 기본 브랜치를 항상 초록으로 지키는 4단계 최종 수단. 앞 단계를 켠 뒤에 쓴다.
머지 큐는 2023년 7월 12일 정식 출시됐습니다. 문서의 설명대로 바쁜 브랜치에서 호환되지 않는 변경 때문에 브랜치가 깨지는 일을 막아 줍니다. 필수 검사를 통과한 PR을 큐에 넣으면 GitHub이 기본 브랜치의 최신 상태와 앞선 PR들을 합친 임시 후보를 만들어 검사하고, 통과하면 병합합니다. 사람이 매번 브랜치를 최신으로 맞추고 다시 기다리는 일이 사라집니다. 제공 범위는 조직 소유 공개 저장소와 Enterprise Cloud 조직의 비공개 저장소이므로, 적용 전에 확인합니다.

머지 큐의 검사 단위: ‘누적 후보’

{{svg:p15-mq}}

PR 하나의 성공은 후보의 성공이 아닙니다. 실패한 PR이 빠지면 뒤 후보는 다시 검사합니다.

큐는 누적으로 돕니다. A, B, C가 줄을 서 있으면 먼저 main에 A를 얹은 후보, 그 위에 B를 얹은 후보, 그 위에 C를 얹은 후보를 차례로 만들어 검사합니다. 각 PR이 따로 통과했더라도 합쳤을 때 깨지는 경우를 머지 전에 잡습니다. B가 실패하면 B는 큐에서 빠지고, B를 포함했던 뒤 후보는 B 없이 다시 만들어 검사합니다. 그래서 실패가 잦으면 오히려 대기가 늘 수 있습니다. 러너가 부족해도 마찬가지입니다. 큐는 충돌을 해결해 주는 도구도, 검토를 대신하는 도구도 아닙니다.

GitLab Docs 문서. MR(Merge Request, 머지 요청)을 줄 세워 앞선 MR과 합친 상태로 검사한다는 설명.

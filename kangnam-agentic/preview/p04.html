내 하네스의 첫 버전:
에이전트에게 설계부터 맡기기

4교시는 실습입니다. 도구 설치는 각자 알아서 해 두신 것으로 하고, 오늘은 설치 없이 진행합니다. 이미 각자 쓰는 에이전트가 있으니 그것을 그대로 씁니다. 오늘은 5회차까지 키워 갈 ‘나만의 하네스’의 첫 버전을 만듭니다. 어떤 기능과 스펙의 하네스인지, 어떤 형태인지는 각자 정합니다. 정해진 구성은 없습니다. 소개하고 싶은 것은 만드는 방법입니다. 하네스도 에이전트에게 시켜서 만들고, 저는 그 코드를 읽지 않습니다. 대신 에이전트가 먼저 묻게 하고, 만든 뒤에는 실제로 돌려 확인합니다. 이 과정에서 소개하는 일하는 방식을 하네스를 만드는 데에도 그대로 씁니다.
약 55분18단계 중 1–7단계를 개인 PoC(Proof of Concept, 개념 증명) 크기로 · 각자 쓰던 에이전트 그대로

하네스 제작 과정: 분석 → 개요·ADR → 승인 → 구현 → 스모크

사람이 하는 일은 코드를 읽는 것이 아니라 질문에 답하고, 설계를 승인하고, 스모크 결과를 보는 것입니다. 강사 방식이며, 자기 방식대로 바꿔도 됩니다. ADR(Architecture Decision Record, 아키텍처 결정 기록)은 결정과 이유를 짧게 남긴 문서입니다.

오늘 실습은 제가 쓰는 프로세스를 소개하고 따라 해 보는 시간입니다. 제 운영 기준 18단계 가운데 앞의 1~7단계, 즉 프로젝트 분석, 시나리오, 입출력, 개요, 가이드라인, ADR(Architecture Decision Record, 아키텍처 결정 기록)을 개인 PoC(Proof of Concept, 개념 증명) 크기로 줄여서 하네스에 적용합니다. 먼저 에이전트가 분석에 필요한 질문을 하고 여러분이 답합니다. 에이전트는 답을 개요 문서와 첫 ADR로 정리합니다. 여러분이 그 문서를 읽고 승인한 뒤에야 에이전트가 구현합니다. 코드는 열어 보지 않고, 만들어진 v0을 실제로 돌리는 스모크로 확인합니다. 작은 과제를 한 번 시키고, 금지한 일을 일부러 시켜서 정말 막히는지 보고, 막힌 것까지 기록합니다. 설계 대화 15분, 설계 검토와 승인 10분, 구현 지시 5분, 스모크와 기록 25분 정도로 잡습니다.
네 번의 실습 순서강사 운영 기준 18단계 · 저위험 개인 도구는 1–8단계를 짧은 개요 하나로

네 번의 실습: 하나의 에이전틱 엔지니어링 프로세스

하네스를 만드는 일 자체가 이 과정의 프로세스를 연습하는 시간입니다. 강사 방식을 소개하는 것이고, 강제하지 않습니다.

네 번의 실습이 따로 노는 것이 아닙니다. 제가 실제 프로젝트에 쓰는 18단계 운영 기준을 하네스라는 작은 개인 프로젝트에 맞게 줄인 것입니다. 오늘은 1~7단계로 분석하고 개요와 ADR을 씁니다. 다음 주에는 스펙을 Task와 이슈로 나누고, 이슈 하나를 스펙, 계획, 구현, 리뷰 순서로 처리합니다. 3회차에는 워크트리와 워크플로우를 정하고 스킬과 MCP(Model Context Protocol, 모델 컨텍스트 프로토콜), /goal로 이슈를 끝까지 맡깁니다. 4회차에는 PR(Pull Request, 병합 요청), CI(Continuous Integration, 지속적 통합), 스모크, 피드백, 다음 루프까지 갑니다. 저위험 개인 도구에서는 1~8단계를 짧은 개요 하나로 합쳐도 된다는 것이 제 기준입니다. 이 흐름은 제가 쓰는 방식이고, 각자 바꿔도 됩니다.

  • 멈춤 조건과 금지 목록이 설계에 들어간다
  • 결정과 이유가 개요·ADR에 남는다
  • 나중에 공유할 때 구조를 내 말로 설명할 수 있다
에이전트에게 하네스를 만들어 달라고만 하면 대개 바로 코드를 씁니다. 그 순간 비어 있던 결정들, 어떤 모델을 쓸지, 어떤 도구를 줄지, 언제 멈출지, 무엇을 금지할지가 전부 에이전트의 가정으로 채워집니다. 결과물은 그럴듯하지만 왜 그렇게 생겼는지 여러분이 설명하지 못합니다. 반대로 질문부터 시키면 같은 결정을 여러분이 내리게 됩니다. 1교시에서 PoC라고 명시한다고 말씀드린 것, 11교시에서 볼 grill-me 스킬이 바로 이 생각입니다.
설계 질문 표강사 질문 순서(예) · 4단계(마켓 인사이트)는 개인 도구라 생략 · 하네스의 기능은 내가 결정

분석 대화: 1–7단계 여섯 질문에 하나씩 답하기

18단계 중에이전트가 물을 것예시 답빠지면
1 분석누가 어떤 일에 쓰나나, 메모 앱의 작은 수정범위가 끝없이 넓어진다
2 시나리오정상·실패 예 하나씩정렬 옵션 추가 / 테스트 실패 시 중단무엇이 성공인지 모른다
3 입출력입력과 기대 출력, 성공 판정과제 문장 → 변경 + pytest 통과“된 것 같다”로 끝난다
5 개요수준과 범위, 제외할 것PoC, 파일 3개, UI(User Interface, 사용자 화면) 없음과잉 설계
6 가이드라인트랙·모델·도구·비용에이전트 추천 방식, 읽기·수정·실행, 하루 예산비용 폭주, 할 수 없는 일 시도
7 ADR권한·멈춤 같은 되돌리기 비싼 결정금지 3개, 완료+20바퀴+예산3교시의 사고 사례
분석 대화가 잘 됐는지 보는 기준입니다. 18단계 중 1~7단계의 질문을 하네스 크기로 줄였고, 4단계 시장 분석은 개인 도구라 뺐습니다. 이 여섯 줄이 다 정해졌으면 충분합니다. 표의 답은 모두 예시이고, 무엇을 하는 하네스인지는 각자 정합니다. 에이전트가 이 중 일부를 묻지 않으면 제가 먼저 꺼냅니다. 특히 7단계의 권한과 멈춤 조건은 3교시에서 본 사고 사례와 승인 피로로 바로 이어집니다. 어떤 방식으로 만들지도 에이전트가 추천하게 하고 저는 이유만 읽습니다. 모르는 항목은 에이전트에게 선택지 두 개와 장단점을 달라고 하면 됩니다.
그대로 붙여 넣기 가능각자 쓰는 에이전트(Claude Code · Codex · Gemini CLI(Command-Line Interface, 명령줄 인터페이스) · Cursor …)

첫 프롬프트: ‘코드 전에 질문부터, 하나씩’ 지시

> 내가 원하는 기능(예: 메모 앱, PoC)에 쓸 작은 코딩 에이전트 하네스를 만들고 싶다. 어떤 기능과 형태가 좋을지도 같이 물어봐 줘. 아직 코드는 쓰지 마. 분석·시나리오·입출력·개요·가이드라인·ADR 순서로 필요한 질문을 한 번에 하나씩 해 줘. 질문마다 네 추천 답과 이유를 같이 주고, 10개 안에서 끝내. 끝나면 docs/overview.md와 docs/adr/0001-harness-shape.md로 정리하고 결정마다 한 줄 요약을 보여 줘. 내가 “승인”이라고 할 때까지 기다려.

grill-me 스킬. 계획을 세우기 전에 에이전트가 사용자에게 질문을 하나씩 집요하게 던지게 하는 스킬.
첫 프롬프트에서 세 가지를 못 박습니다. 아직 코드를 쓰지 말 것, 질문을 한 번에 하나씩 할 것, 그리고 정리한 설계를 한 줄 요약으로 보여 주고 내가 승인할 때까지 기다릴 것입니다. 질문마다 에이전트의 추천 답과 이유를 같이 달라고 하면, 모르는 부분도 선택하기 쉬워집니다. 질문 수에 상한을 두는 이유는 끝없는 질문도 시간을 잡아먹기 때문입니다. 오른쪽은 같은 생각을 스킬로 만든 예입니다. 매번 이 프롬프트를 쓰기 귀찮다면 11교시에서 자기 스킬로 만들어 보면 됩니다.

분석 대화의 결과물: 짧은 개요 하나와 첫 ADR 하나 (예)

문서결정 한 줄 요약 (예시)
개요 · 사용자·시나리오나 · 메모 앱 작은 수정, 실패 시 중단
개요 · 입출력·판정과제 문장 → 변경 + 테스트 통과
개요 · 수준·범위PoC · 파일 3개 · UI 없음
개요 · 아직 안 정한 것스킬·MCP(Model Context Protocol, 모델 컨텍스트 프로토콜)는 3회차에
ADR-0001 · 결정금지 3개 + 멈춤 3중(완료·20바퀴·예산)
ADR-0001 · 대안·이유전부 허용 / 매번 승인 · 3교시 사고 사례, 승인 피로
ADR-0001 · 다시 판단할 조건스모크에서 금지 요청이 하나라도 통과되면
  • 개요는 무엇을, ADR은 왜 그렇게 정했나
  • “아직 안 정한 것” 칸을 둔다. 다음 회차에 하네스가 자란다
  • 승인 전에 내가 읽고 고친다. 승인은 사람만 한다
→ 14교시: 이 방식이 ADR이 된다
분석 대화가 끝나면 에이전트가 이런 두 문서를 만들고, 결정마다 한 줄 요약을 보여 줍니다. 저는 문서 전체보다 이 요약표를 읽습니다. 개요는 1~6단계에서 정한 것을 한 장에 모은 것이고, ADR은 7단계에서 정하는, 되돌리기 비싼 결정(여기서는 권한과 멈춤 조건)을 왜 그렇게 정했는지 남긴 것입니다. 길 필요가 없습니다. 아직 안 정한 것 칸을 일부러 둡니다. 이 과정에서 하네스는 회차마다 자라기 때문에, 이번에 정하지 않은 것을 적어 두면 다음 회차의 출발점이 됩니다. 그리고 승인은 사람만 합니다. 저는 에이전트가 쓴 설계를 그대로 승인하지 않고 한 번은 고쳐 봅니다. 이 짧은 결정 기록은 14교시의 ADR로 이어집니다.
승인 체크리스트승인 전에 볼 것(예) · 내 하네스에 맞게 수정 가능

승인 전에 확인할 다섯 가지

  1. 에이전트의 질문에 내가 한 답이 빠짐없이 반영됐다
  2. 결정 요약에 수준이 PoC/MVP(Minimum Viable Product, 최소 기능 제품)로 적혀 있고 범위가 작다
  3. 멈춤 조건과 비용 상한이 적혀 있다
  4. 금지 목록이 있다 (예: 비밀값·대량 삭제·강제 푸시)
  5. 정한 항목마다 스모크로 어떻게 확인할지 한 줄씩 있다
코드를 열지 않고도 사람이 볼 곳이 세 군데로 줄어, 설계를 빨리 검토할 수 있다.
체크리스트에 없는 위험(예: 외부 API(Application Programming Interface, 응용 프로그램 인터페이스) 호출)은 놓칠 수 있다. 낯선 항목은 에이전트에게 위험을 따로 물어본다.
에이전트가 쓰고 사람이 판정하는 분업의 첫 연습. 2회차의 스펙 승인으로 이어진다.
설계 문서를 다 읽을 시간이 없어도 이 다섯 가지는 봅니다. 각자 하네스에 맞게 바꿔도 됩니다. 질문에 한 답이 그대로 들어갔는지, 수준이 PoC로 적혔는지, 멈춤 조건과 비용 상한이 있는지, 금지 목록이 있는지 봅니다. 저는 비밀값 읽기와 대량 삭제와 강제 푸시를 넣습니다. 마지막은 정한 항목마다 스모크로 확인할 방법이 한 줄 적혀 있는지입니다. 확인할 방법이 없는 규칙은 있는지 없는지 알 수 없기 때문입니다. 빠진 것이 있으면 승인하지 않고 고쳐 달라고 합니다. 이렇게 에이전트가 쓰고 사람이 판정하는 분업이 2회차의 스펙 승인으로 이어집니다.
승인 뒤 한 번예시 프롬프트 · 코드 대신 끝나는 조건과 보여 줄 것 지정

구현 프롬프트: 원하는 것·끝나는 조건·보여 줄 것

> 승인. overview.md와 ADR-0001대로 하네스 첫 버전을 만들어 줘. 끝나는 조건 - 내가 정한 기능이 동작한다 (예: 작은 과제 하나, 메모 정렬 옵션 추가를 끝까지 처리하고 테스트 통과) - ADR에 적은 금지·제한이 실제로 막힌다 (정했다면) 끝나면 보여 줘 - 테스트 결과 요약과 걸린 시간·바퀴 수 - 금지·제한 요청을 직접 시도한 결과 (예: 3개) - 안 막힌 게 있으면 원인과 고친 뒤 재시도 결과
“만들어 줘”가 아니라 조건과 증거까지 시키면, 코드를 읽지 않고도 판단할 근거가 생긴다.
에이전트가 낸 증거를 그대로 믿으면 안 된다. 다음 장에서 내가 직접 한 번 더 시켜 본다.
구현은 에이전트의 몫이고, 사람은 결정과 스모크 결과만 본다.
승인한 다음에는 이 프롬프트 하나로 구현을 맡깁니다. 무엇을 만들라고만 하지 않고, 어떤 조건이면 끝인지와 끝나면 무엇을 보여 달라는 것까지 적습니다. 저는 이렇게 시키고 코드는 열어 보지 않습니다. 대신 에이전트가 스스로 돌려 본 증거를 받습니다. 다만 에이전트가 낸 증거만으로 끝내지 않고, 다음 장처럼 제가 직접 요청을 넣어 한 번 더 확인합니다. 어떤 방식으로 만들지는 설계 대화에서 이미 정해졌으니 여기서 다시 묻지 않습니다.

막힐 때: 에이전트에게 다시 할 말

증상이렇게 다시 말한다
질문 없이 바로 코드를 쓴다“설계 질문이 끝나고 내가 승인하기 전에는 파일을 만들지 마.”
질문이 끝없이 이어진다“남은 질문은 네 추천 답으로 정하고 overview.md와 ADR을 써.”
무엇을 골라야 할지 모르겠다“선택지 두 개와 장단점을 표로 보여 줘.”
파일이 너무 많이 생긴다“PoC다. 파일 세 개 이내로 다시.”
스모크에서 멈추지 않고 계속 돈다“최대 바퀴 수와 예산 상한을 넣고, 상한에서 멈추는지 보여 줘.”
스모크에서 막혀야 할 요청이 통과됐다“방금 요청이 왜 통과됐는지 설명하고, 막히게 고친 뒤 같은 요청으로 다시 보여 줘.”
됐다고만 하고 증거가 없다“화면이나 로그로 보여 줘. 못 보여 주면 못 했다고 말해.”
오늘 막히는 곳은 대부분 설치나 문법이 아니라 대화입니다. 에이전트가 질문 없이 바로 코드를 쓰면 승인 전에는 파일을 만들지 말라고 다시 말합니다. 질문이 끝나지 않으면 남은 것은 추천 답으로 정하라고 합니다. 고르기 어려우면 선택지 두 개와 장단점을 표로 달라고 합니다. 스모크에서 막혀야 할 요청이 통과되면 왜 통과됐는지 설명시키고 고친 뒤 같은 요청으로 다시 보여 달라고 합니다. 이 표는 그대로 쓸 수 있는 문장들이니 막히면 옆에 띄워 두세요. 그래도 안 풀리면 손을 들어 주세요. 같이 대화 기록을 보면서 어디서 어긋났는지 찾겠습니다.

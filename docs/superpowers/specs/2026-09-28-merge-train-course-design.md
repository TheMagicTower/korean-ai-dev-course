# 병렬 AI 개발의 통합 병목 — 승인된 교재 보강 설계

사용자는 2026-09-28에 독립 실전 부록을 만들고 기존 CI/CD 자료 및 주차 본문에 연결하는 안을 승인했습니다. 기존 4주 × 120분은 유지합니다.

## 핵심 학습 목표

DDD로 업무 경계·계약·의존성을 명확히 하고, TDD로 영역별 행동을 검증하며, CI가 변경 영향 범위에 속하는 영역과 소비자·계약을 검사하도록 연결합니다. 검사 범위가 작아지면 머지트레인의 후보 검증 시간도 줄일 수 있습니다. DDD·TDD만 도입하거나 폴더만 나눈다고 자동으로 격리되는 것은 아닙니다. import 경계, 데이터 소유권, 의존성 그래프, 독립 테스트 환경이 뒷받침되어야 합니다.

## 내용과 범위

- PR 폭증: 에이전트·세션·커밋·PR을 구분하고 검토·롤백 가능한 변경 단위와 WIP 제한을 설명합니다.
- TDD는 Red–Green–Refactor 구현 반복, DDD는 Domain-Driven Design입니다. 상호 보완 관계이며 단위 테스트만으로 통합을 보장하지 않습니다.
- ApplyFlow 공고·지원 기록·알림을 설계 연습으로 사용합니다. 현재 데모에 해당 경계가 구현되었다고 주장하지 않습니다.
- 변경 영향 분석: 변경 영역 + 전이적 소비자 + 경계 계약 검사를 기본으로 하고 공통 코드·스키마·lockfile·CI 변경 또는 불명확한 그래프는 보수적으로 확대합니다.
- PR 검사는 최신 후보 기준으로, 큐 검사는 선행 PR을 포함한 합성 후보 전체 기준으로 계산합니다. 비교 base/head와 실제 테스트 대상 SHA를 기록합니다.
- GitLab Merge Trains와 GitHub Merge Queue를 구분합니다. 선행 실패·삭제·재정렬의 재실행, merge_group 필수 이벤트, 경로 필터와 필수 검사 누락, 잘못된 concurrency 그룹을 설명합니다.
- 속도·비용을 구분합니다. 교육용 가정 수치를 실측으로 표현하지 않고 러너 수·큐 대기·전체 통합 시간을 비교합니다.
- 빠른 검사와 안전한 통합을 함께 유지합니다. 전체 회귀 검사는 예약/릴리스 안전망이며 알려진 영향 검사를 뒤로 미루는 근거가 아닙니다.
- 설명·도해·설정 예시·실습/해설·워크시트·에이전트 프롬프트·공식 출처를 포함합니다.

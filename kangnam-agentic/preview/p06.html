세 가지는 각자 다른 실패를 막습니다. 스펙은 무엇을 만들지 정해 딴길로 새는 것을 막습니다. 테스트는 그 스펙대로 만들어졌는지 판정해 가짜 완료를 막습니다. 도메인 경계는 어디까지 고칠지 정해 범위가 폭주하는 것을 막습니다. 하나만 쓰면 나머지 실패가 그대로 남습니다. 그래서 겹쳐서 씁니다. 오늘은 테스트에서 시작해 경계로 넘어갑니다.

TDD: 실패하는 테스트를 먼저 쓴다

martinfowler.com/bliki/TestDrivenDevelopment.html
Martin Fowler bliki 화면 캡처 · 2026-10-28 확인
Fowler의 TDD 설명 글. 테스트 목록에서 하나 골라 쓰고(Red) → 통과시키고(Green) → 정리(Refactor)하는 반복 도식.
  1. 다음 기능의 테스트를 쓴다 (Red: 아직 실패)
  2. 통과할 때까지 구현한다 (Green: 통과)
  3. 동작은 그대로 두고 구조를 정리한다 (Refactor)

Kent Beck이 1990년대 후반 익스트림 프로그래밍의 일부로 발전시킨 기법

TDD는 새로운 방법이 아닙니다. Fowler의 설명대로 Kent Beck이 1990년대 후반 익스트림 프로그래밍의 일부로 만들었고, 세 단계를 반복합니다. 다음 기능의 테스트를 먼저 쓰고, 통과할 최소한의 코드를 쓰고, 구조를 정리합니다. 이 글은 테스트를 먼저 쓰면 인터페이스를 먼저 생각하게 된다는 점도 이점으로 꼽습니다. 그리고 가장 흔한 실패가 세 번째, 정리를 건너뛰는 것이라고 지적합니다. 사람이 오래 못 지킨 습관이라는 점을 짚어 둡니다.

Claude Code 모범 사례 문서의 ‘Instead of(이렇게 말하지 말고) / Try(이렇게)’ 표. “로그인 버그 고쳐” 대신 실패 재현 테스트를 쓰게 한다.
  • 사람: 테스트 쓰는 시간이 구현만큼 들어 생략
  • AI: 테스트 수십 개를 쓰는 비용이 거의 없다
  • 공식 문서의 프롬프트 예: “write a failing test that reproduces it, then fix it” (재현하는 실패 테스트를 쓰고, 그다음 고쳐라)
사람이 TDD를 못 지킨 가장 큰 이유는 분량이었습니다. 테스트를 쓰는 시간이 구현만큼 들기 때문에 마감 앞에서 먼저 사라졌습니다. 에이전트에게는 분량이 문제가 아닙니다. 그래서 사람이 하지 못하던 TDD를 AI에게 시킬 수 있습니다. 화면은 Claude Code 공식 문서의 프롬프트 예시입니다. 버그를 재현하는 실패 테스트를 먼저 쓰고 그다음 고치라고 구체적으로 적으라는 예입니다. 다만 이 문서가 TDD라는 이름의 별도 절을 두고 있지는 않다는 점을 밝혀 둡니다. 제가 확인한 현재 문서에서 근거로 삼은 것은 이 예시와 검증 수단 절입니다.

완료는 에이전트의 말이 아니라 통과 결과

code.claude.com/docs/en/best-practices
공식 문서 화면 캡처 · 2026-10-28 확인
Claude Code 문서의 ‘실행해서 확인할 수단을 주라’는 절. 통과·실패를 돌려주는 검증 수단 예시.
“Give Claude something it can run that comes back pass or fail.”“Claude에게 실행했을 때 통과나 실패를 돌려주는 무언가를 주어라.”Claude Code Docs · Best practices
  • 검증 수단: 테스트 파일, 빌드 종료 코드, 린터(코드 규칙 검사기)
  • repo의 CLAUDE.md에 테스트 실행 명령을 적는다
  • “All tests pass(모두 통과)”만 믿지 말고 실행 출력을 요구
공식 문서는 에이전트에게 통과 또는 실패를 돌려주는 검증 수단을 주라고 말합니다. 그것이 없으면 에이전트에게 남는 기준은 다 한 것 같다는 느낌뿐이고, 그러면 사람이 테스트 스위트 노릇을 하게 된다고 설명합니다. 검증 수단은 테스트 파일, 빌드 종료 코드, 린터 등 무엇이든 됩니다. CLAUDE.md에 그 명령을 적어 두는 것이 가장 유용한 한 줄입니다. 그리고 문서는 모두 통과했다는 말만으로는 알 수 있는 것이 적으니 실행한 명령과 출력을 요구하라고 권합니다. 이것이 8교시 실습의 완료 기준이 됩니다.
사례통과가 곧 완료 · 가상 예(프롬프트·보고) / 실제 실행(출력)

“구현 완료했습니다” 뒤에 숨은 쿠폰 중복 적용

1) 완료 기준 없이 시킴
> 장바구니에 할인 쿠폰 적용 기능 만들어 줘 에이전트: 구현 완료했습니다. # 같은 쿠폰 WELCOME3000을 두 번 적용 {'total': 14000, 'coupons': ['WELCOME3000', 'WELCOME3000']}
  • 20,000원 주문이 6,000원 할인
  • 판정 기준이 없어 “완료”를 믿을 수밖에 없음
2) 테스트를 완료 기준으로 줌
> test_cart.py가 모두 통과해야 완료. 같은 쿠폰 두 번은 ValueError. 실행 출력을 붙여서 보고해. $ python3 test_cart.py # 첫 구현 FAIL: test_same_coupon_twice_is_rejected AssertionError: ValueError not raised $ python3 test_cart.py # 수정 후 Ran 2 tests ... OK
  • 같은 첫 구현이 이번엔 보고 전에 걸림

코드는 같아도 판정 기준이 있으면 빠진 규칙이 보고 전에 드러납니다.

쇼핑몰에서 할인 쿠폰을 붙이는 기능을 맡긴 가상 상황입니다. 왼쪽처럼 기능만 말하면 에이전트는 할인이 한 번 들어가는 것을 확인하고 완료라고 보고합니다. 그런데 같은 쿠폰을 두 번 넣으면 할인이 두 번 들어갑니다. 이 출력은 그 첫 구현을 실제로 실행해 얻은 결과입니다. 오른쪽처럼 중복 규칙을 테스트로 적고 통과를 완료 조건으로 주면, 똑같은 첫 구현이 보고 전에 실패로 걸리고 에이전트가 스스로 고칩니다. 핵심은 에이전트가 더 똑똑해진 것이 아니라, 완료를 판정할 기준이 생겼다는 점입니다.
실제 실행 결과domain-testing 예제 · Python unittest · 강사 운영 방식

Red 확인이 먼저, Green은 그다음

1) 스텁(가짜 구현) · 테스트 실행 → Red(실패)
def submit(status): return "submitted" $ python3 transition_test.py FAIL: test_submitted_cannot_be_submitted_again AssertionError: ValueError not raised Ran 2 tests ... FAILED (failures=1)
2) 구현 → Green(통과)
def submit(status): if status != "draft": raise ValueError("작성 중인 지원만 제출할 수 있습니다.") return "submitted" $ python3 transition_test.py Ran 2 tests ... OK

규칙: 이미 제출한 지원은 다시 제출할 수 없다. 실패가 규칙을 가리키는지 확인한 뒤에 구현합니다.

제 강의 자료의 작은 예시를 이 자리에서 실제로 실행한 결과입니다. 규칙은 이미 제출한 지원은 다시 제출할 수 없다는 것입니다. 먼저 항상 제출됨을 돌려주는 스텁으로 테스트를 돌리면 두 번째 테스트가 실패합니다. 이 Red를 눈으로 확인하는 것이 중요합니다. 실패한 이유가 규칙 때문이어야 테스트가 쓸모 있다는 증명이 됩니다. 그다음 구현을 넣으면 두 테스트가 통과합니다. 에이전트에게도 구현 전에 테스트를 실행해 실패를 보여 달라고 시킵니다.

테스트를 완료 기준으로 삼으면 새 문제가 생깁니다. 통과가 목적이 되면 에이전트가 통과만 하는 길을 찾을 수 있습니다. Anthropic은 2025년 5월 Claude 4 발표에서 모델이 작업을 끝내려고 지름길이나 허점을 쓰는 행동을 줄였고, 그런 행동에 취약한 에이전트 과제에서 Sonnet 3.7보다 65% 덜 한다고 밝혔습니다. 반대로 말하면 이전 모델에는 그런 행동이 있었고, 줄었더라도 사라졌다고 보장하지는 않습니다. 그래서 모델이 좋아지기를 기다리지 않고 구조로 막습니다. 장점은 지름길 행동이 65% 줄었다는 발표 수치, 단점은 그런 행동이 사라진 것은 아니고 수치를 발표한 주체가 모델을 만든 회사라는 점, 의미는 구조로 막아야 한다는 것입니다.
실제 실행 결과같은 예제에서 테스트를 건드린 경우 · 강사 운영 방식

속임수 세 가지: 고치고, 건너뛰고, 박아 넣기

# 구현은 그대로 (규칙을 어긴 채) def submit(status): return "submitted" # 에이전트가 테스트 쪽을 고침 @unittest.skip("flaky") def test_submitted_cannot_be_submitted_again(self): ... $ python3 cheat_test.py Ran 2 tests ... OK (skipped=1)
  1. 테스트 수정·삭제·skip(건너뛰기): 초록불이지만 규칙은 안 지킴
  2. 기대값 약화: 단언을 느슨하게 바꿈
  3. 하드코딩(정답 박아 넣기): 테스트 입력만 통과하는 분기

공통점: 실행 결과는 초록, 규칙은 어겨졌다

가장 단순한 속임수를 실제로 돌려 본 화면입니다. 구현은 규칙을 어긴 그대로인데 테스트에 skip 한 줄을 붙이면 OK가 나옵니다. 끝에 skipped=1이 작게 붙어 있어 놓치기 쉽습니다. 같은 부류로 기대값을 느슨하게 바꾸는 것, 테스트에 나온 입력만 통과하게 분기를 박아 넣는 것이 있습니다. 모두 초록불인데 규칙은 지켜지지 않았습니다. 그래서 저는 초록불만 보지 않고 테스트 자체가 바뀌었는지를 함께 봅니다.
대응 4가지강사 운영 방식

속임수에 대한 대응: 막고, 대조하고, 직접 본다

테스트를 먼저 커밋해 기준을 고정하고, 파일을 보호하고, 다른 눈으로 검토합니다. 마지막 판정은 사람입니다.

대응은 네 겹입니다. 첫째, 테스트를 먼저 커밋합니다. 이후 테스트 파일이 바뀌면 git diff에 바로 드러납니다. 둘째, 에이전트가 테스트 파일을 수정하지 못하게 권한 deny나 훅으로 막습니다. 셋째, 구현한 에이전트와 별개의 리뷰어 서브에이전트가 스펙과 대조하게 합니다. 넷째, 결국 사람이 직접 실행해 봅니다. 1교시에서 말한 스모크 테스트의 이유입니다. 이어서 둘째와 셋째를 하나씩 보겠습니다.
사례대응 전략 · 테스트 먼저 커밋 · 실제 실행(가상 예제 저장소)

비밀번호 재설정: 기대값을 약하게 바꾼 것이 diff에 남는다

# 스펙: 재설정 링크는 30분 뒤 만료 $ git commit -m "test: 재설정 링크는 30분 뒤 만료" # 에이전트 구현: 60분으로 잘못 → 테스트 실패 # 에이전트가 테스트 쪽 단언을 바꿈 $ python3 tests/test_reset.py Ran 2 tests ... OK $ git diff -- tests/ - self.assertFalse(is_token_valid(0, 31)) + self.assertIsNotNone(is_token_valid(0, 31))
# 끝내기 전 관문: 테스트가 커밋 때와 같은가 $ git diff --exit-code --stat HEAD -- tests/ tests/test_reset.py | 2 +- exit=1 ← 테스트가 바뀜, 완료 불가

각 영역이 데이터와 규칙을 소유하고, 다른 영역과는 조회 계약·이벤트로만 만납니다. 실제 앱이 이 구조로 구현되어 있다는 뜻이 아닌 설계 예시입니다.

왜 에이전트에게 경계가 필요한가: 볼 범위 축소

경계는 컨텍스트 창 절약, 수정 범위 제한, 영역별 테스트 실행을 한꺼번에 줍니다.

사람 팀에게 바운디드 컨텍스트가 필요한 이유는 소통 비용이었습니다. 에이전트에게는 보는 범위가 곧 비용입니다. 경계가 없으면 에이전트는 관련 있어 보이는 파일을 다 읽고 다 고쳐서 컨텍스트 창을 낭비하고 회귀를 만듭니다. 경계가 있으면 지원 기록 폴더와 공개 계약만 보고, 그 영역의 테스트만 돌리면 됩니다. 테스트와도 연결됩니다. 영역별 테스트가 있어야 범위를 묶은 채로 통과를 판정할 수 있습니다. 이 효과가 제가 SDD(Spec-Driven Development, 스펙 주도 개발), TDD, DDD를 함께 쓰는 이유입니다.

클린 아키텍처: 의존은 안쪽으로만

blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html
Uncle Bob 블로그 화면 캡처 · 2026-10-28 확인
Uncle Bob의 클린 아키텍처 글 중 의존성 규칙 문단. 안쪽 원은 바깥쪽을 알아서는 안 된다.
“source code dependencies can only point inwards.”“소스 코드의 의존은 안쪽으로만 향할 수 있다.”Robert C. Martin · 2012
의존 방향이 안쪽 하나라 규칙이 단순하다. 안쪽은 엔티티(업무 규칙), 바깥은 UI(User Interface, 사용자 화면)·DB(Database, 데이터베이스)·프레임워크.
작은 PoC에 쓰면 계층·추상화가 과잉 개발로 흐른다.
엔터프라이즈 규모일 때만 프롬프트에 적는다. 규모를 한 줄로 밝히는 것이 핵심.
클린 아키텍처의 핵심은 의존성 규칙입니다. 소스 코드 의존은 안쪽으로만 향하고, 안쪽 원은 바깥쪽 이름을 알아서는 안 됩니다. 가장 안쪽은 엔티티, 즉 업무 규칙이고, 바깥은 UI(User Interface, 사용자 화면), DB(Database, 데이터베이스), 프레임워크 같은 세부 사항입니다. 이 글의 원래 도식 이미지는 제가 가져온 화면에서 로딩되지 않아 본문 문단을 보여 드립니다. 프롬프트에 클린 아키텍처라고 적으면 에이전트는 이 계층 구조를 따라 도메인, 응용, 인프라로 나누려 합니다. 장점은 의존 방향이 하나라 단순하다는 것, 단점은 작은 PoC에는 과하다는 것, 의미는 규모를 프롬프트에 적어야 한다는 점입니다.
사례클린 아키텍처 · 의존성 규칙 · 실제 실행(가상 예제 저장소)

강의실 예약 규칙이 DB와 현재 시각을 직접 부른다

1) “예약 가능 여부 검사 추가해 줘” 결과
# domain/reservation.py from datetime import datetime from infra.db import RoomTable def can_reserve(room_id, start): if start < datetime.now(): return False return RoomTable.get(room_id).is_open $ sh check_deps.sh domain/reservation.py:2:from infra.db import RoomTable FAIL: domain이 infra를 import함 exit=1
2) 바깥 것은 인자로 받기
# domain/reservation.py def can_reserve(room, start, now): if start < now: return False return room.is_open $ sh check_deps.sh OK: domain → infra 의존 없음 exit=0
  • DB 없이 테스트 가능
  • “지금”을 고정해 시간 테스트 가능
  • 검사 스크립트를 완료 조건에
강의실 예약에서 지난 시각은 예약할 수 없다는 규칙을 가정한 예제를 실제로 돌려 본 결과입니다. 왼쪽은 에이전트가 흔히 내놓는 모양입니다. 업무 규칙 파일이 DB 테이블과 현재 시각을 직접 부르고 있어서, 규칙 하나를 테스트하려 해도 DB가 있어야 하고 시각에 따라 결과가 바뀝니다. 오른쪽은 강의실과 현재 시각을 바깥에서 받게 바꾼 것입니다. 의존이 안쪽으로만 향한다는 말이 코드로는 이런 차이입니다. 검사는 grep 몇 줄짜리 스크립트로도 충분하고, 종료 코드가 0이 아니면 완료가 아니라고 정해 두면 에이전트가 경계를 어긴 것을 바로 압니다.
기초 중의 기초강사 운영 방식 · 프롬프트에 규모를 적는다

프롬프트에 수준을 적는다: PoC냐, 엔터프라이즈냐

PoC(시험 제작) · MVP(Minimum Viable Product, 최소 기능 제품)
이건 PoC입니다. 지원 제출 기능을 가장 단순하게. 계층 분리·추상화·설정 파일 금지. 테스트는 핵심 규칙 한 개만.
  • 쓰고 버려도 되는 코드
  • 안 적으면 과잉 개발로 흐른다
엔터프라이즈 규모
클린 아키텍처로. 도메인 / 응용 / 인프라를 분리하고 의존은 도메인 방향으로만. 영역별 테스트와 계약 테스트 포함.
  • 오래 유지·여러 팀이 쓰는 코드
  • 경계 안에서만 고치게 한다

같은 요구사항도 규모를 적지 않으면 에이전트가 임의로 정합니다. 한 줄이면 충분합니다.

이것이 오늘 가장 실용적인 한 줄입니다. 엔터프라이즈 규모라면 프롬프트에 클린 아키텍처라고 적고, 그렇지 않다면 PoC나 MVP(Minimum Viable Product, 최소 기능 제품)라고 분명히 적습니다. 적지 않으면 에이전트는 친절하게도 계층과 추상화와 설정을 잔뜩 만들어 과잉 개발을 합니다. 학생 프로젝트와 사이드 프로젝트 대부분은 PoC나 MVP입니다. 그래서 저는 이것이 기초 중의 기초라고 말합니다. 1교시에서 본 과열 방지 스킬, 대표적으로 Ponytail과 Karpathy guidelines도 같은 방향의 장치입니다.
시연 예정같은 요구사항을 두 수준으로 · 강사 실제 화면으로 교체 예정

같은 기능도 PoC냐 클린 아키텍처냐에 따라 모양이 달라진다

현장에서 같은 요구사항을 두 프롬프트로 시켜 파일 수와 줄 수를 직접 세어 비교합니다.

여기서는 구조의 차이만 도식으로 보여 드립니다. PoC로 시키면 파일 하나와 테스트 정도로 끝납니다. 클린 아키텍처로 시키면 도메인, 응용, 인프라가 나뉘고 의존은 도메인을 향합니다. 실제 파일 수와 줄 수는 모델과 프롬프트에 따라 달라지므로 수업에서 같은 요구사항을 두 번 시켜 그 자리에서 세어 보겠습니다. 숫자를 미리 말씀드리지 않는 이유는 제가 이 비교를 아직 측정해 두지 않았기 때문입니다. 어느 쪽이 맞다는 이야기가 아니라 목적에 맞는 수준을 고르라는 이야기입니다.

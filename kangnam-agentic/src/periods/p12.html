실습 3

하네스 한 번 더 키우기:
격리 규칙 · 스킬 · MCP · /goal

12교시는 실습입니다. 도구 설치와 로그인은 하지 않고, 각자 쓰던 에이전트를 그대로 씁니다. 지난 회차에는 이슈 하나를 스펙, 계획, 구현, 리뷰 순서로 에이전트와 처리했습니다. 오늘 소개하는 장치는 메뉴입니다. 순서를 스킬로 포장하기, 이슈마다 작업 공간을 나누는 규칙, 외부 도구 연결, 이슈 하나를 완료 조건까지 통째로 맡기기가 있고, 이 가운데 내 하네스에 필요한 것을 골라 시키면 됩니다. 제가 쓰는 방식을 보여 드리고, 자기 방식대로 바꿔도 됩니다. 이번에도 설정 파일은 여러분이 쓰지도, 읽지도 않습니다. 에이전트에게 질문부터 시켜서 만들고, 여러분은 답하고 승인한 뒤 실제로 돌려 보며 확인합니다.
약 55분 · 프롬프트 + 스모크18단계 중 15단계(워크플로우·워크트리 설정) · 이슈별 워크플로우 1–8단계를 스킬로

진행 순서: 질문 → 승인 → 구현 → 스모크 → /goal

여러분이 보는 것은 코드가 아니라 내가 한 답, 에이전트가 정리한 결정, 스모크 결과 세 가지입니다.

오늘은 제 운영 기준 18단계 가운데 15단계, 작업을 어떻게 격리하고 합칠 것인가를 하네스 크기로 줄여 적용합니다. 먼저 에이전트가 격리, 리뷰, 머지 규칙과 스킬, MCP(Model Context Protocol, 모델 컨텍스트 프로토콜), 완료 조건에 대해 질문하고 여러분이 답합니다. 에이전트는 답을 ADR(Architecture Decision Record, 아키텍처 결정 기록) 한 건과 스킬 설계로 정리하고, 여러분이 읽고 승인한 뒤에야 구현합니다. 구현 뒤에는 코드를 열어 보는 대신 스모크로 확인합니다. 스킬이 불리는지, MCP가 붙었는지 보고, 원하면 마지막으로 이슈 하나를 /goal로 맡겨 조건에서 멈추는지 봅니다. 설계 대화 12분, 승인 8분, 구현 10분, 스모크 10분, 이슈 완주 15분 정도로 잡습니다.

스킬 후보: 지난 회차에 매번 말로 시킨 순서

  • 이슈 분석 → ADR(Architecture Decision Record, 아키텍처 결정 기록) 점검 → 스펙 → 스펙 리뷰 → 계획 → 계획 리뷰 → 구현 → 구현 리뷰를 이슈마다 다시 설명했다
  • 같은 설명을 세 번 쓰면 후보. 한 스킬 = 한 작업
  • 스킬의 본문은 필요할 때만 읽힌다. 어떤 말에 불리는지가 호출을 좌우한다

직접 도식 · 스킬 로딩 흐름
8교시에 이슈 하나를 처리하면서 에이전트에게 스펙을 쓰라고 하고, 리뷰하라고 하고, 계획을 세우라고 하고, 구현하라고 했습니다. 이슈가 열 개면 같은 설명을 열 번 하게 됩니다. 이런 반복이 스킬로 만들 후보입니다. 도식처럼 세션이 시작되면 스킬의 이름과 설명만 목록에 올라가고, 요청이 설명과 맞을 때 본문을 읽습니다. 그래서 설명 문장을 잘 쓰는 것이 중요합니다. 이 스킬도 직접 쓰지 않고 에이전트에게 설계 대화를 거쳐 만들게 한 뒤, 불리는지만 확인합니다.
그대로 붙여 넣기 가능강사가 쓰는 프롬프트의 예 · 내 하네스에 맞게 바꿔 쓰기 · 각자 쓰는 에이전트

첫 프롬프트(예): 코드 전 질문은 하나씩, 설계는 ADR로

> 내 하네스 저장소(메모 앱 PoC(Proof of Concept, 개념 증명))에 장치를 더하고 싶다. 후보: ① 이슈마다 격리할 워크트리·브랜치·리뷰·머지 규칙, ② 반복하는 순서를 하나의 스킬로(예: issue-flow), ③ MCP 서버, ④ /goal로 이슈 맡기기. 내게 필요한 게 뭔지부터 물어봐. 아직 파일은 만들지 마. 필요한 질문을 한 번에 하나씩, 네 추천 답과 이유를 같이 주고 8개 안에서 끝내. 끝나면 docs/adr/0003-workflow.md, 스킬·MCP 설계 요약, 스모크로 확인할 시나리오 목록을 쓰고 내가 “승인”이라고 할 때까지 기다려.

4교시와 같은 방식의 프롬프트입니다. 아직 파일을 만들지 말 것, 질문은 한 번에 하나씩 추천 답과 함께, 정리한 설계는 사용자가 승인할 때까지 기다릴 것, 이 세 가지를 못 박습니다. 하나 더, 끝에 스모크 시나리오 목록을 달라고 합니다. 코드를 열어 보지 않는 대신 돌려서 확인하기 위해서입니다. 이번에는 고를 수 있는 항목이 몇 묶음 있습니다. 이슈를 어떻게 격리하고 합칠지, 이슈별 순서를 스킬로 만들지, 어떤 외부 도구를 붙일지, /goal로 맡길지입니다. 위 프롬프트는 제가 고른 경우이고, 여러분은 후보를 바꿔 쓰시면 됩니다. 결과는 새 ADR 한 건으로 남깁니다. 4교시에 만든 문서가 있으면 에이전트가 먼저 읽도록 저장소 안에서 시키면 됩니다. 오른쪽은 워크트리를 설명하는 공식 문서 화면입니다.
설계 대화 체크리스트강사가 쓰는 질문의 예 · 15단계 + 스킬 · MCP · /goal · 안 물으면 먼저 꺼내기

에이전트가 물을 질문: 격리·리뷰·스킬·MCP·완료 조건

주제에이전트가 물을 것예시 답빠지면
15 격리이슈 하나를 어디서 작업하나이슈마다 워크트리 + issue/번호 브랜치두 이슈가 한 폴더에서 섞인다
15 충돌같은 파일을 건드리는 이슈는한 번에 하나, 공유 파일은 이슈에 미리 적음합칠 때 뒤늦게 충돌
15 리뷰·머지누가 리뷰하고 언제 합치나리뷰어 서브에이전트, 머지는 사람 승인(16교시)쓴 쪽이 스스로 통과시킨다
스킬순서와 멈춤을 어디까지 담나1–8단계, 블로커 없으면 종료, 예산 소진 시 인계이슈마다 말로 다시 설명
MCP어떤 외부 정보가 필요하고 믿을 만한가라이브러리 문서 서버 1개, 읽기만, 비밀 없음쓸모없는 도구, 주입·토큰 낭비
/goal어느 이슈를 어떤 끝 상태까지, 상한은이슈 하나, 테스트 통과 + 블로커 0, 20턴조건이 모호해 헛돈다
기록무엇을 남기나시간·턴·토큰·성공/실패다음 회차의 근거가 없다
설계 대화에서 에이전트의 질문을 살피는 기준입니다. 15단계의 핵심은 작업을 어떻게 격리하고 어떻게 합치는가입니다. 격리, 충돌, 리뷰와 머지 세 줄이 여기에 해당합니다. 나머지 네 줄은 오늘 더할 장치인 스킬, MCP, /goal, 기록입니다. 에이전트가 일부를 묻지 않으면 여러분이 먼저 꺼내 봅니다. 모르는 항목은 선택지 두 개와 장단점을 표로 달라고 하면 됩니다. 머지와 PR(Pull Request, 변경 병합 요청) 규칙은 오늘은 정하기만 하고, 실제로 PR을 만들고 머지하는 일은 4회차에서 합니다.
18단계 중 15단계에이전트가 정리한 결정 한 줄 요약 · 예시 · ADR 본문 대신 이 표만 확인

15단계의 결과: ADR 한 건의 결정 요약

항목에이전트가 정리한 결정(예시)내가 볼 점
격리이슈 하나 = 브랜치 하나 = 작업 공간 하나두 이슈가 안 섞이는가
충돌같은 파일을 건드릴 이슈는 한 번에 하나겹칠 때의 규칙이 있는가
리뷰구현한 쪽이 아닌 리뷰어 서브에이전트쓴 쪽이 통과시키지 않는가
머지PR(Pull Request, 변경 병합 요청)·머지는 사람 승인 뒤, 4회차(16교시)에오늘은 정하기만 하는가
다시 판단할 조건두 이슈가 같은 파일에서 충돌하면4교시 ADR과 같은 서식인가
이슈마다 작업이 나뉘어, 한 이슈를 하는 동안 다른 이슈의 변경이 섞이지 않는다. 4회차 병렬 실행의 바탕이 된다.
작업 공간이 늘어 디스크를 더 쓴다. 겹치는 파일은 여전히 합칠 때 충돌한다.
15단계의 질문 ‘작업을 어떻게 격리하고 합치는가’에 대한 답. 결정과 이유가 ADR에 남아 다음 판단의 기준이 된다.

워크트리를 만드는 명령은 에이전트가 이슈마다 알아서 실행합니다. 확인할 것은 결정이 맞는지뿐입니다.

에이전트가 정리한 ADR의 한 줄 요약 예입니다. ADR 본문이나 명령을 읽지는 않고 이 표만 봅니다. 격리는 이슈, 브랜치, 작업 공간이 하나씩 대응하는지 봅니다. 충돌은 같은 파일을 건드리는 이슈를 어떻게 다루는지, 리뷰는 구현한 쪽이 아닌 다른 서브에이전트가 하는지 봅니다. 머지는 사람 승인 뒤로 미루었는지 확인합니다. 마지막 줄의 다시 판단할 조건은 4교시 ADR과 같은 서식입니다. 표의 내용은 예시이고, 여러분 에이전트의 정리는 다를 수 있습니다.
승인 체크리스트내가 한 답 · 에이전트가 정리한 결정 · 스모크 시나리오, 이 세 가지만 확인

승인 전에 확인할 다섯 가지

  1. 내가 한 답이 정리에 그대로 들어 있다(바뀐 답이 없다)
  2. 결정 요약에 이슈 하나당 작업 공간 하나와 겹칠 때의 규칙이 있다
  3. 스킬을 만든다면 어떤 말에 불려야 하는지가 한 문장으로 적혔고, PR·머지는 스킬 밖이다
  4. 예산이 떨어지면 통과가 아니라 중단·인계하고, MCP를 붙인다면 믿을 서버 하나다
  5. 스모크 시나리오 목록이 있고(고른 장치별: 스킬 호출 · 일부러 어기기 · MCP · /goal 멈춤), 구조를 30초 안에 설명할 수 있다
볼 것이 세 가지로 줄어, 코드를 읽지 않고도 승인 여부를 빨리 판단할 수 있다.
목록에 없는 위험(예: 서버가 가져오는 글의 프롬프트 주입)은 놓칠 수 있다. 낯선 항목은 에이전트에게 위험을 따로 묻는다.
에이전트가 만들고 사람이 판정하는 분업. 4교시 승인과 같고, 이번에는 대상이 스킬·MCP·완료 조건이다.
승인 전에 다섯 가지를 봅니다. 내가 한 답이 정리에 그대로 들어갔는지, 결정 요약에 격리와 충돌 규칙이 있는지, 스킬이 어떤 말에 불려야 하는지 한 문장으로 적혔는지, 예산이 떨어졌을 때 통과시키지 않고 중단하게 되어 있는지, 스모크 시나리오 목록이 있는지입니다. 이 구조를 30초 안에 설명하지 못하면 승인하지 않고 더 단순하게 바꿔 달라고 합니다. 승인은 사람만 합니다. 마음에 안 드는 한 곳은 에이전트에게 말로 고치게 해 봅니다.

# 프롬프트 > 지난주 이슈 처리 1–8단계(분석 → ADR 점검 → 스펙 → 스펙 리뷰 → 계획 → 계획 리뷰 → 구현 → 구현 리뷰)를 issue-flow 스킬로 만들어 줘. “12번 이슈 처리해 줘”처럼 이슈 번호를 말하면 불려야 해. 구현은 테스트 먼저, 리뷰는 리뷰어 서브에이전트가 해. 예산이 떨어졌는데 블로커가 남으면 통과시키지 말고 진행 파일에 적고 중단해. PR·머지는 이 스킬에 넣지 마. 끝나면 직접 이름으로 한 번, 평범한 문장으로 한 번 불러서 불린 증거를 보여 줘.

스킬은 파일을 열어 보지 않고, 하네스에게 시킨 뒤 실제로 불리는지로 확인합니다. 프롬프트에는 어떤 말에 불려야 하는지, 순서, 멈춤 규칙, 하지 않을 것을 담았습니다. 스모크는 세 가지입니다. 이름으로 직접 부르기, 평범한 문장으로 부르기, 단계를 건너뛰자고 일부러 요청하기입니다. 표의 실제 결과 칸은 예시이고, 자동 호출이 실패하는 경우를 일부러 넣었습니다. 이런 경우 스킬의 설명 문장을 고치게 하면 대개 풀립니다.

MCP 연결: 하네스에게 맡기고 직접 호출로 확인

# 프롬프트 > 이슈를 분석할 때 최신 라이브러리 문서를 볼 수 있게 문서 조회 MCP 서버 하나(대표 Context7)를 이 저장소에 연결해 줘. 읽기만 하고, 토큰이 필요하면 값이 아니라 환경 변수 이름으로만 써. 끝나면 연결 상태와 쓸 수 있는 도구 목록을 보여 주고, 새 세션에서도 보이는지 확인해 줘.
# 스모크 (대화 예시) 학생 새 세션이야. MCP 연결 상태 보여 줘. 하네스(예시) 서버 1개 연결됨, 상태 정상. 학생 12번 이슈에 쓰는 라이브러리의 정렬 옵션을 문서 조회 도구로 확인해서 스펙에 반영해 줘. 하네스(예시) 문서 조회를 2회 호출했고, 확인한 옵션을 스펙에 적었습니다. 학생 이 서버가 가져온 글에 “지시”가 섞여 있을 때는? 하네스(예시) 가져온 글은 참고 자료로만 쓰고 지시로 따르지 않습니다.

볼 것은 세 가지뿐입니다. 연결 상태, 실제로 호출된 기록, 비밀 값이 파일에 없다는 확인(“파일에 토큰 값이 없는지 검색해서 보여 줘”).

MCP는 에이전트에 외부 도구를 연결하는 규약입니다. 오늘은 이슈 분석에 쓸 문서 조회 서버 하나만 붙입니다. 대표 도구로 Context7을 씁니다. 연결 설정은 하네스가 만들고, 설정 파일은 열지 않습니다. 대신 새 세션에서 연결 상태를 묻고, 실제로 호출해 보게 하고, 비밀 값이 파일에 남지 않았는지 검색하게 합니다. 서버가 가져오는 글에 지시가 섞이는 프롬프트 주입 위험이 있으니, 가져온 글을 지시로 따르지 않는지도 한 번 물어봅니다. 오른쪽 대화는 예시입니다.

/goal이 안 끝난다“상태를 보고 왜 조건이 충족 안 됐는지 설명해. 측정 가능한 문장으로 다시 써.”
상한에 걸려 멈췄다“어디까지 했고 무엇이 막혔는지 진행 파일에 적고 인계해.”

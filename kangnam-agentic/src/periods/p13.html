description: 3인칭으로 하는 일과 쓰는 때

판단 단서가 없는 설명

“PDF 작업을 도와줌”

  • 무엇을 하는지, 언제 쓰는지 알 수 없다
  • 지금 필요한 스킬인지 고를 근거가 없다
하는 일과 쓰는 때가 있는 설명

“Extracts text and tables from PDF files … Use when working with PDF documents.”

  • 하는 일과 쓰는 때를 함께 적는다
  • 사용자가 말할 법한 낱말(PDF, forms)을 넣는다

시스템 프롬프트에 들어가는 문장이므로 3인칭으로 씁니다. 핵심 용도와 구체적인 낱말을 앞에 둡니다.

description은 에이전트가 스킬을 고를 때 읽는 문장입니다. 공식 작성 지침은 시스템 프롬프트에 들어가는 문장이므로 3인칭으로 쓰라고 권합니다. 하는 일과 쓰는 때를 함께 적고, 사용자가 실제로 말할 파일 형식이나 작업 이름을 넣습니다. PDF 작업을 돕는다는 정도로 범위만 넓히면 지금 불러야 할 스킬인지 판단하기 어렵습니다. 앞서 본 brainstorming의 “반드시 쓰라”와 docx의 부정 조건도 같은 기술입니다. Claude Code는 설명을 1,536자에서 자르므로 핵심을 앞에 둡니다. 반대로 배포처럼 사람이 결정해야 하는 스킬은 모델 호출을 꺼서 설명 자체를 컨텍스트에서 뺍니다.

본문은 짧게, 세부는 파일로

{{svg:p13-skill-structure}}

모델이 이미 아는 설명은 빼고, 본문은 500줄 미만으로 유지합니다. 참조는 SKILL.md에서 한 단계, 스크립트는 실행과 참고 읽기 중 무엇인지 적습니다.

SKILL.md를 쓸 때는 모델에게 새로 필요한 것만 남깁니다. PDF가 무엇인지나 일반적인 라이브러리 사용법처럼 모델이 이미 아는 설명은 뺍니다. 본문이 500줄에 가까워지면 세부 절차와 참고 자료를 references/의 파일로 나누고, 본문에 어떤 상황에서 읽는지 적습니다. 참조 파일이 다시 다른 참조 파일로 이어지면 일부만 읽힐 수 있으므로 SKILL.md에서 바로 가리키는 한 단계로 유지합니다. 검증이나 변환처럼 결정적인 작업은 scripts/에 실행 파일로 두고, 본문에는 정확한 명령을 적습니다.

  • 구조와 버그 가능성을 살핀다
  • 프로젝트 관례에 맞는 개선안을 제안한다
  • 여러 접근이 가능하고 문맥에 따라 판단한다
낮은 자유도 · 정해진 명령

데이터베이스 마이그레이션

python scripts/migrate.py --verify --backup
  • 순서가 틀리면 안 되는 작업
  • 스크립트와 명령을 정확히 지정한다

작업이 문맥에 따라 달라지면 지침을 유연하게, 순서와 결과가 일관돼야 하면 명령과 매개변수를 구체적으로 적습니다.

같은 스킬 안에서도 작업마다 지침의 구체성을 달리할 수 있습니다. 코드 리뷰는 코드 구조와 맥락에 따라 판단이 달라지므로 무엇을 살필지 글로 제시하는 편이 맞습니다. 데이터베이스 마이그레이션처럼 순서가 틀리면 안 되는 작업은 실행할 스크립트와 명령을 정확히 지정합니다. 모든 작업을 엄격하게 만들기보다 작업이 깨지기 쉬운 정도와 변동성에 맞춰 자유도를 정합니다.

나만의 스킬 만들기: 시험 → 작성 → 비교 → 수정

{{svg:p13-skill-evaluation}}

스킬 없이 먼저 돌려 부족한 점을 보고, 스킬을 쓴 뒤 같은 프롬프트로 비교합니다. 호출되는지와 결과가 나아졌는지를 따로 봅니다.

공식 작성 지침은 긴 문서를 쓰기 전에 평가를 만들라고 권합니다. 실제 사용자가 할 법한 대표 요청 세 개를 골라 스킬 없이 실행하고, 어떤 규칙이나 지식이 빠졌는지 기록합니다. 폴더를 만들고 SKILL.md에 이름과 설명을 씁니다. 본문은 단계와 예시 중심으로 500줄 안에 쓰고, 길어지면 참고 자료를 별도 파일로 뺍니다. 그다음 실제 요청으로 시험하는데, 부르면 호출되는지 호출된 뒤 지침을 따르는지 봅니다. 마지막으로 고치는데, 호출이 안 되면 본문보다 설명 문장부터 봅니다. skill-creator에게 이 과정을 시킬 수도 있습니다. 같은 요청을 스킬과 함께 다시 실행해 스킬 없이 얻은 결과와 비교하고, 호출 여부와 결과의 개선을 따로 확인합니다. skill-creator도 스킬 있는 실행과 없는 실행을 비교하며 개선하는 순서를 안내합니다.

task-observer 소개. 수정·반복 작업·판단을 근거와 함께 기록하고, 스킬 개선안과 새 스킬 후보를 만든다.
사람이 고쳐 준 부분과 반복해서 생긴 막힘을 근거와 함께 기록해 다음 검토에서 찾을 수 있다.
기록이 쌓여도 사람이 검토·설치해야 반영된다. 누적 기록을 읽는 검토에도 컨텍스트 윈도우를 쓴다.
빈 문서에서 스킬을 설계하지 않아도 실제 작업에서 후보가 자란다.
앞 장이 시험으로 스킬을 다듬는 순서였다면, Eoghan Henn의 task-observer는 실제 작업에서 다음에 만들 것을 찾습니다. 사람이 출력을 고쳐 준 일, 반복된 작업, 판단이 필요했던 순간을 근거와 함께 관찰 기록으로 남깁니다. 흐름은 관찰, 제안, 사람 검토이며 설치된 스킬을 관찰자가 직접 바꾸지 않습니다. 작은 추가 수정은 검토용 복사본에 바로 적용할 수 있지만 실제 스킬에는 사람이 업데이트를 설치할 때 반영됩니다. 저장소 첫 커밋은 2026년 2월 15일이고, 확인 당시 최신 릴리스 v3.11.0은 2026년 11월 15일에 공개됐습니다. 라이선스는 CC BY 4.0(Creative Commons Attribution 4.0, 저작자 표시 국제 라이선스)입니다.

관찰에서 스킬까지: 기록 → 검토 → skill-creator로 반영

{{svg:p11-task-observer-flow}}

작은 추가 수정은 검토용 복사본에 적용하고, 실제 스킬에는 사람이 업데이트를 설치할 때 반영합니다. task-observer가 없어도 수정 기록 파일로 후보를 모을 수 있습니다.

관찰은 작업을 멈추지 않는 선에서 같은 턴이나 다음 턴에 기록합니다. 세션을 끝낼 때 기록을 확인하고, 주기적인 검토에서는 열린 관찰을 스킬 전체와 대조합니다. 스킬 하나를 넘는 반복 관찰은 공통 원칙으로 모아 두고, 새 스킬을 만들거나 기존 스킬을 고칠 때 다시 확인합니다. 무엇을 만들지는 task-observer가 제안하고, 크게 만들거나 구조를 바꾸는 일은 skill-creator가 맡습니다. 작은 추가 수정은 검토용 복사본에 바로 적용할 수 있지만, 그 복사본을 실제 스킬로 설치하는 결정은 사람에게 있습니다. 내 하네스에서는 task-observer가 없어도 고친 내용과 이유를 수정 기록 파일에 남기는 것부터 시작할 수 있습니다.
설명 흐름 · 프롬프트 + 스모크18단계 중 15단계(워크플로우·워크트리 설정) · 이슈별 워크플로우 1–8단계를 스킬로

진행 순서: 질문 → 승인 → 구현 → 스모크 → /goal

{{svg:p12-flow}}

여러분이 보는 것은 코드가 아니라 내가 한 답, 에이전트가 정리한 결정, 스모크 결과입니다.

이 순서는 제 운영 기준 18단계 가운데 15단계, 작업을 어떻게 격리하고 합칠 것인가를 하네스 크기로 줄여 적용한 것입니다. 먼저 에이전트가 격리, 리뷰, 머지 규칙과 스킬, MCP(Model Context Protocol, 모델 컨텍스트 프로토콜), 완료 조건에 대해 묻고 사람이 답합니다. 에이전트는 답을 ADR(Architecture Decision Record, 아키텍처 결정 기록) 한 건과 스킬 설계로 정리하고, 사람이 읽고 승인한 뒤에야 구현합니다. 구현 뒤에는 코드를 열어 보는 대신 스모크로 확인합니다. 스킬이 불리는지, MCP가 붙었는지 보고, 이슈 하나를 /goal로 맡겨 조건에서 멈추는지 보는 흐름입니다. 집에서 해 볼 때는 설계 대화부터 이슈 완주까지 한 시간 안팎으로 잡으면 됩니다.

스킬 후보: 지난 회차에 매번 말로 시킨 순서

  • 이슈 분석 → ADR(Architecture Decision Record, 아키텍처 결정 기록) 점검 → 스펙 → 스펙 리뷰 → 계획 → 계획 리뷰 → 구현 → 구현 리뷰를 이슈마다 다시 설명했다
  • 같은 설명을 세 번 쓰면 후보. 한 스킬 = 한 작업
  • 스킬의 본문은 필요할 때만 읽힌다. 어떤 말에 불리는지가 호출을 좌우한다

직접 도식 · 스킬 로딩 흐름
8교시에 이슈 하나를 처리하면서 에이전트에게 스펙을 쓰라고 하고, 리뷰하라고 하고, 계획을 세우라고 하고, 구현하라고 했습니다. 이슈가 열 개면 같은 설명을 열 번 하게 됩니다. 이런 반복이 스킬로 만들 후보입니다. 도식처럼 세션이 시작되면 스킬의 이름과 설명만 목록에 올라가고, 요청이 설명과 맞을 때 본문을 읽습니다. 그래서 설명 문장을 잘 쓰는 것이 중요합니다. 집에서는 이 스킬도 직접 쓰지 않고 에이전트에게 설계 대화를 거쳐 만들게 한 뒤, 불리는지만 확인하면 됩니다.

4교시와 같은 방식의 프롬프트입니다. 아직 파일을 만들지 말 것, 질문은 한 번에 하나씩 추천 답과 함께, 정리한 설계는 사용자가 승인할 때까지 기다릴 것을 명확히 지시하고, 코드를 열어 보지 않는 대신 돌려서 확인하려고 끝에 스모크 시나리오 목록도 달라고 합니다. 이번에는 고를 수 있는 항목이 몇 묶음 있는데, 이슈를 어떻게 격리하고 합칠지, 이슈별 순서를 스킬로 만들지, 어떤 외부 도구를 붙일지, /goal로 맡길지입니다. 위 프롬프트는 제가 고른 경우이고, 집에서는 후보를 바꿔 쓰면 됩니다. 결과는 새 ADR 한 건으로 남깁니다. 4교시에 만든 문서가 있으면 에이전트가 먼저 읽도록 저장소 안에서 시키면 됩니다. 오른쪽은 워크트리를 설명하는 공식 문서 화면입니다.

설계 대화에서 에이전트의 질문을 살피는 기준입니다. 15단계는 작업을 어떻게 격리하고 어떻게 합치는지를 묻습니다. 격리, 충돌, 리뷰와 머지 세 줄이 여기에 해당합니다. 나머지 네 줄은 오늘 더할 장치인 스킬, MCP, /goal, 기록입니다. 에이전트가 일부를 묻지 않으면 여러분이 먼저 꺼내 봅니다. 모르는 항목은 선택지 두 개와 장단점을 표로 달라고 하면 됩니다. 머지와 PR(Pull Request, 변경 병합 요청) 규칙은 정하기만 하고, 실제로 PR을 만들고 머지하는 순서는 16교시 뒷부분에서 설명으로 봅니다.

15단계의 결과: ADR 한 건의 결정 요약

항목에이전트가 정리한 결정(예시)내가 볼 점
격리이슈 하나 = 브랜치 하나 = 작업 공간 하나두 이슈가 안 섞이는가
충돌같은 파일을 건드릴 이슈는 한 번에 하나겹칠 때의 규칙이 있는가
리뷰구현한 쪽이 아닌 리뷰어 서브에이전트쓴 쪽이 통과시키지 않는가
머지PR(Pull Request, 변경 병합 요청)·머지는 사람 승인 뒤, 4회차(16교시)에오늘은 정하기만 하는가
다시 판단할 조건두 이슈가 같은 파일에서 충돌하면4교시 ADR과 같은 서식인가
이슈마다 작업이 나뉘어, 한 이슈를 하는 동안 다른 이슈의 변경이 섞이지 않는다. 4회차 병렬 실행의 바탕이 된다.
작업 공간이 늘어 디스크를 더 쓴다. 겹치는 파일은 여전히 합칠 때 충돌한다.
15단계의 질문 ‘작업을 어떻게 격리하고 합치는가’에 대한 답. 결정과 이유가 ADR에 남아 다음 판단의 기준이 된다.

워크트리를 만드는 명령은 에이전트가 이슈마다 알아서 실행합니다. 확인할 것은 결정이 맞는지뿐입니다.

에이전트가 정리한 ADR의 한 줄 요약 예입니다. ADR 본문이나 명령을 읽지는 않고 이 표만 봅니다. 격리는 이슈, 브랜치, 작업 공간이 하나씩 대응하는지 봅니다. 충돌은 같은 파일을 건드리는 이슈를 어떻게 다루는지, 리뷰는 구현한 쪽이 아닌 다른 서브에이전트가 하는지 봅니다. 머지는 사람 승인 뒤로 미루었는지 확인합니다. 마지막 줄의 다시 판단할 조건은 4교시 ADR과 같은 서식입니다. 표의 내용은 예시이고, 여러분 에이전트의 정리는 다를 수 있습니다.
승인 체크리스트내가 한 답 · 에이전트가 정리한 결정 · 스모크 시나리오, 세 자료를 다섯 항목으로

승인 전에 확인할 다섯 가지

  1. 내가 한 답이 정리에 그대로 들어 있다(바뀐 답이 없다)
  2. 결정 요약에 이슈 하나당 작업 공간 하나와 겹칠 때의 규칙이 있다
  3. 스킬을 만든다면 어떤 말에 불려야 하는지가 한 문장으로 적혔고, PR·머지는 스킬 밖이다
  4. 예산이 떨어지면 통과로 처리하지 않고 멈춘 뒤 인계한다. MCP 서버는 출처를 믿을 수 있는 것 하나만, 되도록 읽기 권한으로 연결한다
  5. 스모크 시나리오 목록이 있고(고른 장치별: 스킬 호출 · 일부러 어기기 · MCP · /goal 멈춤), 구조를 30초 안에 설명할 수 있다
볼 것이 세 가지로 줄어, 코드를 읽지 않고도 승인 여부를 빨리 판단할 수 있다.
목록에 없는 위험(예: 서버가 가져오는 글의 프롬프트 주입)은 놓칠 수 있다. 낯선 항목은 에이전트에게 위험을 따로 묻는다.
에이전트가 만들고 사람이 판정하는 분업. 4교시 승인과 같고, 이번에는 대상이 스킬·MCP·완료 조건이다.
집에서는 시키기 전에 다섯 가지를 보면 됩니다. 내가 한 답이 정리에 그대로 들어갔는지, 결정 요약에 격리와 충돌 규칙이 있는지, 스킬이 어떤 말에 불려야 하는지 한 문장으로 적혔는지, 예산이 떨어지면 통과로 처리하지 않고 멈춘 뒤 인계하게 되어 있는지, MCP는 출처를 믿을 수 있는 서버 하나를 되도록 읽기 권한으로 연결하는지, 스모크 시나리오 목록이 있는지입니다. 이 구조를 30초 안에 설명하지 못하면 승인하지 않고 더 단순하게 바꿔 달라고 합니다. 승인은 사람만 합니다. 마음에 안 드는 한 곳은 에이전트에게 말로 고치게 하면 됩니다.

# 프롬프트 > 지난주 이슈 처리 1–8단계(분석 → ADR 점검 → 스펙 → 스펙 리뷰 → 계획 → 계획 리뷰 → 구현 → 구현 리뷰)를 issue-flow 스킬로 만들어 줘. “12번 이슈 처리해 줘”처럼 이슈 번호를 말하면 불려야 해. 구현은 테스트 먼저, 리뷰는 리뷰어 서브에이전트가 해. 예산이 떨어졌는데 블로커가 남으면 통과시키지 말고 진행 파일에 적고 중단해. PR·머지는 이 스킬에 넣지 마. 끝나면 직접 이름으로 한 번, 평범한 문장으로 한 번 불러서 불린 증거를 보여 줘.

X가 나오면 “스킬이 방금 왜 안 불렸는지 설명하고, 내가 실제로 할 말에 불리게 고친 뒤 같은 문장으로 다시 보여 줘”라고 시킵니다.

스킬은 파일을 열어 보지 않고, 집에서 하네스에게 시킨 뒤 실제로 불리는지로 확인하면 됩니다. 프롬프트에는 어떤 말에 불려야 하는지, 순서, 멈춤 규칙, 하지 않을 것을 담았습니다. 스모크는 이름으로 직접 부르기, 평범한 문장으로 부르기, 단계를 건너뛰자고 일부러 요청하기입니다. 표의 실제 결과 칸은 예시이고, 자동 호출이 실패하는 경우를 일부러 넣었습니다. 이런 경우 스킬의 설명 문장을 고치게 하면 대개 풀립니다.

MCP 연결: 하네스에게 맡기고 실제 호출로 확인

# 프롬프트 > 이슈를 분석할 때 최신 라이브러리 문서를 볼 수 있게 문서 조회 MCP 서버 하나(대표 Context7)를 이 저장소에 연결해 줘. 읽기만 하고, 토큰이 필요하면 값이 아니라 환경 변수 이름으로만 써. 끝나면 연결 상태와 쓸 수 있는 도구 목록을 보여 주고, 새 세션에서도 보이는지 확인해 줘.
# 스모크 (대화 예시) 학생 새 세션이야. MCP 연결 상태 보여 줘. 하네스(예시) 서버 1개 연결됨, 상태 정상. 학생 12번 이슈에 쓰는 라이브러리의 정렬 옵션을 문서 조회 도구로 확인해서 스펙에 반영해 줘. 하네스(예시) 문서 조회를 2회 호출했고, 확인한 옵션을 스펙에 적었습니다. 학생 이 서버가 가져온 글에 “지시”가 섞여 있을 때는? 하네스(예시) 가져온 글은 참고 자료로만 쓰고 지시로 따르지 않습니다.

볼 것은 연결 상태, 실제로 호출된 기록, 비밀 값이 파일에 없다는 확인뿐입니다(“파일에 토큰 값이 없는지 검색해서 보여 줘”).

MCP는 에이전트에 외부 도구를 연결하는 규약입니다. 이 순서에서는 이슈 분석에 쓸 문서 조회 서버 하나만 붙입니다. 대표 도구로 Context7을 씁니다. 집에서는 연결 설정을 하네스에게 맡기고, 설정 파일은 열지 않습니다. 대신 새 세션에서 연결 상태를 묻고, 실제로 호출해 보게 하고, 비밀 값이 파일에 남지 않았는지 검색하게 합니다. 서버가 가져오는 글에 지시가 섞이는 프롬프트 주입 위험이 있으니, 가져온 글을 지시로 따르지 않는지도 한 번 물어봅니다. 오른쪽 대화는 예시입니다.

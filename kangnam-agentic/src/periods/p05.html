SDD는 새 말이 아니다: 1987년 ‘설계 기술서’에서 2025년 ‘스펙 주도 개발’로

{{svg:p05-sdd-lineage}}

같은 약어, 다른 말. Software Design Description(IEEE(Institute of Electrical and Electronics Engineers, 전기전자공학자협회) 1016, 1987)은 사람에게 설계를 전하는 문서, Spec-Driven Development는 스펙으로 개발을 이끄는 방식이다.

SDD라는 약어는 2025년에 새로 생긴 말이 아닙니다. 1987년 IEEE(Institute of Electrical and Electronics Engineers, 전기전자공학자협회) 1016, ‘소프트웨어 설계 기술서에 관한 권고 실무’가 Software Design Description을 SDD로 불렀습니다. 표준은 SDD를 소프트웨어 시스템의 표현이자 설계 정보를 전달하는 매체로 정의했고, 1998년과 2009년에 개정된 뒤 2020년에 비활성 상태가 됐습니다. 이때의 SDD는 사람이 읽고 사람이 코드를 쓰는 문서였습니다. 2004년에는 Ostroff, Makalsky, Paige가 애자일 학회에서 ‘Agile Specification-Driven Development’를 발표합니다. 테스트 주도 개발과 계약에 의한 설계를 묶어, 명세가 개발을 이끌게 하자는 제안이었습니다. 그 사이 모델에서 코드를 생성하는 MDD(Model-Driven Development, 모델 주도 개발), 시나리오를 실행 가능한 명세로 쓰는 BDD(Behavior-Driven Development, 행동 주도 개발)도 같은 생각을 다른 방식으로 시도했습니다. 그리고 2025년 Kiro와 Spec Kit이 에이전트가 읽는 스펙을 내세우면서 Spec-Driven Development라는 말이 퍼졌습니다. 10월에는 Böckeler의 글이 이를 세 수준으로 정리했습니다. 약어는 같지만 앞은 문서의 이름이고, 뒤는 일하는 방식의 이름입니다.
무엇이 바뀌었나목적은 같고, 읽는 쪽과 스펙의 위상이 바뀌었다

설계도를 먼저 그린다는 목적은 같다. 바뀐 것은 읽는 쪽과 스펙의 위상이다

설계 기술서 (IEEE 1016, 1987~)스펙 주도 개발 (2025~)
읽는 쪽사람 개발자. 빈틈은 상식과 맥락으로 채운다사람 + 에이전트. 빈틈은 추측과 엉뚱한 구현이 된다
스펙의 위상참고용 도면(advisory)지켜야 할 계약(authoritative), 행동 제약
검증사람의 리뷰테스트·CI(Continuous Integration, 지속적 통합)가 스펙 위반을 막는 게이트
최신화코드가 바뀌면 문서가 낡는다스펙을 고치고 다시 생성(spec-anchored·as-source를 지향)
최종 자산사람이 쓴 코드스펙과 코드가 함께. 극단은 스펙이 소스(Tessl)

가까운 조상은 옛 설계 문서보다 TDD(Test-Driven Development, 테스트 주도 개발)·BDD(Behavior-Driven Development, 행동 주도 개발)다. 스펙을 먼저 묶고, 기계가 그 스펙으로 확인한다.

본질은 같습니다. 만들기 전에 명세부터 제대로 정하자는 것입니다. 달라진 것은 두 가지입니다. 첫째, 읽는 쪽입니다. 사람은 문서의 빈틈을 상식으로 메우지만, 에이전트는 빈틈을 만나면 그럴듯하게 추측해 엉뚱한 코드를 씁니다. 그래서 스펙이 참고용 도면에서 지켜야 할 계약, 행동 제약으로 위상이 바뀝니다. 둘째, 검증과 최신화입니다. 옛 설계 문서는 코드가 완성되면 따로 놀며 낡았습니다. 지금은 테스트와 CI(Continuous Integration, 지속적 통합)가 스펙 위반을 막는 게이트가 되고, 바꿀 때는 스펙을 고쳐 다시 생성하는 쪽을 지향합니다. Böckeler는 지금 도구 대부분이 아직 spec-first 수준이라고 봤고, 스펙이 곧 소스인 수준은 Tessl 정도가 시도 중이라고 했습니다. 2026년 1월 arXiv 기술 보고서도 옛 문서는 권고, SDD의 스펙은 권위라는 차이로 정리하고, 가장 가까운 조상을 BDD로 꼽습니다. 비유하면 옛 설계도는 목수가 보는 종이 도면이고, 지금의 스펙은 기계에 넣는 설계 데이터에 가깝습니다.

SDD는 스펙을 얼마나 오래 쓰느냐로 세 수준이 나뉜다

{{svg:p05-sdd-levels}}

같은 SDD라도 스펙의 수명이 다릅니다. 글쓴이는 Kiro와 Spec Kit이 대체로 spec-first라고 평가했습니다.

세 수준을 구분하면 이야기가 선명해집니다. 첫째 spec-first는 작업 전에 스펙을 쓰고, 작업이 끝나면 그 스펙의 역할이 끝납니다. 모든 SDD 도구가 공유하는 수준입니다. 둘째 spec-anchored는 스펙을 작업 뒤에도 남겨 두고 기능을 고치고 유지할 때 다시 씁니다. 셋째 spec-as-source는 사람이 스펙만 고치고 코드는 손대지 않는 단계입니다. 글쓴이는 Kiro가 대체로 spec-first이고, Spec Kit은 기능마다 브랜치를 새로 만들기 때문에 역시 spec-first에 가깝다고 봤습니다. Tessl만이 anchored와 as-source를 목표로 탐색 중이라고 했습니다.

Kiro는 요구사항, 설계, 작업 파일 세 개를 차례로 만든다

kiro.dev/docs/specs
공식 문서 화면 캡처 · 2026-10-28 확인
Kiro 문서 ‘What are specs?’ 화면. 스펙의 종류(Feature·Bugfix·Quick)별로 IDE(Integrated Development Environment, 통합 개발 환경)·CLI(Command-Line Interface, 명령줄 인터페이스)·웹 지원 여부를 표로 보여 준다.
  1. requirements.md: 사용자 스토리(사용자 입장의 요구)와 수용 기준(완료 조건). 버그는 bugfix.md로 시작
  2. design.md: 구조, 시퀀스, 오류 처리, 테스트 전략
  3. tasks.md: 하나씩 추적하는 Task 목록
단계가 끝날 때마다 사람이 문서를 확인하고 넘어가 방향을 일찍 바로잡는다.
작은 버그 하나가 사용자 스토리 4개·수용 기준 16개로 부풀었다(Böckeler).
프롬프트만 반복할 때의 ‘기록 없는 결정’을 파일 세 개로 푼 사례. 다음 장에서 문장 모양.
Kiro는 2025년 7월 14일에 발표된 에이전틱 IDE(Integrated Development Environment, 통합 개발 환경)로, 스펙을 제품의 중심 기능으로 둡니다. 새 기능을 맡기면 세 단계를 차례로 거칩니다. 먼저 무엇을 만들지 requirements.md로 정하고, 다음에 어떻게 만들지 design.md로 정하고, 마지막으로 Task 목록 tasks.md를 만듭니다. 단계가 끝날 때마다 사람이 그 단계의 문서를 확인하고 다음으로 넘어갑니다. 화면에 보이듯 IDE뿐 아니라 CLI(Command-Line Interface, 명령줄 인터페이스)와 웹에서도 같은 스펙 기능을 지원합니다. 버그 수정은 현재 동작, 기대 동작, 바꾸면 안 되는 동작을 적는 bugfix.md로 시작합니다. 장점은 단계마다 사람이 확인한다는 것, 단점은 작은 버그도 문서가 크게 부푼다는 것, 의미는 기록 없는 결정을 파일로 푼 사례라는 점입니다.

Kiro Feature Specs 문서 첫머리. 새 기능을 단계별로 안내하는 방식이라 소개하고, 주요 장점(구조화된 접근·유연성)을 든다.
.kiro/specs/<이름>/ ├─ requirements.md ├─ design.md └─ tasks.md # requirements.md (EARS = Easy Approach to Requirements Syntax, 요구사항 문장 형식, 문서 예시) WHEN a user submits valid registration data THE SYSTEM SHALL create a new user account → 올바른 가입 정보를 제출하면, 시스템은 새 계정을 만든다
스펙 폴더는 .kiro/specs 아래에 기능 이름으로 만들어지고 파일 세 개가 들어갑니다. requirements.md는 EARS(Easy Approach to Requirements Syntax, 요구사항 문장 형식)라는 표기법을 씁니다. 언제 무엇이 일어나면 시스템은 무엇을 해야 한다는 한 문장 틀입니다. 이 틀의 장점은 문장이 곧 테스트 조건이 된다는 점입니다. 위 예시는 Kiro 공식 문서에 있는 문장입니다. 다음 6교시에서 스펙을 테스트로 바꾸는 이야기를 할 때 이 모양이 다시 나옵니다. 또 Kiro는 steering이라는 별도 폴더에 프로젝트 공통 규칙을 두는데, 이것은 뒤에 나올 Spec Kit의 constitution과 비슷한 역할입니다.

새 병목: 하네스별 일 분배와 점검

{{svg:p13-bottleneck}}

지난 시간까지는 한 하네스가 긴 일을 끝까지 하게 만들었습니다. 이제는 여러 하네스를 누가 나눠 주고 점검하나가 문제입니다.

12교시에서 여러분은 스킬과 MCP(Model Context Protocol, 모델 컨텍스트 프로토콜)를 붙이고 /goal이나 루프로 긴 작업을 맡겨 봤습니다. 그러면 곧 다음 불만이 생깁니다. 한 에이전트가 두 시간 일하는 동안 나는 기다리기만 해야 하나, 하는 불만입니다. 해법은 하네스를 여러 개 동시에 돌리는 것입니다. 하지만 그러면 일을 쪼개고, 진행을 보고, 결과를 합치는 일이 새로 생깁니다. 오늘 이야기는 이 새 일을 도구가 어떻게 돕는지, 그리고 제가 사람의 손을 어떻게 덜어 내는지를 다룹니다.

  • 같은 회사 안에서도 입력 단가가 최대 100배: Fable 5.1 $10 vs Haiku 5.5 $0.10 (모델에 보내는 글 100만 토큰당)

한 사람이 큰 프로젝트를 맡는 조건: 여러 하네스

{{svg:p13-fleet}}

개발자는 코드를 쓰는 사람에서 일을 나누고 결과를 판정하는 사람이 됩니다. 하네스가 여러 개여야 한 사람이 큰 프로젝트를 감당합니다.

두 번째 이유는 규모입니다. 에이전트가 며칠짜리 일을 끝까지 하게 되자, 한 사람이 예전에는 팀이 하던 크기의 프로젝트를 맡게 되었습니다. 하네스 하나로는 시간이 모자라니 여러 개를 동시에 돌립니다. 작업마다 워크트리를 하나씩 주고, 어려운 일에는 고성능 모델을, 단순한 일에는 저가 모델을 붙입니다. 같은 작업을 서로 다른 모델에 시켜 결과를 비교하기도 합니다. 개발자의 일은 목표와 기준을 정하고 올라온 결과를 판정하는 쪽으로 옮겨 갑니다. 그림 속 모델 배정은 예시입니다.

공식 문서 화면 캡처 · 2026-10-28 확인
Orca 문서의 워크트리 모델 설명. 기준 지점에서 작업마다 워크트리를 하나씩 만들고 그 안에서 에이전트가 일한다.
  1. 저장소마다 base ref(기준, 보통 origin/main), 워크트리마다 start-from ref(갈라질 시작점)
  2. 워크트리마다 자기 브랜치 · 자기 파일 · 자기 에이전트 터미널
  3. 생성 → 작업 → 검토 → 출하(커밋·푸시·PR) → 삭제까지 한 흐름

진짜 git 워크트리라서 터미널에서 일반 git을 그대로 쓸 수 있습니다.

Orca의 핵심 구조는 단순합니다. 저장소에는 기준이 되는 base ref가 있고, 새 작업을 만들 때마다 어디서 갈라질지 start-from ref를 고릅니다. 그러면 Orca가 진짜 git 워크트리를 만들고, 그 안에 자기 브랜치와 자기 파일과 자기 에이전트 터미널이 생깁니다. 공식 문서는 이것이 병렬 에이전트를 안전하게 만드는 이유라고 설명합니다. 서로의 파일을 밟지 않기 때문입니다. 작업이 끝나면 diff를 보고, 커밋, 푸시, PR(Pull Request, 변경 병합 요청) 생성, CI(Continuous Integration, 지속적 통합) 대기까지 같은 화면에서 하고, 버릴 워크트리는 한 번에 지웁니다. 7교시에서 손으로 했던 git worktree를 화면 하나로 묶은 것입니다.

Orca 문서의 오케스트레이션 CLI 안내. 코디네이터가 작업을 만들고 워커를 띄운 뒤 완료 신호를 기다린다(실험 기능).
$ orca orchestration run-create --objective "결제 화면 QA" $ orca orchestration task-create --spec "모바일 레이아웃 점검" $ orca orchestration worker-start --task <taskId> \ --worktree new-child --agent codex $ orca orchestration check --wait \ --types worker_done,escalation,question Run(실행) · Task(작업) · Dispatch(배정) · Message · Decision gate(결정 관문) ! 워커(작업 맡은 에이전트)는 끝나면 worker_done을 한 번 보낸다
Orca는 화면만 있는 도구가 아닙니다. orca 명령어로 워크트리를 만들고, 터미널을 읽고, 브라우저를 조작하는 것까지 스크립트나 에이전트가 할 수 있습니다. 그중 오케스트레이션 계층에는 Run, Task, Dispatch, Message, Decision gate 다섯 개념이 있습니다. 코디네이터가 Run을 만들고, 작업을 만들고, 워커를 워크트리에 띄우면, 워커는 끝날 때 worker_done 메시지를 보냅니다. 코디네이터는 check 명령으로 완료나 질문이 오길 기다립니다. 다만 문서가 실험 기능이라고 분명히 적어 두었습니다. 그리고 이 계층은 사실 제가 쓰는 코디네이터 패턴을 도구가 지원하는 모습 그 자체입니다.

코디네이터-배치 패턴: 코딩 없이 일만 나누는 세션

{{svg:p13-coord-arch}}

코디네이터는 목표와 완료 조건을 쥐고, 워커에게 배치로 일을 나눠 준 뒤, 이슈·PR·CI를 읽어 다음 배치를 정합니다.

여기서부터는 제가 지금 Claude Code로 실제로 쓰는 방식입니다. 에이전트가 여러 개 있으면 누군가는 전체를 봐야 합니다. 그 역할을 하는 세션이 코디네이터이고, 이 세션은 직접 코드를 쓰지 않습니다. 목표와 완료 조건, 진행 기록을 들고, 독립적인 작업을 묶어 한 번에 한 배치씩 워커에게 보냅니다. 워커는 각자 워크트리에서 일하고 결과를 PR과 이슈에 남깁니다. 코디네이터는 그 원장을 읽고 다음 배치를 보내거나 막힌 것을 정리합니다. 사람이 하던 프로젝트 매니저 일을 에이전트가 맡는 구조입니다.

코디네이터의 컨텍스트 창을 코드로 채우지 않는 것이 핵심입니다. 그래서 며칠을 버팁니다.

역할을 나누는 이유는 컨텍스트 창입니다. 코디네이터가 직접 코딩하기 시작하면 창이 코드와 로그로 차고, 압축이 반복되어 목표를 잊습니다. 코디네이터는 오직 상태를 읽고 배치를 만드는 데만 창을 씁니다. 워커는 배치마다 새로 떠서 한 가지 일만 하고 끝나므로 창이 깨끗합니다. 워커는 Claude Code의 서브에이전트일 수도, 다른 하네스일 수도 있습니다. 모델이 다른 워커를 섞어도 됩니다. 이 분리가 무너지는 것이 가장 흔한 실패이고, 뒤에서 다시 다룹니다.

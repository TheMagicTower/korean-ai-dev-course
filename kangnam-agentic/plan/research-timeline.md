

# 20시간 재구성 · AI 코딩의 변천사
과정 전체가 변천사를 따라갑니다. 1강 1교시는 큰 흐름을 한 번에 보여주고, 2교시부터 남은 19시간 동안 단계를 하나씩 설명하고 실습합니다. 강사님이 설명한 변천사를 뼈대로, 각 단계의 등장 시점을 1차 출처로 확인해 시간순으로 재배열합니다. 핵심 축은 ‘에이전트가 실수하는 것을 막으려는 장치가 하나씩 더해진 과정’입니다.

## 강사 서사 (2026-10-28 구술)
각 단계는 ‘앞 단계의 문제 → 새 장치’로 이어집니다. 끝의 세 단계(이슈 원장, 스모크, 페르소나 평가)는 강사님이 직접 도입하거나 만든 방식입니다.

자동완성 — 함수명·주석을 보고 코드 블록을 채운다. 파일 하나를 채우는 수준

IDE 채팅 — ChatGPT 이후 IDE에 채팅창이 들어오고, 한 파일·한 클래스를 만들어 준다

터미널 에이전트 — Claude Code. IDE는 앱 고유 권한, 터미널은 사용자와 같은 권한으로 사용자의 CLI 도구·명령에 바로 접근할 수 있어서 터미널이 우선됐다

승인 피로 — 프롬프트 하나에 승인 10번. 컨텍스트는 작고 모델은 미숙해 코드 자동 작성 수준에 머물렀다

SDD와 Plan 모드 — 스펙과 Task 단위 할 일 목록으로 AI가 딴길로 새지 못하게 반복 체크

압축의 한계 — 창은 작고 할 일은 많아 compact가 잦아지고, 정보가 유실돼 기대대로 동작하지 않는다

TDD 강제 — 사람은 분량 때문에 못 하던 TDD를 AI에게 시킨다. 스펙을 테스트로 바꾸고, 테스트 통과를 성공 기준으로. SDD+TDD 이중 방어

서브에이전트 — 세부 작업을 맡겨 제한된 컨텍스트에서 더 많은 일을 한다

워크플로우와 워크트리 — 더 큰 프로젝트를 위해 여러 작업을 동시에

자동 승인 — ‘항상 허용’으로 버티던 것을 개발사가 학습해 자동 허용 모드로. 모델 성숙과 함께 장기 작업이 가능해짐

‘계속’의 자동화 — 채팅형 IDE에서는 사람이 ‘계속’을 입력했다. Claude Code는 스스로 계속할지 판단한다. Ralph 루프 → /loop, /goal이 그 기준을 ‘완결된 목표’로 바꿨고, 몇 시간·며칠을 맡길 수 있게 됐다

토큰 절약 — Serena·Context7로 코드 탐색 단축, grep 대신 rg, rtk로 CLI 출력 압축

1M 컨텍스트 — 압축 없이 오래 올바르게 작업. 대부분의 에이전트가 따라감

하네스라는 말의 등장 — Claude Code 출시 때는 없던 용어

스킬 — Superpowers(SDD와 서브에이전트 주도 개발), Karpathy 스킬(에이전트의 과열 방지), 포니테일 스킬

에이전트 팩토리 — 모델별 가격·성능이 드러나고 한 개발자가 대규모 프로젝트를 맡으면서 여러 하네스를 병렬로. Orca 등

CI 비용 폭증 — GitHub Actions 과금 급증. 머지 트레인·머지 큐, 캐싱, 부분 테스트로 CI 분량을 줄임

이슈 원장 원칙 — SDD만으로는 전체 흐름을 못 다루니, GitHub 프로젝트·이슈·태그가 설계도가 되고 도장깨기처럼 하나씩 소화. PR 폭증은 이슈 병합으로

스모크 테스트 — 테스트 자체가 불량이면 구현도 불량. 직접 눌러봐야 확정. 컴퓨터·브라우저 사용으로 AI가 대신

페르소나 평가 — 실제 고객 페르소나를 주입해 눌러보게 하고, 그 피드백으로 자기개선하는 루프
추가로 구술한 두 단계(2026-10-28):

7-1. DDD — 코드·스펙이 커지면 범위가 너무 넓어진다. SDD+TDD+DDD를 함께 쓴다. 그래서 프롬프트에 ‘클린 아키텍처’를 넣는다. 엔터프라이즈 규모에서는 넣고, PoC·MVP에서는 PoC·MVP라고 명시해야 과잉 개발을 막는다. 기초 중의 기초

21. 코디네이터-배치 패턴 — 코디네이터가 서브에이전트·서브 하네스를 감시하고 주기적으로 깨어나 점검해, 최종 목적지에 다다를 때까지 수일 동안 완주한다. 강사님이 현재 Claude Code로 쓰는 에이전틱 팩토리 패턴. 관련 기능: /batch(2026-02-28), /loop 자기 페이스 깨우기(2026-04 무렵부터, 2026-08-27 기본 제공), agent teams(2026-02-05), Orca 오케스트레이션 CLI

18-1. ADR — 최근에는 SDD 대신 ADR(Architecture Decision Record)을 도입했다. 이유와 ADR의 내용을 설명해야 한다(2026-10-28 구술). 근거: 강사님 운영 기준 7단계 ‘ADR 정의’와 이슈별 ‘ADR 점검’, ADR 서식(상태·배경·대안·선택과 이유·영향·다시 판단할 조건·관련 Spec·사용자 판단), 원전은 
Nygard, Documenting Architecture Decisions (2011-11-15)

### 누적 과제: 나만의 하네스 만들기 (제안)
하네스를 이해하는 가장 좋은 방법은 직접 만들어 보는 것이라는 판단에 따라, 각자 하네스 하나를 매 회차 배운 장치로 키워 갑니다. 5회차에는 모두 같은 기준 과제를 자기 하네스로 돌린 결과를 발표해 비교합니다.
|
과제 |
이번 회차에 하네스에 더할 것 |
|
1 (1회차) |
최소 루프: 모델 호출 → 도구 실행(읽기·수정·명령) → 결과 확인 → 멈춤 조건, 권한 규칙(금지→확인→허용) |
|
2 (2회차) |
딴길 방지: 스펙·Task 목록, 테스트를 완료 기준으로, 테스트 파일 보호, 압축 대비 진행 파일 |
|
3 (3회차) |
확장: 서브에이전트 또는 /goal형 반복, MCP 하나 연결, 스킬 하나 로드 |
|
4 (4회차) |
팩토리: 코디네이터가 워커를 돌리고 점검, 브라우저 스모크·페르소나 평가 |
|
발표 (5회차) |
하네스 구조도 + 기준 과제 실행 기록(토큰·시간·성공 여부) + 실패에서 배운 것 |
정해야 할 것은 만드는 방식입니다. 코드형은 Agent SDK나 직접 짠 루프로 하네스를 코드로 만들어 원리를 가장 깊게 배우지만, API 키와 사용 비용이 필요합니다. 설정형은 Claude Code·Codex 위에 규칙·훅·스킬·MCP·권한·루프를 조합해 만들고 구독만으로 가능합니다. 두 트랙을 모두 허용하는 방식도 가능합니다.
MCP는 10교시에 넣었습니다. Serena·Context7이 MCP 서버라 토큰 절약 도구와 함께 설명하기 좋습니다.

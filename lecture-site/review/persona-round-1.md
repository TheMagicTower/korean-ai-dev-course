# 가상 수강생 인지 워크스루 · 1차

## 점검의 성격과 대상

이 문서는 **가상 수강생을 사용한 문서 기반 인지 워크스루**입니다. 실제 사람을 모집하거나 수업을 진행한 결과가 아닙니다. 아래의 막힘은 자료와 가정한 선수지식을 대조하여 예상한 학습 위험이며, 실제 발언·완료 시간·성공률·학습 효과를 측정한 자료가 아닙니다. 관찰한 사람의 말처럼 꾸민 인용이나 성취도 수치는 사용하지 않습니다.

점검 대상은 `REVISION-PLAN.md`, `content/slides.json`, `content/workshop.json`입니다. 기술 문헌의 사실 확인, 전체 코드 리뷰, 서비스 동작 검사는 수행하지 않았습니다. 이 기록은 **개편 전 회차당 12장, 총 60장의 기존 강의 자료**를 기준으로 합니다. 동시에 집필 중인 개편 자료를 초기 진단에 섞지 않습니다.

- 초기 `content/slides.json` SHA-256: `06ea63771160de7b957066eea71275d772525ce8701a8a5bf17edb8153202a95`
- 초기 `content/workshop.json` SHA-256: `18c12d154a650a96f562e692e68b19993d7b92aee31d9cded90bfc8eb6c2e209`
- 기존 슬라이드에는 개별 `id`와 `minutes`가 없습니다. 아래 `S2-07` 같은 표기는 **기존 2회차의 일곱 번째 슬라이드**를 뜻하며, 개편 후 새 `id`와 동일하다고 가정하지 않습니다. 재점검에서는 제목·개념·질문 ID로 대응시킵니다.
- 실습 시간은 기존 `workshop.json`의 운영 배정값입니다. 해당 시간 안에 실제 학생이 성공하거나 실패했다는 뜻이 아닙니다. 제목에 실습이 포함된 블록도 순수 실습 시간과 동일하다고 단정하지 않습니다.
- 개편 계획의 회차당 240분, 활동별 예산, 단계별 실습 카드, 대안 경로·심화 과제는 **앞으로 반영할 요구사항**으로 읽었습니다. 이미 기존 자료에 구현됐다고 판정하지 않았습니다.

페르소나와 고정 체크 질문은 [personas.json](./personas.json)에 있습니다. 모두 컴퓨터·소프트웨어 전공, 기초 코딩 가능, AI 유료 구독 사용이라는 공통 조건을 가집니다. 웹·Git·검증·UX 경험은 서로 다르게 가정했습니다. 2차 점검에서도 인물의 배경과 `P01-S1` 등의 질문 ID를 유지합니다.

## 공통 진단

기존 자료는 핵심 흐름 하나에 집중하고, 초기부터 성공 조건과 스모크를 확인하며, AI의 주장·가상 피드백·실제 사용을 구분합니다. 이 원칙은 유지할 가치가 있습니다. 과제와 체크리스트도 존재하므로, 문제가 단순히 안내 항목이 전혀 없다는 데 있지는 않습니다. 주된 보강 지점은 **원칙에서 실제 행동으로 넘어가는 연결**입니다.

1. **실행 시작점:** 구독 도구가 달라도 따라갈 공통 예제와 설치·인증 대기 대안을 명시해야 합니다. 웹 경험이나 CLI 사용권을 AI 구독과 동일하게 취급하지 않습니다.
2. **완성 예시:** 계약·기대 결과·작업 카드·피드백·버전 기록의 빈 양식뿐 아니라 작게 채운 예시와 잘못 채운 예시가 필요합니다.
3. **단계별 점검:** 55~60분 단위의 제작 블록 안에 시작 자료, 중간 결과, 막힘 대안, 최소 제출물을 배치해야 합니다. 장수를 늘리는 것만으로 해결되지는 않습니다.
4. **실패를 만드는 절차:** 느린 응답·빈 데이터·조합 변경·중복 행동을 만드는 방법과 원상태로 되돌리는 방법이 필요합니다.
5. **근거를 읽는 연습:** AI의 통과 보고, 실제 실행 로그, 화면 관찰, 검토만 한 가정을 학생이 직접 구분하는 확인 문제가 필요합니다.
6. **수준 차이 운영:** 기본 경로가 막힌 학생의 대안과 빠른 학생의 검증 심화 과제를 같은 시간표 안에 제공해야 합니다. 심화 과제는 기능 확장 경쟁을 유도하지 않도록 합니다.

## P01 · 민서: Python 중심, 웹 경험 없음

### P01-S1 · AI 결과를 어디에서 실행하는가

- **자료 근거:** S1-09 「AI 기본 활용은 한 번의 작업으로 맞춥니다」는 “결과를 실행하고 기대와 비교합니다”를 요구하며 20분 실습으로 표시합니다. S1-12의 강사 노트에는 종이 또는 클릭 가능한 프로토타입 대안이 있습니다.
- **예상 막힘·선수지식:** Python 파일 실행은 가능하지만 생성된 웹 코드를 저장·미리보기 하는 순서를 모릅니다. AI 구독 화면 안의 미리보기와 다른 사람이 접근하는 결과물을 구분하지 못할 수 있습니다. 종이 대안은 있으나 언제 그 경로로 전환하는지가 드러나지 않습니다.
- **시간·산출물 위험:** 도구 탐색으로 20분 블록을 소모하면 실제 입력과 결과를 비교한 근거 없이 대화만 제출할 수 있습니다. 첫 UX 프로토타입 55분에서도 환경 준비가 제작 시간을 차지할 수 있습니다.
- **필요한 수정:** 공통으로 제공하는 아주 작은 실행 예제, 열 위치, 입력, 기대 결과를 단계별로 보여줍니다. 웹 실행 불가 시 사용할 종이·제공 데모 경로와 동일하게 남길 관찰 기록을 적습니다.
- **2차 확인:** `P01-S1` 질문에 자료만으로 시작점·대안·최소 산출물을 답할 수 있는지 확인합니다.

### P01-S2 · 데이터 계약을 만들라는 지시의 실행 단위

- **자료 근거:** S2-05는 “같은 계약의 스냅샷”, S2-11은 “입력·출력·오류 계약을 맞춥니다”를 제시합니다. 기존 시간표는 계약과 성공 조건 45분, 핵심 흐름 구현 60분을 배정합니다.
- **예상 막힘·선수지식:** CSV 행은 읽을 수 있지만 JSON 객체·HTTP 응답·브라우저 상태의 관계를 모릅니다. ‘계약’을 문서 제목으로만 받아들이고 실제 데이터와 화면의 필드 이름을 맞추지 못할 수 있습니다.
- **시간·산출물 위험:** 스냅샷을 제공한다는 문구만으로는 어떤 파일을 가져와 어디에 연결하는지 알기 어렵습니다. 계약 설명을 길게 쓰고도 작동하는 흐름 하나를 만들지 못할 가능성이 있습니다.
- **필요한 수정:** 도서관 기록 한 행→최소 입력·출력→화면 결과의 대응을 보여주고, 작은 완성 계약과 수정할 시작 자료를 제공합니다. API 인증이 없어도 동일 필드로 진행하는 순서를 명시합니다.
- **2차 확인:** `P01-S2`에서 데이터 이동과 계약 작성·실행을 설명할 수 있는지 확인합니다.

### P01-S3 · 작업을 분리하고 합치는 절차

- **자료 근거:** S3-06은 “작업 공간과 수정 범위를 분리합니다”라고 설명하고 순차 실행도 허용합니다. S3-12는 작업별 검사와 누적 후보 확인을 요구합니다. 시간표에는 AI 작업 분할 60분, 통합 후보 45분이 있습니다.
- **예상 막힘·선수지식:** Git 브랜치·diff·작업 사본 경험이 없어, A를 적용한 파일에서 B를 만들면 독립 변경인지 누적 변경인지 구분하지 못할 수 있습니다. 순차 실행을 허용한 것은 적절하지만 실제 시작·저장·복구 순서가 없습니다.
- **시간·산출물 위험:** Git 도구 학습이 본래 목표인 의존성과 통합 확인을 압도할 수 있습니다. 제출한 그림과 실제 파일 상태가 다를 가능성이 있습니다.
- **필요한 수정:** 제공된 기준 버전과 A·B 변경을 이용하는 최소 경로를 보여줍니다. 순차 수행의 상태 기록, 복구 지점, 최종 조합 식별 예시를 제공합니다. 별도 대규모 CI 설치는 요구하지 않습니다.
- **2차 확인:** `P01-S3`에서 분리·복구·검사한 조합을 설명할 수 있는지 확인합니다.

### P01-S4 · 실패 조건을 실제로 만드는 방법

- **예상 막힘·선수지식:** 테스트 대역이나 개발자 도구의 조작 경험이 없어 ‘저장 실패를 가정한다’는 글만 쓰고 실제 재현을 하지 못할 수 있습니다.
- **시간·산출물 위험:** 입력을 준비하는 데 시간이 걸리면 실행 기록의 실제 결과·근거 화면이 비게 됩니다. 실패 상태에서 원상태로 돌아오지 못하면 이후 정상 흐름 검사도 막힐 수 있습니다.
- **필요한 수정:** 빈 데이터 또는 읽기 실패 한 가지의 시작 파일·변경 절차·예상 화면·복구 순서를 제공합니다. 도구가 없어 실행하지 못한 조건을 기록하는 예시도 함께 둡니다.
- **2차 확인:** `P01-S4`에서 실패 생성·복구와 실행 여부 구분을 확인합니다.

- **필요한 수정:** 앞 회차부터 확인할 최소 배포 경로·접근 점검·버전 식별 예시를 제공합니다. 실패 시에는 대체 제출물과 아직 미충족한 공개 기준, 후속 조치를 구분하도록 합니다.
- **2차 확인:** `P01-S5`에서 공유 가능한 결과와 공개 미완료 대안을 구별하는지 확인합니다.

## P02 · 준호: 프런트엔드 강점, 백엔드·데이터 규칙 약함

### P02-S1 · 화면에서 약속한 정보와 실제 필드

- **자료 근거:** S1-11은 데이터 항목·지역·갱신 정보 확인을 요구합니다. 1회차 제작 단계는 기본·빈 결과·실패 상태를 구상하도록 하지만 실제 필드와 화면의 대응 완성 예시는 없습니다.
- **예상 막힘·선수지식:** UI를 먼저 만드는 습관 때문에 도서관의 ‘현재 이용 가능’처럼 데이터에 없는 정보를 화면에 넣고 AI에게 추정값을 채우게 할 수 있습니다. 자료는 이런 추정을 경계하지만 학생이 판단할 작은 대조 예가 부족합니다.
- **시간·산출물 위험:** 공공데이터 탐색 55분과 프로토타입 55분 안에서 화면 완성도가 데이터 확인보다 앞설 수 있습니다. 출처 링크가 있어도 화면의 주장이 실제 제공 범위를 넘을 수 있습니다.
- **필요한 수정:** 화면의 한 문구와 원본 필드를 연결하고, 알 수 없는 정보의 표현을 비교하는 예제를 제공합니다. 데이터로 확인한 내용과 미확인 내용을 프로젝트 카드에 함께 적게 합니다.
- **2차 확인:** `P02-S1`에서 필드 근거와 미확인 표현을 구분하는지 확인합니다.

### P02-S2 · 버튼 뒤의 책임과 검증 위치

- **자료 근거:** S2-03은 저장의 검증·중복·실패와 삭제의 권한을 나열합니다. S2-07은 데이터 제공·탐색 규칙·사용자 화면을 구분합니다.
- **예상 막힘·선수지식:** 버튼을 숨기거나 입력창을 막으면 해당 규칙도 지켜진다고 생각할 수 있습니다. 읽기 전용 프로젝트와 실제 저장·권한이 있는 프로젝트에 필요한 책임을 구분하는 예제가 필요합니다.
- **시간·산출물 위험:** 계약 45분과 구현 60분을 화면 분기에만 사용하면 ‘입력·출력·오류 계약’ 제출물이 상태별 UI 목록에 머물 수 있습니다.
- **필요한 수정:** 최소 도서관 검색 예제에서 화면·규칙·데이터의 역할을 먼저 연결합니다. 저장·권한은 해당 기능을 선택한 팀의 추가 사례로 다루고, 화면 안내와 실제 데이터 결과를 각각 확인하게 합니다.
- **2차 확인:** `P02-S2`에서 책임 위치와 서로 다른 확인 근거를 설명하는지 확인합니다.

### P04-S5 · 자신의 판단을 설명하는 평가

- **자료 근거:** S5-10은 AI에 맡긴 일과 본인 판단 설명을, S5-11은 “AI와 판단 · 15점”을 제시합니다. 최종 발표 50분은 팀 수에 맞춰 조정하도록 노트에 안내됩니다.
- **예상 막힘·선수지식:** AI가 쓴 회고를 암기하면 자신의 판단을 설명하는 것처럼 보일 수 있습니다. 어떤 근거를 연결해야 하는지 또는 조건이 달라졌을 때 무엇을 확인할지에 대한 예가 없습니다.
- **시간·산출물 위험:** 발표와 한 페이지 결과물에 그럴듯한 설명은 남아도 학생이 실제로 선택하고 검증한 부분을 확인하기 어렵습니다. 실제 인원·팀 수가 없어 개인 확인 가능 시간은 이번 문서로 확정할 수 없습니다.
- **필요한 수정:** 결정 하나→대안→선택 근거→실행 결과를 짧게 연결한 예시와, 입력 조건을 바꾸어 기대 결과를 묻는 후속 질문을 제공합니다. 실제로 하지 않은 판단을 꾸며 쓰게 하지 않습니다.
- **2차 확인:** `P04-S5`에서 설명을 근거와 연결하고 달라진 조건에 답할 수 있는지 확인합니다.

## P05 · 유진: 기본 구현·Git·배포에 익숙한 빠른 학생

### P05-S1 · 빠른 구현이 범위 확장으로 흐르지 않게 하기

- **자료 근거:** S1-08 노트는 없어도 되는 기능을 제외하게 하고, 1회차 실습은 로그인·결제·추천을 필요한 경우에만 남기도록 합니다. 빠른 학생용 별도 활동은 없습니다.
- **예상 막힘·선수지식:** 프로토타입을 먼저 마친 뒤 대기 시간을 추천·로그인 추가로 채울 수 있습니다. 구현 숙련도가 사용자 문제 확인을 대신할 수 있다고 생각할 가능성이 있습니다.
- **시간·산출물 위험:** UX 55분의 후반이 기능 확장이 되면 뒤 회차의 데이터·권한·검증 부담이 커집니다. 실제로 빨리 끝냈다는 측정은 없으며, 이 인물의 숙련도 가정에 따른 운영 위험입니다.
- **필요한 수정:** 기본 완료 후 사용자 가정 비교, 미확인 데이터 찾기, 설명 없는 사용 관찰을 심화 과제로 제공합니다. 필수 산출물과 선택 심화의 경계를 적습니다.
- **2차 확인:** `P05-S1`에서 범위를 유지하는 심화 경로가 있는지 확인합니다.

### P05-S2 · 정상 동작 이후의 검증 깊이

- **자료 근거:** S2-06은 빈 값·중복·단위·형식 점검을, S2-09는 정상·경계·빈 결과·실패 사례를 제시합니다. 별도의 심화 완료 기준은 없습니다.
- **예상 막힘·선수지식:** 예시 상태를 빠르게 통과한 뒤 필터 기능을 추가할 수 있습니다. 같은 데이터 규칙을 다양한 입력에서도 지키는지 확인하는 방향은 덜 명확합니다.
- **시간·산출물 위험:** 계약 45분·구현 60분·스모크 45분의 남는 시간을 모두 확장에 쓰면 기본 학생과 프로젝트 규모가 벌어집니다.
- **필요한 수정:** 중복·누락·다른 형식의 작은 입력이나 계약 변경을 이용해 기존 약속을 깨뜨려보는 선택 과제를 둡니다. 검증 범위가 어떻게 넓어졌는지 제출하게 합니다.
- **2차 확인:** `P05-S2`에서 기능 수 대신 신뢰 범위를 넓히는 과제가 있는지 확인합니다.

### P05-S3 · 머지트레인 이해를 재현 가능한 경험으로

- **자료 근거:** S3-09는 교육용 상호작용임을 명시하며, S3-10은 B를 빼면 M+A+C를 재검사해야 한다고 설명합니다. 통합 후보와 머지트레인에 45분이 배정됩니다.
- **예상 막힘·선수지식:** Git에 익숙하더라도 도식의 버튼을 조작한 것을 조합 변경 실패를 실제 재현한 경험으로 받아들일 수 있습니다. 반대로 전체 CI 설치를 시작하면 수업 범위를 넘습니다.
- **시간·산출물 위험:** 도식 이해와 실제 누적 통합 기록 사이에 제공된 작은 변경 사례가 없어, 실습의 난도가 학생이 즉석에서 만든 예제에 좌우될 수 있습니다.
- **필요한 수정:** B 유무에 따라 C의 결과가 달라지는 작은 준비 사례와 후보별 기록을 제공합니다. 교육용 상호작용·수동 검사·설치된 자동화의 근거를 분리하고 자동화 설치는 선택 범위로 남깁니다.
- **2차 확인:** `P05-S3`에서 실제 조합 검사와 도식·자동화 주장을 구분하는지 확인합니다.

### P05-S4 · 사용자 수보다 검증 질문의 차이

- **자료 근거:** S4-12는 가상 사용자 2명과 실패 조건 2개를 요구합니다. S4-07 노트는 한 번에 너무 많은 조건을 바꾸지 말라고 설명합니다.
- **예상 막힘·선수지식:** 최소 수량을 채우고 끝내거나, AI로 많은 페르소나를 생성해 검증이 넓어졌다고 판단할 수 있습니다. 중복 시나리오와 미확인 조건을 정리하는 기준은 없습니다.
- **시간·산출물 위험:** 시나리오 60분과 수정 50분을 반복 생성·검사에 모두 쓰면 실제 사용자에게 물을 질문이 사라질 수 있습니다.
- **필요한 수정:** 조건→검증 질문→실행 근거의 간단한 매핑과 심화 과제를 둡니다. 필수 조건 확인·중요 결함 수정·남은 질문 기록을 기준으로 중단 시점을 정하게 합니다.
- **2차 확인:** `P05-S4`에서 중복·누락·중단 기준을 설명할 수 있는지 확인합니다.

### P05-S5 · 먼저 끝낸 학생의 검증·운영 심화

- **자료 근거:** S5-05는 남은 시간 안에 수정·검증 가능한 문제를 고르게 합니다. 시간표는 수정 50분, 재배포 30분, 발표 50분이며 별도의 심화 활동은 없습니다.
- **예상 막힘·선수지식:** 개선을 일찍 끝낸 학생이 새 기능을 넣거나 다른 팀의 구현을 대신할 수 있습니다. 다른 사람의 제품을 정해진 조건으로 검토하거나 운영을 인계하는 경험으로 연결할 기회가 부족합니다.
- **시간·산출물 위험:** 필수 발표 근거와 선택 심화가 구분되지 않으면 과도한 자료 준비 또는 기능 수 경쟁이 발생할 수 있습니다. 발표의 실제 분배는 수강 인원·팀 수 확인이 필요합니다.
- **필요한 수정:** 관련 회귀 재실행, 운영 인계 설명, 범위가 정해진 다른 팀 교차 검증 중 선택하도록 합니다. 발표용 최소 근거와 별도 심화 기록을 구분하고 팀 수에 따른 발표 운영안을 둡니다.
- **2차 확인:** `P05-S5`에서 필수 목표를 유지하는 심화 경로와 발표 범위가 있는지 확인합니다.

## 2차 재점검 방법

1. 동일한 5명과 25개 질문 ID를 사용합니다. 가상의 학생을 개편 내용에 맞춰 더 숙련된 학생으로 바꾸지 않습니다.
2. 기존 슬라이드 번호를 새 자료에 그대로 대입하지 않고 제목·개념과 새 슬라이드 ID를 대응시킵니다.
3. 각 항목에 `자료상 해결 / 일부 해결 / 미해결 / 확인 불가`와 새 근거 위치를 남깁니다. 설명 문구만 늘었는지, 실행 예제·시작 자료·완료 기준·대안까지 연결됐는지 구분합니다.
4. 시간은 계획 합계와 활동 배치를 점검합니다. 실제 소요 시간이나 학습 성취는 수업·파일럿 관찰 전까지 미확인으로 남깁니다.
5. 이번 기록의 해결 여부는 자료 개선의 근거일 뿐입니다. 실제 수강생의 이해, 실습 완료, 공개 MVP 완성은 별도의 수업 관찰로 검증해야 합니다.

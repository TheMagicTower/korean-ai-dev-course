스킬 → MCP → 긴 작업, 세 단계를 직접 해 본다

준비물: 지난주까지 만든 하네스 폴더(Git 저장소) · Node.js(npx 사용) · Claude Code 또는 Codex 로그인

순서는 세 단계입니다. 먼저 제가 평소 하는 작업 방식 하나를 SKILL.md 한 장으로 만듭니다. 다음으로 MCP 서버 하나를 연결해서 에이전트가 쓸 수 있는 도구를 늘립니다. 마지막으로 완료 조건과 상한을 적은 긴 작업을 맡기고, 시간과 턴, 토큰을 기록합니다. 마지막 기록이 과제 제출물의 일부이니 터미널 화면이나 상태 출력을 꼭 남겨 두세요. 준비물은 지난 시간까지 쓰던 하네스 저장소와 Node.js, 그리고 로그인된 에이전트 도구입니다. 시간 배분은 스킬 15분, MCP 15분, 긴 작업 20분, 과제 안내 10분 정도로 잡았습니다.

code.claude.com/docs/en/skills#create-your-first-skill
공식 문서 화면 캡처 · 2026-10-28 확인
Claude Code 문서의 ‘첫 스킬 만들기’ 절. 폴더를 만들고 SKILL.md를 두는 순서를 예제로 보여 준다.
$ mkdir -p ~/.claude/skills/pre-commit-check # ~/.claude/skills/pre-commit-check/SKILL.md --- description: 커밋 직전 변경을 점검한다. 커밋하기 전, diff 확인, 리뷰 요청 때 사용. disable-model-invocation: false --- ## 현재 변경 !`git diff HEAD` ## 지침 1. 테스트 실행, 실패하면 중단 2. 위험한 변경 3줄 이내로 보고

프로젝트 전용은 .claude/skills/<이름>/SKILL.md에 두고 저장소에 커밋합니다. frontmatter(맨 위 메타데이터 블록)는 파일 첫 줄부터.

공식 문서의 첫 스킬 예제와 같은 구조입니다. 개인용은 홈의 .claude/skills 아래, 프로젝트 전용은 저장소의 .claude/skills 아래에 폴더를 만들고 그 안에 SKILL.md를 둡니다. 맨 위 frontmatter에서 가장 중요한 것은 description입니다. 문서에 따르면 Claude가 언제 이 스킬을 불러올지 이것으로 판단하고, 설명과 when_to_use를 합친 글은 1,536자에서 잘리니 쓰임새를 앞에 쓰라고 합니다. 이름을 따로 안 적으면 폴더 이름이 곧 명령 이름이 됩니다. 느낌표와 백틱으로 쓴 줄은 스킬이 실행될 때 명령 결과를 본문에 채워 넣는 기능입니다. 화면의 예시는 제가 수업용으로 줄인 것이니, 여러분은 자기 작업에 맞게 바꾸세요.

실습 2 · MCPClaude Code MCP 문서 · MCP(에이전트를 외부 도구에 잇는 규약, 2024-11-25 발표)

MCP 서버는 명령 한 줄로 Claude Code에 붙인다

code.claude.com/docs/en/mcp#option-3-add-a-local-stdio-server
공식 문서 화면 캡처 · 2026-10-28 확인
Claude Code MCP 문서의 ‘로컬 stdio 서버 추가’ 절. claude mcp add 한 줄로 내 컴퓨터에서 도는 서버를 붙인다.
# 내 컴퓨터에서 도는 서버(stdio): Context7 예 $ claude mcp add context7 -- npx -y @upstash/context7-mcp # 원격(HTTP) $ claude mcp add --transport http notion \ https://mcp.notion.com/mcp $ claude mcp list $ claude mcp get context7 > /mcp # 세션 안에서 상태 확인

옵션(--env, --scope)은 이름 앞에, 서버 명령은 -- 뒤에 씁니다.

MCP 서버 연결은 명령 한 줄입니다. 로컬 프로세스로 도는 서버는 이름 뒤에 두 개의 하이픈을 쓰고 그 뒤에 서버를 실행하는 명령을 그대로 적습니다. 여기서는 10교시에 본 Context7, 즉 최신 라이브러리 문서를 가져다 주는 서버를 예로 들었습니다. 원격 서버는 transport를 http로 주고 주소를 적습니다. 연결 뒤에는 claude mcp list로 상태를 보고, 세션 안에서는 슬래시 mcp로 확인합니다. 환경 변수가 필요한 서버는 env 옵션을 쓰는데, 문서에 따르면 env 바로 뒤에 서버 이름을 두면 이름이 또 하나의 값으로 읽히므로 다른 옵션을 사이에 끼워야 합니다. 꼭 Context7이어야 하는 것은 아니고, 10교시에 소개한 서버 중 내 프로젝트에 쓸모 있는 하나를 고르세요.
실습 2 · MCPCodex MCP 문서 · ~/.codex/config.toml

Codex는 같은 MCP 서버를 설정 파일에 적어 붙인다

learn.chatgpt.com/docs/extend/mcp
공식 문서 화면 캡처 · 2026-10-28 확인
Codex의 MCP 문서 첫 화면. MCP로 Codex를 외부 도구·정보에 연결한다고 설명한다. 설정 파일 형식은 오른쪽.
# ~/.codex/config.toml [mcp_servers.context7] command = "npx" args = ["-y", "@upstash/context7-mcp"] [mcp_servers.figma] url = "https://mcp.figma.com/mcp" bearer_token_env_var = "FIGMA_OAUTH_TOKEN" # 선택: startup_timeout_sec = 20 > /mcp # 연결된 서버 보기

프로젝트 전용은 .codex/config.toml(신뢰한 프로젝트만). 토큰은 값이 아니라 환경 변수 이름으로 적습니다.

Codex는 설정 파일의 mcp_servers 표에 서버를 적습니다. 로컬 서버는 command와 args, 원격 서버는 url을 쓰고, 인증 토큰은 파일에 직접 쓰지 않고 bearer_token_env_var로 환경 변수 이름만 적습니다. 문서에 따르면 시작 제한 시간 기본값은 10초, 도구 호출 제한은 60초이고 서버별로 바꿀 수 있습니다. 프로젝트 안의 점코덱스 폴더에 같은 설정을 두면 프로젝트 전용이 되는데 신뢰한 프로젝트에서만 적용됩니다. 형식은 다르지만 Claude Code와 구조는 같습니다. 이름, 실행 명령이나 주소, 필요한 환경 변수. 이 세 가지만 기억하시면 됩니다. 제출물에 설정을 넣을 때는 토큰 값이 섞이지 않았는지 꼭 확인하세요.
실습 2 · MCPClaude Code MCP 범위 · 프로젝트 서버 승인

MCP는 저장 위치를 고르고 믿을 서버만 연결한다

{{svg:p12-mcp-scope}}

--scope project로 만든 .mcp.json은 팀에 공유되고, 대화형 세션에서 승인 질문이 뜹니다. 서버가 가져오는 외부 글은 프롬프트 주입(글 속 명령에 에이전트가 속음) 위험이 있습니다. → 결론: 범위는 좁게, 서버는 믿을 곳만

Claude Code는 서버 설정을 어디에 저장할지 scope로 정합니다. 기본값 local은 이 프로젝트에서 나만 쓰고, user는 내 모든 프로젝트에서 쓰고, project는 저장소 루트의 mcp 점 json에 저장되어 버전 관리로 팀과 공유됩니다. 프로젝트 범위 서버는 대화형 세션에서 처음 쓸 때 승인을 묻습니다. 문서는 연결 전에 각 서버를 신뢰할 수 있는지 확인하라고, 외부 내용을 가져오는 서버는 프롬프트 주입 위험이 있다고 경고합니다. 10교시에서 본 도구 설명 주입과 토큰 비용 문제가 바로 여기서 실제가 됩니다. 과제에서는 project 범위로 만들어 제출하시면 설정 파일이 그대로 증거가 됩니다.

긴 작업은 측정 가능한 완료 조건을 줘서 맡긴다

code.claude.com/docs/en/goal#write-an-effective-condition
공식 문서 화면 캡처 · 2026-10-28 확인
/goal 문서의 ‘효과적인 조건 쓰기’ 절. 조건에는 끝 상태 하나와 그 증명 방법을 담으라고 한다.
  1. 끝 상태 하나: 테스트 결과, 종료 코드, 빈 큐
  2. 증명 방법: “npm test 종료 코드 0”
  3. 건드리면 안 되는 것: “다른 테스트 파일은 수정 안 함”
상한 문구(20턴 넘으면 멈춤): or stop after 20 turns
/goal은 완료 조건을 주면 그 조건이 충족될 때까지 매 턴 뒤에 별도의 모델이 확인하고 계속 일하게 하는 기능입니다. 문서가 강조하는 점은 평가 모델이 명령을 직접 실행하거나 파일을 읽지 않고, 대화에 드러난 내용만 보고 판단한다는 것입니다. 그래서 조건은 에이전트의 출력으로 증명되는 문장이어야 합니다. 끝 상태 하나, 증명하는 방법, 지켜야 할 제약 이렇게 세 가지를 쓰세요. 조건은 4,000자까지 쓸 수 있고, 몇 턴 안에 끝내라는 상한 문구를 조건에 넣으면 에이전트가 턴마다 진행 상황을 보고합니다. 이 상한이 오늘 실습의 핵심입니다.

직접 도식 · 성공 기준과 상한
왼쪽 위의 나쁜 예는 사람에게는 통하지만 평가 모델에게는 기준이 없습니다. 아래의 좋은 예는 끝 상태, 증명 방법, 변경 금지 범위, 상한이 모두 들어 있습니다. 도식처럼 매 턴 조건을 확인하고, 충족하면 끝내고, 아니면 상한을 확인합니다. 상한이 없으면 비용이 끝없이 늘 수 있으니 반드시 넣으세요. 문서에 따르면 상태는 슬래시 goal만 입력하면 조건, 경과 시간, 평가한 턴 수, 토큰 사용량, 마지막 판정 이유를 보여 주고, 슬래시 goal clear로 해제합니다. 자동 승인 모드에서 돌리면 도구 호출 승인도 없어집니다. 맡길 작업은 이번 주 하네스에서 테스트가 있는 작은 기능이 좋습니다.

같은 작업을 될 때까지 반복해 사람이 매번 다시 시키지 않아도 된다. 셸 몇 줄이면 짤 수 있다.
상한 없이 무한 반복하면 비용이 끝없이 늘 수 있다. 그래서 횟수·시간 상한이 꼭 필요하다.
핵심은 반복이 아니라 명령으로 판정하는 성공 기준과 상한. Codex에도 /goal이 있다(구문은 설치한 버전에서 확인).
/goal을 쓸 수 없는 환경이거나 코드형 트랙이라면 루프를 직접 짭니다. 구조는 같습니다. 일을 한 번 시키고, 성공 기준을 사람이 아닌 명령으로 판정하고, 상한에 닿으면 멈춥니다. 2025년 7월 Ralph 루프가 바로 이 방식이었는데, 상한 없이 무한 반복한다는 점이 위험했습니다. 화면의 셸 예시는 비대화형 실행 옵션으로 작업 파일을 읽히고 테스트가 통과하면 빠져나옵니다. 횟수와 시간 상한이 같이 있다는 점을 봐 주세요. 코드형 트랙은 이 루프를 자기 하네스 안에서 돌고, 매 회 시간과 토큰을 기록하게 만들면 과제의 실행 기록까지 한 번에 해결됩니다. 장점은 같은 작업을 될 때까지 반복해 맡길 수 있다는 점입니다. 단점은 상한이 없으면 비용이 끝없이 늘 수 있다는 점입니다. 의미는 반복보다 명령으로 판정하는 성공 기준과 상한이 핵심이라는 것입니다.

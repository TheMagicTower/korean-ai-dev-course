GitHub 블로그의 Spec Kit 소개 글. 제목은 ‘AI와 함께하는 스펙 주도 개발’(SDD).
  1. 요구사항을 스펙(명세서)으로 쓴다
  2. 스펙을 계획과 Task(할 일 한 단위) 목록으로 쪼갠다
  3. Task마다 스펙과 대조하며 구현한다
요구사항→스펙→Task→스펙 대조 구현으로 에이전트가 딴길로 새는 것을 붙잡는다.
스펙은 길어지고 금방 낡는다. 에이전트는 낡은 스펙도 믿는다(30번 장).
같은 문제를 푸는 두 갈래: 도구 안의 Plan 모드와 문서 중심의 SDD.
→ 5교시에서 자세히
에이전트가 한 번에 많은 일을 하자, 중간에 목표를 잊고 딴길로 새는 일이 잦아졌습니다. 답은 먼저 쓰고 나중에 구현하는 것이었습니다. SDD라는 약어는 1987년 IEEE(Institute of Electrical and Electronics Engineers, 전기전자공학자협회) 1016의 소프트웨어 설계 기술서, Software Design Description에서 먼저 쓰였습니다. 사람에게 설계를 전하는 문서였습니다. 지금 말하는 스펙 주도 개발, Spec-Driven Development는 2004년 같은 이름의 애자일 논문을 거쳐 2025년 에이전트 도구와 함께 퍼진 말입니다. 지금의 SDD는 요구사항을 스펙으로 쓰고, 계획과 Task 목록으로 쪼갠 뒤, Task마다 스펙과 대조하며 구현합니다. Claude Code의 Plan 모드가 2025년 6월, Kiro가 7월, GitHub Spec Kit이 9월에 나왔습니다. 명세 우선 개발이라는 생각 자체는 오래됐고, AI가 그것을 다시 필요하게 만들었습니다. 5교시에 SDD의 세 수준까지 자세히 봅니다. 장점은 스펙으로 에이전트를 붙잡는다는 점이고, 단점은 스펙이 길어지고 낡는다는 점입니다. 의미는 Plan 모드와 SDD가 같은 문제를 푸는 두 갈래라는 것입니다.
